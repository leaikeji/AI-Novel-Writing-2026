# 正文版本恢复、多标签冲突与离线恢复实测

实测日期：2026-08-22  
测试作品：《零点折城》  
测试章节：第 5 章《折返限定》；一次性手写第 6 章《多标签安全测试》（均位于第二卷）  
当前状态：R1 正文版本与故事账本恢复、R2 多标签冲突与本地草稿恢复均已完成；临时第 6 章已删除。

## 一、测试目标与隔离方式

本轮首先验证：同一章节先后保存两个内容和情报完全不同的 AI 版本，再恢复旧版本时，正文、本章情报、角色最新状态、主线事件、非主线路线和伏笔是否一起回退。

为避免破坏已有第 4 章证据，新增一次性测试章《折返限定》。两个版本使用相同角色和空私有库配置，只改变章纲中的专属事实：

| 维度 | 版本 A | 版本 B |
| --- | --- | --- |
| 场景 | 维修隧道 | 废弃北站钟楼 |
| 核心物 | 蓝色三角车票 | 银色怀表 |
| 时间 | 四点十二分 | 一点十七分 |
| 标记 | 红色工具箱、三声敲击 | 白鸽、2036、钟声 |
| 排除项 | 不出现银色怀表和北站钟楼 | 不出现蓝色车票、红色工具箱和四点十二分 |

角色固定为沈砚、周晓琳、陈卫国；关闭“允许 AI 新增角色”和“允许 AI 退场角色”；只选择主线，不手动选择伏笔。

## 四、恢复版本 A

### 4.1 恢复动作

点击第 1 次生成的“恢复此版本”后，确认文案称：

- 当前编辑器内容将被覆盖。
- 操作不可撤销。

恢复完成后又提示“请点击保存按钮保存修改”。因此恢复本身只改当前编辑稿，不是一次完整的正式版本切换。

恢复后的正文指纹：

- JavaScript 文本长度 2452。
- “蓝色”出现 6 次。
- “北站”和“银色”均为 0。

正文正确回到了 A；版本 B 仍保留在两条生成历史中，所以“不可撤销”文案与实际仍可再次选择 B 的能力相互矛盾。

### 4.2 本章情报

恢复后尚未保存时，点击“情报”已经显示版本 A 的情报：维修隧道、蓝色车票、A 的关系、A 的两个伏笔和 A 的线路事件。

也就是说，历史恢复同时切换了：

- 编辑器正文。
- 当前展示的章节情报快照。

但它没有在此时处理全局故事账本。

### 4.3 保存恢复版本后的全局结果

保存恢复后的 A，再检查全局主线：

1. 版本 B 的两条银色怀表事件仍然存在。
2. 版本 A 的三条蓝色车票事件被原样再次追加。
3. 主线因此出现 `A 三条 → B 两条 → A 三条`，共 8 条测试事件。

这是本轮最关键的结论：**正文恢复不是故事账本回滚；再次保存恢复版本反而会重复提交旧情报。**

线路没有再创建同名实体：支线仍为 5、感情线 5、势力线 4。但页面无法证明同名线路内部是否重复追加了不可见事件。伏笔仍为 9，两个 A 伏笔没有重复建卡，说明其按名称做了部分去重。

### 4.4 角色最新状态

为读取角色真实最新状态，新开一个未提交的章节向导进入“配置角色”，页面显示：

- 沈砚：在维修隧道深处盯着车票；发现蓝色三角车票并听到工具箱敲击。
- 周晓琳：在维修隧道探索；将车票藏进工具箱。
- 陈卫国：在维修隧道；承认车票来源并要求销毁。

因此再次保存 A 会把角色“当前状态”切回 A。但是角色编辑页只提供“删除最新记忆”，不展示记忆时间线、来源版本或恢复影响，无法判断 B 记忆是被覆盖、仍藏在历史栈中还是已失效。

## 五、真实状态模型

实测行为不是统一 revision，而是至少四套松散状态：

```text
生成历史版本
  -> 恢复编辑器正文
  -> 同时切换本章情报快照
  -x- 不回滚全局故事账本

再次保存恢复版本
  -> 角色最新状态切换到恢复版本
  -> 某些线路/伏笔按标题或名称复用
  -> 主线事件无幂等键地重复追加
  -x- 不使较新版本 B 的事件失效
```

这会造成正文现在讲蓝色车票，但全局主线仍把银色怀表和未来救援队当作已发生事实。

## 六、对本项目的强制约束

1. 历史恢复必须创建一个新的正式 revision，不能只覆盖编辑器工作稿。
2. 每个角色状态、关系、线路事件和伏笔进展必须绑定来源 chapter revision 和 proposal item。
3. 当前正文 revision 切换时，旧来源派生项先标记 `source_superseded`，从当前故事查询中排除。
4. 恢复到旧 revision 时，作者先看到将失效、重新生效和需要比较的完整变更集。
5. 同一情报 commit batch 重放必须幂等；恢复后再次保存正文不能重新提交相同事件。
6. 正文保存、分卷选择、正式 revision、情报采用和情报回滚必须是可独立执行的命令。
7. 角色记忆必须有可见时间线、来源 revision、当前/失效状态和可逆操作，不能只有“删除最新记忆”。
8. “本章未涉及”不能被保存为伏笔推进；无证据项默认拒绝。
9. 历史恢复文案必须准确区分“预览”“恢复为工作稿”“建立新 revision”和“同步故事账本”。
10. 全局故事账本默认只查询当前有效正文链上的派生项，历史事实仍可审计但不能混入生成上下文。

## 八、R2：多标签冲突与本地草稿恢复

### 8.1 隔离章节与手写入口

为避免再次重放第 5 章的 AI 情报，本轮新建一次性第 6 章，选择“我已有正文，点击直接填写”，只写短测试文本，不点击“同步进展”。流程为：

1. “新建章节”会先建立 URL 中带稳定章节 ID 的空章节壳，本次 ID 为 `573529`。
2. 点击标题旁铅笔，打开“编辑章节标题”；输入《多标签安全测试》后点击弹窗内第二个“保存”。
3. 标题保存立即显示“保存成功”，与正文保存相互独立。
4. 点击“我已有正文，点击直接填写”后，空态切换为正文编辑器。
5. 输入基线：“多标签冲突测试基线。正文仅用于保存冲突与离线恢复，不参与章节情报。”

即使本章没有任何 AI 情报，正文保存仍强制经历：

```text
保存
  -> 选择分卷
  -> “角色记忆将同步 / 最新进展不可撤销”确认
  -> 保存成功
```

这段确认对纯手写空情报章节仍然出现，属于错误的副作用暗示。首次保存时编辑器显示 33 字；加入单个标签后编辑器显示 41 字、章节列表显示 44 字，再次证实计数口径不一致。

### 8.2 两个标签页的实测顺序

两个标签页 A、B 同时打开已保存的同一基线，然后按下列顺序操作：

1. A 改为“基线 + `【标签A已保存】`”，完成分卷选择、不可撤销确认并保存成功。
2. B 不刷新，仍基于旧基线改为“基线 + `【标签B后保存】`”。
3. B 点击保存；系统没有提示服务端已有更新，也没有要求比较或合并，仍按普通保存流程成功。
4. 保存后 A 继续显示 A，B 显示 B；新开的第三个标签页显示 B。

结论：当前实现是**静默的 last-write-wins**。旧标签页不仅能覆盖新正文，还继续显示自己的陈旧内容，没有“已被其他窗口修改”提示。

### 8.3 手写版本无法从“历史”找回

B 覆盖 A 后打开“历史”，页面显示：

- “生成历史（共 0 次）”。
- “每次生成的内容都会自动保存”。
- “暂无生成历史”。

因此历史只收录 AI 生成结果，不收录手写保存检查点。被 B 覆盖的 A 不在站内任何可见版本列表中，作者无法恢复。这与第 5 章 AI 历史可恢复形成两套互不完整的版本机制。

### 8.4 未保存内容的四种离开行为

| 动作 | 页面行为 | 再进入后的结果 |
| --- | --- | --- |
| 点击“返回列表” | 出现“未保存的修改”，可选“保存后离开 / 直接离开” | 选择直接离开后，测试标记丢失，回到最近服务端正文 |
| 选择“保存后离开” | 跳过通常的分卷选择，直接出现不可撤销同步确认；随后又出现浏览器原生提示 | 正文保存成功并离开；但保存路径、路由和反馈与普通保存不一致 |
| 浏览器刷新 | 没有站内确认，也没有原生 beforeunload 提示 | 未保存标记立即丢失，回到最近服务端正文 |
| 关闭标签页后重开 | 没有恢复提示 | 未保存标记丢失，回到最近服务端正文 |

“保存后离开”还把章节路由从 `/novel/110432/chapter/573529` 切到 `/chapter/573529`，保存反馈使用原生 JavaScript alert；普通保存则使用站内“提示 / 确定”弹窗。相同业务动作存在两套路由和两套反馈组件。

本轮浏览器控制面没有网络离线开关，因此没有伪造“真正断网后继续输入”的结果。但刷新和关闭重开均无法恢复草稿，已经可以确认：当前页面至少没有可跨刷新/标签关闭恢复的耐久本地工作稿。真实断网重连仍应在自研产品中作为网络故障验收，而不是据此猜测竞品结果。

### 8.5 删除临时章又暴露分卷计数幽灵

删除前检查“情报”，面板只有标题，没有角色、关系、线路或伏笔条目，所以临时章不含需保留的派生证据。删除弹窗仍统一警告：删除章节不会删除最新进展，需要作者自行删除线路事件和角色最新记忆。

确认删除后：

- 全书由 6 章、5435 字正确回到 5 章、5384 字。
- 第 6 章不再出现在列表。
- 第二卷实际只列出第 5、4 章，共 2 章。
- 第二卷标题却继续显示“3 章”。
- 新开页面后仍显示“3 章”，不是当前 DOM 的瞬时缓存。

因此删除章节更新了作品总章数和总字数，却没有更新分卷聚合计数。聚合数据不是同一事务维护，也不是从当前章节实时派生。

### 8.6 对本项目新增的强制约束

11. 所有手写保存也必须进入统一 revision/checkpoint 历史；AI 生成历史不能是唯一可恢复版本。
12. 保存 working copy 必须提交 `base_revision_id` 或 `expected_version`；旧基线保存返回冲突和三方比较，不能静默覆盖。
13. 编辑中的正文按防抖写入 IndexedDB；刷新、崩溃、关闭重开和重新登录后提供草稿恢复预览。
14. 站内跳转、刷新、关闭标签页使用一致的 dirty 状态；恢复稿成功落盘后才允许静默离开。
15. “保存后离开”复用普通保存命令和反馈组件，不能绕过分卷/版本规则、切换到另一套路由或弹原生 alert。
16. 纯正文保存不选择分卷、不触发也不宣称同步角色记忆；移动分卷和采用情报是独立命令。
17. 作品、分卷和章节聚合数必须在同一事务更新，或统一从未归档章节派生；删除后刷新不得出现幽灵计数。

## 九、R2 最终判定

```text
并发保护：失败——无 expected_version，无冲突提示，旧标签静默覆盖
手写历史：失败——0 条生成历史，被覆盖手稿不可恢复
站内离开保护：部分通过——有自定义确认，但保存后离开走另一流程
刷新恢复：失败——无提示、无本地草稿恢复
关闭重开恢复：失败——无本地草稿恢复
分卷聚合一致性：失败——删除后实际 2 章仍显示 3 章
故事账本隔离：通过——临时手写章情报为空，删除前未同步进展
```
