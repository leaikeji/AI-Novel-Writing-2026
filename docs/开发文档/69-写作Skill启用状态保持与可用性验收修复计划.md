## 2. 修复方案与冻结约束

### A. 统一插件替换流程

复用现有安装脚本，统一“快照、恢复、核验”三个小步骤；保留热安装和离线维护各自的启停顺序。将配置脚本已有的Skill开关读写抽为窄函数，完整`configure()`和安装收尾复用它；单独恢复只操作专用Agent的项目Skills，不顺带更新提示文件、工具或模型。

- 停止旧宿主／替换插件之前取得公开快照。保持`skill-enable-state/1`字段不变，将其作为现有本次发布证据／恢复目录中的一个文件保存，复用已有候选哈希、目标身份及运行编号；没有发布目录时要求调用方给出持久输出路径。只补必要的前后比较结果，不新建快照数据库、备份服务、定时扫描或通用回执框架。
- 对既有Agent，记录每个Skill的显式开关；安装后精确恢复。新增获批Skill沿用现有发布策略，单独列出，不能用“新增”掩盖旧项丢失。
- 替换前缺失／不匹配基线应先停在替换动作之前。已有Agent却得到空目录时不能把所有模块解释为“新增”；只有公开证据确认新建Agent或明确初始化意图，才执行初始启用。完整全关快照、空目录、未知状态必须区分；旧版非空有效快照继续兼容。
- 在线完整安装：捕获 → 替换 → Skill恢复 → 按原流程重启 → 最终逐项读回。直接热安装函数应要求调用方提供已捕获基线并完成收尾，不能返回一个可被当成完整发布PASS的结果。
- 离线`offline-install-stopped`：继续保持“不启、不停宿主”的原合同；接收停机前冻结快照，替换后只报告`pending_skill_restore`。由现有发布责任人在schema等原门禁通过、按原流程启动宿主后调用同一Skill恢复与核验。不得为本问题提前启动旧包或新包。
- 恢复异常时先公开读回，只对与冻结预期不一致的项补偿一次；仍不一致则停止发布成功判定并保留快照／差异。禁止无限重试或重放整套安装。单纯Skill失败不触发自动降包、重跑迁移或数据库回滚；确需旧包恢复时沿用原发布方案的兼容性门禁。
- 明确区分升级替换与作者完整卸载：卸载应清理插件注册；作者重新安装时是否恢复保留的专用Agent选择，必须有可核对的先前快照或显式初始化意图。

并发只使用项目安装互斥；若现有脚本确无进程锁，在安装脚本内补标准库文件锁，不引入锁服务。锁覆盖捕获至恢复核验；离线跨进程维护沿用单一发布责任人。该锁不能阻止作者在原生页面同时修改设置，因此维护期间须避免并行改Skill；不伪称公开接口提供了CAS，也不在后台反复覆盖用户选择。

### B. 修正验收语义

- `state_preserved`：提供基线时逐项比较，取true/false；无基线为null（未核验）。明确全关可以保持成功。比较范围为仍受本次发布支持的旧项，新发布与移除项单列；不要求已移除模块重新出现。
- `writing_skills_ready`：只表示当前受管任务必需的Skill文件／启用状态可用，不证明模型、原生聊天自动路由或文学质量。复用`backend/writing_skills/primary.py`当前任务映射，输出缺失主Skill及可选分类模块状态；不要求9个通用Skill全部成为每次任务的必需项。
- `scope_isolated`：Default、QA及其他Agent的状态不因专用Agent恢复改变。
- 在现有验证命令输出中增加上述字段，不新增产品API、页面或常驻检查。发布保态门禁要求`state_preserved=true`；独立写作Skill就绪检查不可用时返回非零。显式全关的保态用例可以通过，但须同时输出`writing_skills_ready=false`，不得合并为“写作验收PASS”。
- `configure()`对已有Agent缺少快照的保守行为可以保留，但输出必须明确“未恢复／无基线”，不能报告初始化完成。

不把全部分类Skill强制开启作为通过条件：作者明确关闭金手指或悬疑时应被保留，报告准确显示该分类不可用；主任务被关闭时对应生成不能被宣称可用。
