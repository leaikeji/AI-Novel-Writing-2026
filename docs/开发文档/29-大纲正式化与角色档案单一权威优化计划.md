## 0. 最终裁决

### 0.1 一句话方案

作者可以把当前已填写的任意大纲模块（允许部分为空）正式化，也可以显式不采用草稿并直接写作；两条路径都会建立不可变的正式规划基线。此后大纲页只读取正式大纲和正式角色卡，`OutlineDraft` 永久退出普通编辑路径，AI 只能生成候选，不能重新批量覆盖正式角色。

### 0.2 这次真正要修的不是页面，而是权威边界

当前同一 PostgreSQL 数据库内存在两份角色表示：

| 表／字段 | 当前用途 | 正确定位 |
| --- | --- | --- |
| `outline_drafts.characters_json` | 五步向导中的角色快照 | 仅限首次正式化之前的生成草稿，不是角色档案 |
| `novel_characters` | 角色页、关系网及部分下游能力使用的角色实体 | 正式角色当前态的唯一权威 |
| `novels.background/main_plot/highlight/outline_target_chapters` | 正式大纲当前值 | 兼容读取投影；正式历史由不可变 revision 负责 |

现有大纲阅读卡读取 `Novel` 正式字段，点击编辑却重新加载 `OutlineDraft`；角色页读取 `novel_characters`。因此，同一个页面在“看正式数据、改草稿数据”，最终再次点击完成时还会尝试把草稿角色并入正式角色。这才是角色对不上和已有作品可能越改越乱的根因。

### 0.3 与现有计划的冲突裁决

本文在以下窄范围内取代旧决策，不改写历史记录：

1. 取代文档 07 于 2026-08-28 冻结的“已有大纲继续复用五步草稿完成接口”行为；五步 UI 可以继续用于**首次初始化**，但不能继续用于**正式化后的维护**。
2. 取代文档 28 第 3.2 节中“正式大纲和角色继续通过现有 `OutlineDraft` 与完成事务更新”的部分，以及该问题上的“零新表”约束。没有持久正式基线和不可变历史，无法可靠区分草稿与正式数据，也无法安全恢复。
3. 文档 28 的两页建书、单页章前卡、一次点击一次模型调用等其他裁决继续有效；但其大纲单页重构必须在本文权威修复之后施工。
4. 文档 26 的角色候选安全应用保留；本文实施后，任何正式角色基线变更还必须写入独立的不可变角色 revision，但不再推动 outline head 或复制完整角色卡到每一版大纲。
5. 文档 27 若先施工，其 `StoryFact.character_id` 等迁移可被本文复用；若尚未施工，本文不得重复建设第二套人物事实模型，角色改名先依靠影响预览、正式别名和旧姓名兼容解析保证安全。

### 0.4 本轮明确不做

- 不修改 QwenPaw 上游核心、私有会话、私有数据库或安装包。
- 不自动修复、删除、合并或覆盖现有小说数据。
- 不自动重写已经存在的章节正文、章纲、故事事实或人物关系。
- 不在 P0 恢复“全书重新生成人物”或“一键重新规划全书”。
- 不新建第二个角色库、第二个 Agent Runtime、任务队列或模型选择器。
- 不把 `OutlineDraft.state`、章节数量、章节 revision 数量或正文是否为空当作未来生命周期权威。

## 1. 已核实实现事实

### 1.1 当前代码事实

- `backend/models.py` 中 `OutlineDraft.characters_json` 与 `NovelCharacter` 是两套独立持久表示。
- `frontend/src/workbench-studio.ts` 的正式大纲卡读取 `novel.highlight/background/main_plot`，进入编辑时却调用 `GET /novels/{id}/outline-draft`。
- 同文件角色页调用 `GET /novels/{id}/characters`，因此大纲角色与角色页天然可能漂移。
- `complete_outline_draft()` 只在 `character_id` 存在时按稳定 ID 匹配；旧草稿没有 ID 时会按姓名做兼容匹配，其他草稿角色可能新建为正式角色。
- `update_novel_character()` 只更新正式角色，不把修改反写到大纲草稿。
- `update_outline_draft()` 每次保存都把状态写回 `draft`；仅凭草稿状态无法知道作品是否已经正式化。
- 创建章节会生成初始 revision；“存在 revision”也不能准确代表作者已经写过正文。
- `ChapterBrief.role_constraints` 当前保存姓名数组；`StoryFact.subject` 也是文本。稳定角色 ID 尚未覆盖全部下游引用，改名不能只改一行角色记录。
- `character_aliases` 已存在且以稳定 `character_id` 关联正式角色，但目前主要服务朗读识别，尚未成为全产品统一的姓名兼容层。
- 当前存在两条建书路径：`complete_novel_creation_draft()` 创建空小说，旧 `POST /novels` 则立即创建默认卷章；后者若不纳入正式化事务，会绕过未来的 outline head 守卫。
- 正式角色除手工新增／编辑／归档外，还会被角色卡 AI 候选应用和批次恢复修改；这些写路径必须进入同一个角色 revision 与目录版本事务。
- `backend/app.py` 与 `backend/creative_api.py` 当前只为少数冲突返回结构化 `detail.type`，普通 `ValidationError` 仍是字符串；新增生命周期错误不能只在某一个路由适配器中实现。
- `frontend/src/chapter-workflow.ts` 仍把章纲角色约束作为姓名文本读写；ID 化必须同时修改其表单投影、请求 DTO 和兼容读取。
- `novel.description` 是建书阶段的作品简介／元数据，当前 `complete_outline_draft()` 却会用 `highlight_text` 覆盖它；这是既有耦合，不应被新的兼容投影继续固化。

### 1.2 已核实现有作品风险

只读核查小说《潮声替我说晚安》时发现：

- 正式角色为 5 人：苏晚、陆沉舟、周柚、何漫、唐知渔。
- 大纲草稿为 6 人：苏晚、陆沉舟、外婆、开发商、老听众、老邻居，且都没有 `character_id`。
- 两侧只有苏晚、陆沉舟同名，内容仍不完全相同。
- 按当前完成逻辑再次提交，苏晚、陆沉舟会保留正式非空资料，四名草稿角色可能新增，周柚、何漫、唐知渔仍会保留，最终正式角色可能变成 9 人，而不是作者直觉中的 6 人替换 5 人。
- 当前正式章节规划仍以苏晚、陆沉舟、周柚、何漫等姓名为角色约束，证明批量替换或无预览改名会影响已写内容的一致性。

上述数据仅作只读证据。本文规划阶段没有修改该小说；后续回填必须保留正式 5 人，草稿 6 人只能隔离为历史草稿／候选，不能自动合并。

## 2. 目标、非目标与硬不变量

### 2.1 目标

1. 大纲阅读、编辑、AI 上下文和角色页使用同一组正式权威数据。
2. 首次初始化与开书后维护成为两个明确模式，不能靠页面猜测或草稿状态切换。
3. 正式大纲每次采用、手工保存和恢复都创建不可变 outline revision，支持比较、审计与恢复。
4. 正式角色始终使用稳定 ID 和独立不可变 character revision；大纲页不维护第二份可写角色卡，也不把角色详情复制为大纲当前态。
5. AI 只产生草稿或候选；采用时校验正式基线、CAS、幂等键和角色映射。
6. 已有书允许继续编辑目标章节数、背景、情节、亮点和角色，但风险不同、处理规则不同。
7. 现有双轨数据可通过只读预检、备份、可复核回填和兼容投影安全收敛。

### 2.2 非目标

- P0 不提供多套大纲分支、协作审阅或全书自动重写。
- P0 不让模型批量删除、替换、重命名或归档正式角色。
- P0 不自动判断新背景／情节与正文的文学一致性；先提供确定性影响范围与 revision Diff，语义一致性报告以后作为候选能力增加。
- P0 不重构关系网、故事事实或正文 revision 的既有权威模型。
- P0 不要求文档 28 的整套 UI 压缩同时上线；先让现有 UI 使用正确数据。

### 2.3 硬不变量

1. `NovelCharacter` 是正式角色当前态的唯一权威；草稿角色不能覆盖它。
2. 正式大纲当前态由正式 outline head 指向的不可变 revision 决定；`Novel` 文本字段只是同事务维护的兼容投影。
3. 正式化之后，普通大纲编辑永不读取或保存 `OutlineDraft`。
4. 模型结果未被作者采用前，对正式大纲、正式角色、正文和故事账本零写入。
5. 任何正式采用都必须以服务端范围校验、对应领域 CAS、依赖摘要和幂等键为前提；outline version 与 character catalog version 互不代替。
6. 角色改名不重写历史正文；旧姓名进入正式别名，所有无法确定的文本引用显示为待处理，不静默猜测。
7. 角色不硬删除；已被引用的角色只能经影响预览后归档，历史 ID 永久保留。
8. 恢复历史永远创建新 revision，不倒拨指针后改写旧 revision。
9. 页面生成按钮继续跟随 `ai-novel-writer` 的有效模型，不新增模型选择器或静默回退。
10. 正式化前，公开的角色、分卷、章节和故事线写接口必须返回 `outline_not_committed`；只有建立正式基线的事务可以内部创建正式角色。该约束必须在服务层执行，不能只靠隐藏前端按钮。
11. 角色变化只推进角色自身 version 和小说级 `character_catalog_version`，不推进 outline head；大纲变化也不伪造角色 revision。
12. `novel.description` 与大纲 `highlight_text` 是两个独立作者字段；正式大纲保存、采用和恢复不得覆盖作品 description。
13. 同一小说中的 active 正式姓名和 active alias 共用规范化身份命名空间；任何新增或改名都必须在小说级锁内校验，不能只依赖大小写敏感的数据库姓名唯一键。

## 3. 唯一生命周期模型

### 3.1 只有两个持久模式

| 模式 | 可靠判定 | 页面数据源 | 可用行为 |
| --- | --- | --- | --- |
| `initializing` | 当前小说没有 `novel_outline_heads` 记录 | `OutlineDraft`；正式角色表仅用于旧数据冲突检查 | 五步或未来单页初始化、手填、AI 生成草稿、采用当前已填内容、显式不采用草稿 |
| `maintaining` | 当前小说存在 `novel_outline_heads` 记录 | 正式 outline revision + `NovelCharacter` | 局部编辑、局部 AI 候选、历史比较、角色新增／编辑／归档 |

`replanning` 不成为第三个正式模式。未来若恢复“重新规划全书”，它只能创建以当前正式 revision 为基线的候选分支；采用前仍处于 `maintaining`，不能产生第二份当前真相。P0 不交付该入口。

### 3.2 两条进入正式维护的显式路径

#### 路径 A：保存当前已有内容并开始写作（默认）

```text
初始化草稿
  -> 作者点击“保存已有内容并开始写作”
  -> 锁定草稿、小说、正式角色和 outline head
  -> 校验草稿 version、字段上限与角色冲突处理
  -> 仅采用作者选择的当前有效 section；未填写 section 保持空值
  -> 对草稿中实际存在的角色逐项新建／映射／放弃
  -> 创建首个不可变正式 revision
  -> 创建 outline head
  -> 同事务更新 Novel 兼容投影
  -> 草稿标记完成
  -> 进入 maintaining
```

首次正式化**不再要求**背景、情节、亮点全部非空，也不要求至少一个角色或主角。目标章节数使用草稿中的有效值；其余每个模块独立采用，避免作者只写完背景时被迫补齐或丢弃已完成内容。

#### 路径 B：明确不采用草稿并直接写作

作者可以点击次级动作“不采用这些草稿，直接开始写作”。如果任何 section 或角色草稿非空，页面必须先列出将被隔离的模块和角色数量，并要求二次确认；服务端校验草稿 version 后，以当前 `Novel.outline_target_chapters` 的兼容默认值（新书当前为 200）创建空文本的 `manual_empty_baseline` revision 和 outline head，不采用草稿中的目标章数。草稿原样保留为只读恢复证据，但不再自动应用。

路径 B 不是路径 A 的隐式别名：A 采用已有的部分内容，B 明确不采用。草稿完全为空时两者生成的正式文本可以相同，但 `source_kind` 与审计摘要仍不同。

角色、分卷、章节和故事线的公开创建服务都必须复用同一个 `_require_formal_outline_head()` 领域守卫。客户端若直接绕过页面调用这些 API，也只能先得到结构化 `outline_not_committed`，再由作者显式选择路径 A 或 B。

唯一兼容例外是旧 `POST /novels`：该接口的既有契约本来就是“一次创建可立即写作的小说、默认卷和默认章”。它必须在同一事务中先创建 `manual_empty_baseline` 和 head，再创建卷章，并在响应中返回 `lifecycle=maintaining`；任一步失败全部回滚。新建书向导的 `complete_novel_creation_draft()` 仍只创建空小说并返回 `lifecycle=initializing`，不会暗中创建 head、卷或章。W0 必须冻结旧入口弃用标记和契约测试，前端新流程不得重新调用旧入口。

### 3.3 正式化后的编辑边界

| 模块 | 是否可改 | 默认行为 | AI 行为 | 特殊风险 |
| --- | --- | --- | --- | --- |
| 目标章节数 | 是 | 手工保存并创建 revision | P0 不需要 AI | 只是规划目标，不创建／删除章节 |
| 故事背景 | 是 | 当前正式值上编辑，保存前展示 Diff | `refine/fresh` 均只生成候选 | 不自动修改正文、事实或设定 |
| 主要情节 | 是 | 当前正式值上编辑，保存前展示 Diff | 只生成局部候选 | 已有章节时提示可能影响后续规划 |
| 亮点与简介 | 是 | 当前正式值上编辑 | 只生成候选 | 低风险，不回写剧情事实 |
| 正式角色 | 是 | 直接读取／编辑 `NovelCharacter` | P0 无批量重生成人物；现有单角色性格候选能力保留 | 改名、归档必须先做影响预览 |
| 人物关系 | 是 | 继续使用关系网领域服务 | 不回写大纲草稿 | 与角色基线独立版本化 |

## 4. 正式数据模型

### 4.1 新增 `novel_outline_revisions`

这是不可变的正式规划快照，不是第二个当前大纲表。冻结字段：

| 字段 | 说明 |
| --- | --- |
| `id` | revision UUID |
| `novel_id` | 当前小说，带本地范围校验 |
| `revision_number` | 单小说单调递增 |
| `parent_revision_id` | 上一个正式 outline revision |
| `restored_from_revision_id` | 仅恢复操作填写 |
| `source_kind` | `legacy_backfill / initial_commit / manual_empty_baseline / manual_edit / ai_adopt / restore` |
| `source_job_id` | AI 候选采用时关联 `CreativeGenerationJob`，其他情况为空 |
| `idempotency_key` | 同一小说内唯一；相同 key、相同请求返回同一 revision，不同请求冲突 |
| `request_hash` | 对操作类型、基线、patch／采用决定和幂等语义计算的规范化哈希，用于拒绝同 key 异请求 |
| `target_chapter_count` | 规划目标 |
| `background_text` | 正式背景快照 |
| `plot_text` | 正式主情节快照 |
| `highlight_text` | 正式亮点／简介快照；是否以后拆分另立产品决策 |
| `character_revision_refs_json` | 仅保存当时可见角色的 `{character_id, character_version}` 有序引用，不复制姓名、描述或 details |
| `character_reference_digest` | 对上述引用清单计算的规范化 SHA-256 |
| `change_set_json` | 本次改变的 section、来源和影响摘要，不存正文、Prompt 或角色详情 |
| `content_hash` | 只对目标章数与三个正式文本 section 计算的规范化 SHA-256 |
| `created_at` | 创建时间 |

数据库至少包含 `(novel_id, revision_number)`、`(novel_id, idempotency_key)` 唯一约束，以及 `(id, novel_id)` 组合唯一键供 head 做小说范围外键。`parent_revision_id` 与 `restored_from_revision_id` 也必须带小说范围外键，禁止跨小说串联。

角色引用清单只用于解释“这一版大纲生成／保存时看到了哪些角色版本”。当前大纲页面的角色卡始终实时读取 `NovelCharacter`，历史页面则按清单读取对应 character revision；角色变化本身不创建 outline revision。

### 4.2 新增 `novel_outline_heads`

每个已正式化小说恰好一行：

| 字段 | 说明 |
| --- | --- |
| `novel_id` | 主键并外键到 `novels` |
| `current_revision_id` | 指向同一小说的当前 outline revision，非空 |
| `version` | 专用 outline CAS，首版为 1；只在正式规划文本／目标章数变化或 outline 恢复时递增 |
| `established_at` | 系统实际建立正式基线的时间；旧数据不伪造历史时间 |
| `establishment_source` | `author_commit / author_discard / legacy_direct_create / legacy_backfill` |
| `updated_at` | 当前 head 更新时间 |

`current_revision_id + novel_id` 必须使用组合外键保证不能串到其他小说。迁移需验证小说删除的级联顺序；正式 revision 没有删除 API。

### 4.3 新增 `novel_character_revisions` 与角色目录版本

`NovelCharacter` 继续是正式角色当前态；新增表只保存不可变历史，不成为第二个当前角色库。冻结字段：

| 字段 | 说明 |
| --- | --- |
| `id` | character revision UUID |
| `novel_id` | 小说范围 |
| `character_id` | 指向同一小说的正式角色 |
| `character_version` | 对应 `NovelCharacter.version`，允许 legacy 首版从大于 1 的现值开始 |
| `parent_revision_id` | 该角色上一个不可变 revision |
| `restored_from_revision_id` | 仅逐角色恢复填写 |
| `source_kind` | `legacy_backfill / initial_commit / manual_create / manual_edit / ai_adopt / restore / archive` |
| `source_job_id`、`source_batch_id` | 可选关联 AI job／现有应用批次 |
| `operation_key / operation_hash` | 作者一次业务动作的幂等键与规范化请求哈希；批量角色应用共享，拒绝同 key 异请求 |
| `name / role_type / description / details_json / lifecycle_state / position` | 该 version 的完整角色快照 |
| `change_set_json`、`content_hash`、`created_at` | 变更字段、规范化哈希和时间 |

数据库至少包含 `(character_id, character_version)` 和 `(novel_id, operation_key, character_id)` 唯一约束，父 revision 使用 `(id, character_id, novel_id)` 组合范围外键。迁移同时给 `CreativeGenerationJob` 与 `CharacterProfileApplyBatch` 补充现有主键 + novel 的组合唯一 guard，使 `source_job_id/source_batch_id + novel_id` 可以使用范围外键；对 nullable novel 的非小说 job 不改变现有行为。

在 `novels` 增加 `character_catalog_version`，初始为 0；每次角色新建、手工编辑、AI 候选应用、逐角色恢复、改名或归档的**一次业务事务只递增一次**。接口同时返回由全部正式角色 `{id, version, lifecycle_state, position}` 计算的 `character_catalog_digest`。单角色 CAS 使用 `NovelCharacter.version`，整组候选依赖使用 catalog version + digest；它们均不复用 `Novel.version` 或 outline version。

### 4.4 保留但降级为兼容投影的字段

`novels.outline_target_chapters/background/main_plot/highlight` 继续保留，避免现有卡片、Agent 上下文和旧版本代码立即失效。每次正式 outline revision 事务同步更新这四个字段；新代码读取权威 head，兼容代码读取投影，二者不允许分开写。

`novel.description` 明确属于作品简介／元数据，不属于 outline 投影。首次正式化、局部保存、AI 采用、历史恢复和旧数据回填都不得用 `highlight_text` 覆盖它。现有 `complete_outline_draft()` 的覆盖行为在新服务接线时删除，并增加“修改大纲不改变 description”的回归测试。

当运行稳定且所有读取者都迁移后，是否删除四个兼容投影另立计划；本文不做破坏性删列。

`Storyline` 不再被视为 `main_plot` 的同义投影。新正式化路径、后续大纲保存和恢复都不自动创建或覆盖故事线；需要把高层情节转成故事线时，只能由作者以后触发独立候选与 Diff。旧数据已有故事线原样保留。

### 4.5 `OutlineDraft` 的最终边界

- 不删除表、不清理旧草稿、不把其数据自动并入正式数据。
- `GET/PATCH /outline-draft` 仅在没有 outline head 时可用。
- 现有 `/outline-draft/complete` 在 initializing 模式下只作为路径 A 的兼容适配器，内部调用新的正式化服务；不再执行按姓名合并的旧逻辑。
- head 已存在时，任何草稿 PATCH／complete 返回稳定领域冲突 `outline_already_committed`，并附当前正式 revision／version；不能继续按姓名兼容合并。
- 普通大纲页在 `maintaining` 模式不调用草稿 API。
- 旧草稿保留为恢复证据；P0 不建设历史草稿编辑器，也不提供一键覆盖正式数据。

### 4.6 正式角色、别名与规范化身份

1. 所有新正式角色只由服务端生成稳定 UUID，并在同事务写入首个 character revision。
2. 首次采用时，草稿临时角色只能“新建”“显式映射到已有正式角色”或“放弃”；禁止按姓名静默覆盖。
3. 正式化后，大纲角色模块直接读取 `/characters`，不保存 `characters_json`。
4. 新建和改名先锁定 `Novel`，再按稳定顺序锁定目标角色；使用一个中立的 `backend/character_identity.py` 执行 NFKC、casefold 与空白归一化。字段长度仍由各调用方按现有契约校验（正式姓名 240、朗读 alias 80），`backend/narration/aliases.py` 只复用并重新导出规范化核心，不能复制第二套算法或放宽朗读 alias 限制。
5. 新姓名不得与其他角色的 active 正式姓名或 active alias 规范化后相同；旧姓名写入 `character_aliases(source=rename_history)` 前也必须通过同一检查。若新姓名正好是该角色自己的历史 alias，事务先把该 alias 转为主姓名占位，再把当前旧名写为 alias，不能留下同一角色主姓名／alias 重复。现有数据库无法跨两表表达该唯一性，因此服务层小说级锁、负向并发测试和只读旧数据冲突报告都是 P0 门禁；任何旧姓名无法满足 active alias 长度／字符契约时，改名预览返回 blocker，禁止截断或丢弃历史名。
6. 改名创建 character revision、递增角色 version 与 catalog version，不创建 outline revision，不改写正文或历史事实文本。
7. 归档只改变 lifecycle 并创建 character revision，保留正式行、稳定 ID、关系和历史引用。活动章纲约束、关系、故事事实文本、正文命中和朗读绑定显示为 warning；需要继续 AI 生成的章纲必须先解决 archived／unresolved 引用。朗读允许对已归档角色执行 `UNSET` 清理，但禁止新增或改绑声音。

### 4.7 `ChapterBrief.role_constraints` 的 ID 化与兼容 DTO

数据库 JSONB 的新写入使用 versioned JSON：

```json
{
  "schema_version": 2,
  "required_character_ids": ["uuid"],
  "allowed_character_ids": ["uuid"],
  "context_only_character_ids": [],
  "forbidden_character_ids": []
}
```

同一发布周期采用加法兼容，不把旧前端瞬间打断：

- 请求优先接收 `role_constraints_v2`；兼容期仍接受旧 `role_constraints` 姓名数组，但两者不能同时提交。
- 旧姓名仅在当前正式姓名或 active alias 能唯一匹配时转换为 ID；歧义或找不到时整个保存返回 `character_reference_unresolved`，不部分写入。
- 响应同时返回 `role_constraints_v2`、按 ID 投影的 `role_constraint_characters`，以及 `unresolved_role_references[] = {bucket, raw_name, reason, candidate_character_ids}`。
- 旧 `role_constraints` 姓名投影保留一个兼容发布周期，只用于展示，不再作为新前端写回依据；移除时间另立兼容裁决。
- 新写入在按 UUID 排序锁定全部目标 `NovelCharacter` 后校验小说归属与 active 状态；这样归档与新增引用可以串行，不依赖影响预览猜测并发结果。
- AI 上下文只包含已解析且 active 的 ID；存在 unresolved 或 archived 的 `required` 角色时阻止生成并要求作者处理，其他 bucket 的异常引用不静默带入 Prompt。
- P0 回填不批量重写现有 ChapterBrief；读取和 AI 生成时做唯一解析，作者下次显式保存时才落成 v2。若以后需要批量转换，必须另做可预览、会递增 brief version 的授权迁移；其余情况只输出审计报告，不自动创建角色。
- 文档 27 若增加 `StoryFact.character_id`，继续由该计划单一所有者施工；本文只在改名影响报告中扫描旧 `subject` 文本，不重复添加字段。

## 5. 统一事务与并发规则

### 5.1 统一锁顺序与事务边界

所有相关领域写入使用固定锁顺序：`Novel -> OutlineDraft（仅初始化） -> NovelOutlineHead（仅大纲写） -> NovelCharacter（按 UUID 排序） -> 下游引用行（按主键排序）`。同一服务不得反向取锁；模型调用、Diff 计算和浏览器等待都在事务外完成。

`Novel` 行承担同一本书的身份命名空间互斥；`NovelOutlineHead.version` 只承担正式规划 CAS；`NovelCharacter.version` 承担单角色 CAS；`Novel.character_catalog_version` 承担一次角色集合业务动作的 CAS。任何代码不得用一个版本号替代另一领域的并发控制。

### 5.2 首次正式化与旧直建事务

路径 A 同一事务必须：

1. 按统一顺序锁定 `Novel`、`OutlineDraft`、可能存在的 head 和相关正式角色。
2. 先按 `novel_id + idempotency_key` 查找已有 revision：request hash 相同则返回原结果，不同则冲突；没有命中后再校验无 head、草稿 version/content digest、采用 section 清单、字段上限，以及每个草稿角色稳定 key 的 `create/map/drop` 决定。目标章数始终取草稿有效值，不要求三个文本 section 或角色非空。
3. 对 `create` 角色执行规范化身份冲突校验，写入 `NovelCharacter` 与首个 character revision；对 `map` 只建立本次采用引用，不覆盖正式角色；对 `drop` 不产生正式写入。
4. 若角色目录实际变化，`character_catalog_version` 只递增一次。
5. 创建 `initial_commit` outline revision、head 与角色 revision 引用清单；同步四个 `Novel` outline 投影，但不修改 `description` 或 `Storyline`。
6. 草稿标记为 completed；提交后进入 maintaining。任一步失败全部回滚。

路径 B 使用同样的 head／幂等／范围校验和最新 draft digest，但不采用草稿目标章数、不 materialize 任何草稿角色；它以 Novel 当前兼容默认目标创建 `manual_empty_baseline`，并在 `change_set_json` 记录被隔离的非空 section 和角色数量，草稿内容本身不复制到日志或 change set。

旧 `POST /novels` 在单一事务中创建 `Novel -> manual_empty_baseline revision -> head -> 默认卷 -> 默认章及空 working copy/revision`。它不创建 `OutlineDraft` 或角色，继续保留现有“每次成功 POST 都创建一本新书”的非幂等兼容语义，不做基于标题的隐式去重；前端新流程不得使用它。该入口标记为 deprecated，但删除或新增全局建书幂等契约另立计划。实现不能继续调用现有多个会自行 `commit()` 的服务拼装事务。

### 5.3 正式大纲手工编辑事务

`expected_outline_version` 匹配后，以当前 outline revision 为 parent 应用 section patch，读取当前 `{character_id, character_version}` 引用清单，创建新 outline revision，移动 head，递增 outline version，并同步四个 `Novel` 投影。空 patch或规范化 `content_hash` 完全相同不创建 revision、不移动 head，返回当前结果。角色目录在请求期间变化不影响纯手工文本保存，但生成的 revision 必须记录事务内实际读取到的角色引用摘要。

无变化请求不写额外 receipt，也不占用 idempotency key；它依靠 expected version 保证网络重放仍返回同一当前结果。客户端在基线变化后必须生成新 key，不能把旧 no-op key 当作跨版本操作标识。角色无变化请求采用同一规则。

### 5.4 AI 候选生成与采用事务

- 正式大纲 job 继续复用 `CreativeGenerationJob`，不新增第二套任务表；`input_snapshot` 保存 `base_outline_revision_id`、`base_outline_version`、目标 section、作者输入哈希、实际使用的依赖集合及其 digest。
- 依赖按 Prompt 实际输入记录，并标记 `character_dependency_scope=none|all_catalog|selected_ids`：未使用角色时不做角色 stale 校验；使用全角色目录时保存并比较 catalog version/digest；只使用作者明确选择角色时保存并比较精确角色 revision 引用，catalog version 仅作审计而不因其他角色变化误判 stale。未使用的关系、事实或故事线不得加入依赖。
- `ready` 只表示候选可审阅，不表示正式采用；模型返回期间不持有数据库事务。
- 作者采用时锁定 Novel 与 head，重新校验 job 归属、源 revision、head version、候选结构、幂等键和所有声明依赖。只有被声明依赖发生变化时返回 `outline_candidate_stale`，并附字段级当前基线，不自动重跑模型。
- 采用成功创建 `ai_adopt` outline revision，只改变目标 section，不改变 description、角色、故事线、正文或故事事实。
- 当前 `_validate_creative_generation_scope()` 把所有 `outline_*` kind 强制绑定 `OutlineDraft`；施工时必须区分初始化草稿 job 与正式大纲 proposal job，并验证 scope 归属，不能用放宽为任意 UUID 的方式绕过。

### 5.5 正式角色变更事务

所有角色新增、手工编辑、角色卡候选应用、批次恢复、改名和归档都调用统一角色写入器：

1. 要求 head 已存在，锁定 Novel，并校验 `expected_character_catalog_version`；再按 UUID 排序锁定目标角色并校验各自 expected version。
2. 新建／改名额外执行正式姓名 + active alias 的统一规范化冲突检查。
3. 先按 `novel_id + operation_key` 查找已有角色 revisions：operation hash 与目标角色集合相同则返回原结果，不同则冲突。没有命中时，对每个实际变化的角色先形成 before/after，再更新当前 `NovelCharacter`、递增角色 version，并写入对应 character revision；无变化不增 version。
4. 一次多角色 AI 应用或恢复共享 operation key，全部成功后 catalog version 只递增一次；任一角色冲突整批回滚。
5. 现有 `CharacterProfileApplyBatch` 继续保存工作流级 before/after 和恢复证据，character revision 负责统一的逐角色历史；二者通过 `source_batch_id` 关联，不互相替代。
6. 角色事务不移动 outline head，不修改 `OutlineDraft`、大纲文本、正文、关系或故事事实。

### 5.6 影响预览、引用锁与并发含义

改名／归档预览返回基于 `character_version + character_catalog_version + 引用 ID/版本摘要` 的 `impact_hash`。正式请求必须回传该哈希，服务端在取锁后重算；不信任前端计数。

所有新稳定 ID 引用写入至少锁定目标角色并重新验证小说归属和 active 状态：章纲角色约束与关系服务在本文内补齐；朗读声音绑定当前已锁 Novel 和角色，只补“归档角色仅允许 UNSET”的窄兼容。文档 27 的 StoryFact ID 写入继续由计划 27 负责同一规则。这样，与归档并发的新增 ID 引用要么先提交并被影响重算看到，要么在归档后因 inactive 被拒绝。

正文、旧 `StoryFact.subject` 和旧姓名章纲属于不可锁定的历史文本命中，只能作为 warning；改名后的 active alias 保证它们仍可解析到原稳定 ID。计划不得把文本扫描结果表述为数据库级完整引用计数。

### 5.7 大纲与角色恢复事务

- 大纲恢复：作者选择历史 outline revision 和明确的文本 section；系统展示“历史值 → 当前值”Diff，确认后以当前 revision 为 parent 创建新的 `restore` outline revision，并记录 `restored_from_revision_id`。角色引用清单使用恢复事务发生时的当前角色版本，不恢复历史角色。
- 角色恢复：作者选择某一个 character revision，展示完整字段 Diff 和当前影响预览；确认后创建新的 character version/revision，记录 `restored_from_revision_id`，递增 catalog version。不得从某一版大纲批量覆盖整组角色。
- 两类恢复都要求各自 CAS 与幂等键；历史 revision 永不改写，失败零当前态写入。

## 6. API 与 DTO 冻结建议

### 6.1 正式大纲

| 方法与路径 | 行为 |
| --- | --- |
| `GET /novels/{novel_id}/outline` | 返回 `initializing/maintaining`、head、正式 section、正式角色摘要和可用动作 |
| `POST /novels/{novel_id}/outline/commit-initialization` | 路径 A；采用所选的当前草稿 section／角色决定，允许部分为空 |
| `POST /novels/{novel_id}/outline/discard-initialization` | 路径 B；显式不采用草稿并建立空正式基线 |
| `PATCH /novels/{novel_id}/outline` | 手工 patch 正式 section，要求 `expected_outline_version + idempotency_key` |
| `POST /novels/{novel_id}/outline/sections/{section}/proposals` | 建立局部 `fresh/refine` AI 候选 |
| `POST /novels/{novel_id}/outline/proposals/{job_id}/adopt` | 采用单 section 候选并创建 revision |
| `GET /novels/{novel_id}/outline/history` | 分页读取 revision 摘要 |
| `GET /novels/{novel_id}/outline/revisions/{revision_id}` | 读取历史快照与当前 Diff |
| `POST /novels/{novel_id}/outline/revisions/{revision_id}/restore` | 选择 section 后创建恢复 revision |

正式读取 DTO 至少包含：

```text
lifecycle
outline_version
current_revision_id
target_chapter_count
background_text
plot_text
highlight_text
character_catalog_version
character_catalog_digest
characters[]           # 当前正式角色摘要，来自 NovelCharacter
legacy_draft_present   # 只提示隔离事实，不混入当前值
updated_at
```

### 6.2 初始化草稿

保留现有草稿 API 路径用于兼容，但响应增加 `lifecycle`。正式化请求冻结为：

```text
expected_draft_version
idempotency_key
adopt_sections[]          # background/plot/highlight；路径 A 使用，目标章数始终采用草稿有效值
character_resolutions[]   # {draft_character_key, decision=create|map|drop, character_id?}
confirm_discard_digest    # 路径 B 在草稿非空时必填
```

草稿读取 DTO 增加 `draft_content_digest`，每个角色增加稳定 `draft_character_key`。新角色创建时把 UUID key 持久化在 `characters_json`；没有 key 的 legacy 项按“草稿 ID + 原始位置 + 规范化内容哈希”投影确定性 key，并在下一次作者保存草稿时持久化。路径 A 的 `adopt_sections` 可为空；每一个有内容的草稿角色都必须有 resolution，不能把未列出的角色默认为新建。路径 B 的 `confirm_discard_digest` 必须等于最新 `draft_content_digest`。完成响应返回 `outline_revision_id`、`outline_version`、`character_catalog_version` 和正式角色列表。

现有 `POST /outline-draft/complete` 仅适配到路径 A；它不得调用旧的按姓名合并实现。旧 `POST /novels` 的兼容响应增加 `lifecycle` 和 `outline_revision_id`，但不改变已有小说／卷／章主体字段。

### 6.3 角色影响预览

新增只读端点：

```text
GET /novels/{novel_id}/characters/{character_id}/change-impact
    ?next_name=...
    &operation=rename|archive
```

响应包含 `character_version`、`character_catalog_version`、`impact_hash`、关系 ID、章纲 ID 引用、旧姓名文本命中、正文命中章节、故事事实命中、朗读绑定／片段、`blockers[]` 和 `warnings[]`。正式改名／归档请求必须携带 `expected_version + expected_character_catalog_version + impact_hash + idempotency_key`；服务端在事务内重算，不信任前端计数。

正式角色读取 DTO 增加 `current_revision_id`；历史端点按角色分页：

```text
GET  /novels/{novel_id}/characters/{character_id}/history
GET  /novels/{novel_id}/characters/{character_id}/revisions/{revision_id}
POST /novels/{novel_id}/characters/{character_id}/revisions/{revision_id}/restore
```

角色新增、编辑、候选应用和恢复的请求都携带 `expected_character_catalog_version` 与 `idempotency_key`；多角色候选应用继续使用现有批次端点，但响应增加新的 catalog version 和逐角色 revision ID。

### 6.4 章纲角色约束兼容契约

`GET /documents/{document_id}/chapter-brief` 在兼容期返回：

```text
role_constraints             # v1 姓名投影，只读兼容
role_constraints_v2          # v2 稳定 ID，新的权威写入形状
role_constraint_characters   # 四个 bucket 的 {id,name,lifecycle_state,version}
unresolved_role_references   # 旧姓名无法唯一解析的精确原因
```

`PUT` 接受 `role_constraints_v2` 或旧 `role_constraints` 二选一。新前端只提交 v2；旧请求在服务端唯一解析成功后直接落成 v2。若任何引用 unresolved、跨小说或已归档，整个请求失败且 chapter brief version 不变。`frontend/src/chapter-workflow.ts` 的文本输入可继续显示姓名，但内部选择值和请求均使用 ID，不能再用 `splitNames()` 的结果充当外键。

### 6.5 统一错误 envelope 与错误码

`backend/app.py` 与 `backend/creative_api.py` 复用同一个领域错误适配器。所有本文新增错误使用：

```json
{
  "detail": {
    "type": "outline_version_conflict",
    "message": "可展示但不可用于程序分支的中文说明",
    "current": {},
    "conflicts": [],
    "retryable": false
  }
}
```

`type` 是稳定程序判别字段，保留项目现有 envelope 习惯；`message` 只用于展示。`current/conflicts` 按错误类型可选，但同一类型形状固定。前端 `api.ts` 提供统一的类型提取函数，页面不得各自解析 `detail`。

HTTP 409 至少包括：

- `outline_already_committed`
- `outline_not_committed`
- `outline_version_conflict`
- `outline_candidate_stale`
- `outline_character_resolution_required`
- `character_catalog_conflict`
- `character_change_impact_stale`
- `character_identity_conflict`

HTTP 422 至少包括：

- `character_reference_unresolved`
- `character_reference_archived`
- `outline_initialization_invalid`

既有错误类型继续兼容，本文不顺带重命名全部历史错误。不得通过匹配中文错误字符串决定生命周期、并发恢复或角色映射行为。

## 7. 页面方案

### 7.1 初始化模式

当前五步布局可以先保留，避免把权威修复与 UI 大改绑成一次高风险施工；只调整语义：

- 页头显示“尚未建立正式档案”。
- 角色步骤明确标记“角色草稿”；不能暗示已经进入角色档案。
- 默认主按钮改为“保存已有内容并开始写作”；背景、角色、情节或亮点只完成一部分时也可使用，确认页明确列出将采用和保持为空的模块。
- 次级动作改为“不采用这些草稿，直接开始写作”；草稿非空时二次确认并列出会被隔离的模块／角色数量，不能用模糊的“跳过”掩盖差异。
- 如果检测到已有正式角色，角色步骤展示“已有正式角色 + 草稿新增角色”，要求作者逐项映射／新建／放弃。

### 7.2 维护模式

- 大纲卡只读取正式 outline API；进入编辑后创建以当前正式 revision 为基线的 working copy。右侧助手继续由 `workbench-studio.ts` 注册当前页面实体与当前可编辑字段快照，不得从历史 `OutlineDraft` 或 `Novel` 兼容列另行拼装一份大纲。
- 页头分别显示“大纲 vN”和“角色目录 vM”；“查看大纲历史”与单角色“查看修改记录”分开，避免暗示两者共用版本。
- 章数、背景、情节、亮点仍可沿用现有五个锚点导航，但角色锚点展示正式角色卡，不再展示草稿数组。
- 背景、情节、亮点的手工编辑使用当前值和保存 Diff；AI 操作为“优化候选／另写一版”，结果进入同一 Diff 审阅，不出现“完成大纲”。
- 角色区域复用角色页的同一 DTO、表单和服务，主操作为“新增角色／管理角色”；移除“重新生成人物”，单角色详情提供历史与逐角色恢复。
- 检测到旧草稿时显示非阻断提示：“历史草稿已隔离，不会影响当前正式内容。”P0 不允许从该提示直接覆盖。

### 7.3 风险文案

- 背景／情节保存：说明“只更新后续规划，不会重写章节正文或故事事实”。
- 改名：先展示影响预览，并明确“正文中的旧姓名不会被自动替换，将作为历史别名保留”。
- 归档：列出仍引用该角色的章节、关系、事实文本与朗读绑定；稳定 ID 引用保留且标记为 warning，存在身份冲突或请求基线过期等 blocker 时禁用确认。
- 历史恢复：按钮文案为“以此版本创建恢复 revision”，不使用“回滚覆盖”。

### 7.4 可访问性与布局非回归

- 保留当前中间工作区、左侧书籍栏、右侧原生助手栏的已验收宽度与布局；本计划不重新调整三栏尺寸。
- 锚点使用真实 `button`、`aria-current` 和禁用语义；Diff、影响预览、错误和成功不能只靠颜色表达。
- 键盘可完成 section 切换、保存、取消、候选审阅、影响确认和返回角色列表。
- 窄屏中维护页采用单滚动容器；不能产生页面滚动与文本框滚动互相锁死。

## 8. 现有数据迁移与修复

### 8.1 迁移性质

采用**加法迁移**：新增 `novel_outline_revisions`、`novel_outline_heads`、`novel_character_revisions`，并给 `novels` 增加 `character_catalog_version`；不删除旧列，不修改旧 revision，不清理 `OutlineDraft`。迁移前重新核对 Alembic head；本文编写时为 `20260828_0024`，如果计划 27 或其他迁移先落地，本文迁移必须串行接到新的真实 head，禁止分叉后强行改写历史。

Alembic upgrade 只建 schema、约束和默认值，不在升级事务里猜测并回填用户小说。逐书 baseline 建立由独立、可 dry-run、需要 `OAU-DATA-G` 授权的回填命令执行；没有成功回填的旧应用继续运行旧代码，不切换到依赖 head 的新版本。

### 8.2 长期数据库操作前置门禁 `OAU-DATA-G`

1. 用只读脚本输出每本小说：正式大纲字段、description 独立哈希、正式角色及其 version、规范化姓名／alias 冲突、草稿状态／角色数、章纲姓名引用、章节／卷／关系／事实／朗读引用统计和建议分类。
2. 对精确项目数据库执行可恢复备份，记录文件路径、大小、SHA-256、PostgreSQL 版本、迁移 head 和恢复命令；不打印密钥。
3. 在隔离恢复库上完整演练 `restore -> upgrade -> backfill -> app rollback compatibility`。
4. 向用户展示逐书 dry-run，尤其单列《潮声替我说晚安》的“正式 5 人保留、草稿 6 人隔离”结果。
5. 用户明确批准该次精确数据回填后，才可操作长期数据库。

### 8.3 一次性保守分类

只用于旧数据回填，不成为未来运行时规则：

| 旧数据情况 | 回填结果 |
| --- | --- |
| 有正式大纲文本、正式角色、卷章、故事线、关系或事实等任一正式创作资产 | 创建 `legacy_backfill` revision 与 head，进入 maintaining |
| `OutlineDraft.state=completed`，即使正式字段异常为空 | 创建回填 revision，同时报告数据异常，不重新完成草稿 |
| 只有未完成草稿，且没有任何正式创作资产 | 不创建 head，继续 initializing |
| 正式数据与草稿不一致 | 正式数据进入 revision；草稿原样保留并标记为 legacy presence，不合并 |

“旧书已正式化”的分类必须偏向保护正式资产；即使只有空章节也不重新开放批量初始化覆盖。未来新书不使用这些启发式判断，而只看 head 是否存在。

### 8.4 回填内容

- 先为每个现有正式角色创建一个 `legacy_backfill` character revision；`character_version` 使用当前真实 version，不伪造缺失的早期版本，active 与 archived 角色都保留。
- 小说存在正式角色时将 `character_catalog_version` 从默认 0 建立为 1；没有角色保持 0。计算 catalog digest，outline revision 只引用当时 active 角色的真实 `{id, version}`。
- 从 `Novel.outline_target_chapters/background/main_plot/highlight` 创建 `legacy_backfill` outline revision 与 head；`established_at` 记录实际回填时间，`establishment_source=legacy_backfill`，change set 标明原始正式化时间未知。
- 不改变角色 ID、version、position、关系、正文、故事事实或朗读绑定。
- 不把草稿角色 materialize 为正式角色。
- 不改变 `Novel.description`；回填前后分别比较四个 outline 投影和 description 的字段级哈希，任何一项意外变化都阻断该书并报告。
- 规范化正式姓名／alias 已冲突的旧书仍可建立只读 baseline，但标记 `identity_conflict` 数据问题；解决前禁止新增／改名，不自动选择任何角色。

### 8.5 正式切换顺序

长期环境只允许串行执行：停止 PawApp 写入入口（不删除数据卷）→ 精确备份 → Alembic schema upgrade → 授权后的逐书 backfill → 完整一致性检查 → 安装新 PawApp → 健康检查与浏览器哨兵 → 恢复写入。不得先部署依赖 head 的代码、再让旧小说处于半初始化状态。

若 schema upgrade 或 backfill 失败，保持旧 PawApp 版本；新增空表／列可以留存，旧代码继续读取 `Novel` 投影。只有全部逐书结果和 hashes 通过，才允许切换应用版本。

### 8.6 恢复方式

- 功能回退优先回滚 PawApp 代码；因为旧 `Novel` 投影持续更新，旧版本仍可读取当前大纲。
- 新表、catalog version 和 revision 保留，不因应用回退删除。
- 只有在已验证备份、确认新应用没有产生任何新 outline/character revision，或作者明确接受丢弃新历史时，才允许执行 Alembic downgrade；长期数据库不得为“测试方便”直接降级。
- 如果某本书回填失败，事务只回滚该书或整个批次，取决于最终冻结的批次策略；绝不能留下 head 指向不存在 revision 的半状态。

## 10. 验收矩阵

### 10.1 领域与数据库

1. 新建书向导完成后没有 head，进入 initializing；保存草稿不会创建正式 revision、角色、卷或章。
2. 路径 A 可以只采用背景、只采用角色或全部为空；未选择的 section 保持空，角色必须逐项 `create/map/drop`，失败零正式写入。
3. 路径 B 在非空草稿上要求匹配 discard digest，创建空 baseline 且保留草稿原文；不调用模型、不 materialize 草稿角色。
4. 旧 `POST /novels` 在一个事务内创建 novel、空 baseline/head、默认卷章和初始 working copy；任一步失败后数据库零残留。
5. 无 head 时角色、卷、章和故事线公开写服务返回统一 `outline_not_committed`；head 存在后草稿 PATCH／complete 返回 `outline_already_committed`。
6. 正式 section 保存创建不可变 outline revision；重复幂等键返回同一结果，空 patch 不创建 revision。
7. 大纲保存、AI 采用和恢复始终不改变 `Novel.description`、`Storyline`、角色、正文或故事事实。
8. 旧 outline version 的并发保存返回结构化冲突；角色编辑只改变 character/catalog version，不移动 outline head。
9. AI job ready 不改变正式数据；采用只更新目标 section。仅实际声明的 outline／角色依赖变化才使候选 stale，无关字段变化不能误杀候选。
10. 正式角色新增／编辑／归档创建独立 character revision；一次多角色应用只递增一次 catalog version，并保持每个角色 version 精确递增。
11. 角色卡 AI 应用和批次恢复同时维护 `CharacterProfileApplyBatch` 与逐角色 revision；任一角色冲突整批零写入。
12. 新正式姓名与其他 active 正式姓名／alias 的 NFKC+casefold 规范化冲突被拒绝；两个并发改名不能同时成功。
13. 改名必须通过影响哈希，创建旧名 alias；正文、历史事实文本和旧章纲文本不被改写，仍能唯一解析到原 ID。
14. 与归档并发的章纲／关系 ID 写入要么先提交并进入影响重算，要么在归档后因 inactive 被拒绝；正式行、历史关系和稳定 ID 始终保留。
15. 大纲恢复只恢复选定 section；角色恢复只恢复单角色并创建新 character version，两者都不倒拨旧 revision。
16. head、outline parent／恢复目标、character parent／恢复目标和 source job／batch 的跨小说 ID 被数据库与服务双重拒绝；JSON 中的历史角色引用由服务端范围校验、规范化 digest 和读取完整性检查拒绝，计划不虚构 JSONB 外键能力。

### 10.2 旧数据与恢复

17. Alembic upgrade 只改变 schema；未执行授权回填前，旧小说内容和草稿零变化。
18. 隔离旧库回填只以正式字段／正式角色建立 baseline，不 materialize 草稿角色，也不修改现有角色 version。
19. 《潮声替我说晚安》的 dry-run 明确得到“正式 5 人保留并各建 baseline revision、草稿 6 人隔离”，不会变成 9 人。
20. 旧姓名章纲引用仅唯一匹配时在响应／AI 输入中投影为 v2；歧义／缺失进入待处理，读取过程不改数据库，作者显式保存时整条 chapter brief 才原子写成 v2。
21. 回填前后四个 outline 投影与 description 字段级哈希相同；规范化身份冲突只报告和阻止后续身份写入，不自动改名。
22. 相同 manifest 重复回填幂等；单书失败不留下无 revision 的 head 或半数角色 baseline。
23. 代码回退后旧版本仍可从 `Novel` 投影读取最新正式大纲，新增表不要求删除。
24. 备份恢复演练能回到迁移前 Alembic head、表数量和逐书内容哈希；切换失败时旧 PawApp 可恢复服务。

### 10.3 前端与可访问性

25. 初始化页明确区分“保存已有内容”与“不采用草稿”；部分完成时能看见采用／留空／隔离摘要。
26. 正式书点击任何锚点都不请求 `/outline-draft`，也不出现“完成大纲”或批量重新生成人物。
27. 大纲页和角色页显示同一正式角色 ID／数量；大纲 version 与角色目录 version 分开展示、分开冲突恢复。
28. 章纲表单显示姓名但提交稳定 ID；unresolved／archived required 角色阻止 AI 生成并可定位处理。
29. 维护模式局部保存、AI 候选、两类历史 Diff、结构化错误和刷新恢复均有明确状态，不匹配中文错误字符串。
30. 改名／归档影响预览及单角色恢复可用键盘完成，警告、冲突和成功不只依赖颜色。
31. 目标桌面与窄屏没有横向溢出、双滚动死锁或底部操作遮挡。
32. 左侧书籍栏、右侧 QwenPaw 原生助手、原生聊天模型／Agent／Skill 和朗读页面行为无回归。

## 12. 最终逻辑自检

本方案满足以下闭环：

- 新书可以采用任意已完成的部分内容，也可以明确不采用草稿；不会再把“部分采用”和“丢弃草稿”混成一个跳过动作。
- 两条建书入口都有确定的生命周期：新向导创建 initializing 空书，旧直建在同事务建立空 baseline 后才创建默认卷章。
- 建立正式基线后，大纲与角色页读取同一正式角色，不再出现“看正式、改草稿”。
- 大纲和角色拥有独立历史与 CAS；角色变化不会伪造 outline revision，无关候选也不会因错误版本耦合过期。
- 开书后仍可编辑背景、情节、亮点、章节目标和角色，但不同风险使用不同确认强度。
- AI 仍能辅助局部内容，却不能批量替换正式角色或偷偷改写正文。
- 作品 description、Storyline、正文和事实不再被大纲保存隐式覆盖。
- 新章纲使用稳定角色 ID；正式姓名和 alias 共用同一规范化身份规则，改名与归档具备可解释并发边界。
