## 0. 第三轮审核结论

### 0.1 最终裁决

人物的身份、性格、年龄和成长都需要保留变化轨迹；章节完成后的“同步进展”也应能发现这些变化。但是，模型只能生成候选，作者看到结果并确认后，变化才能进入故事账本。人物卡的作者设定基线不得被模型静默覆盖。

角色列表中的分析能力继续保留，但只承担低频“基线性格补全/复核”；它不再承担章节人物演进，也不因单纯新增正文持续提醒重新分析。日常变化只有章节“同步进展”这一条入口。

本计划只保留一套生产路径：

```text
正式章节 revision
  -> 固定输入快照与短引用键
  -> 跟随 AI 小说作家 Agent 的当前有效模型
  -> 严格结构与逐字证据校验
  -> 结果后审阅、选择
  -> 单事务写入现有 StoryFact 故事账本
  -> 按叙事位置 + 故事时间投影人物状态
  -> 为角色页和下一章生成提供只读上下文
```

不建设模型档案，不建设第二套模型选择器，不按 MiniMax、Qwen、DeepSeek 分叉 Skill、提示或数据结构。

### 0.2 上一版为什么过重

第一版曾规划 `story_timelines`、`story_time_anchors`、`character_state_events` 三张新表，以及完整时间线 CRUD、手工事件编辑器、四个独立轨迹区和大规模物化投影。复核当前代码与数据后，这个方案被否决，原因是：

- `StoryFact` 已经承担确认后的故事事实；再建人物事件表会形成第二份事实真相。
- `DerivedSourceBinding` 已经记录事实与章节 revision 的来源、失效和恢复；再建来源链会重复。
- `IntelligenceProposalItem` 已经是模型候选，`IntelligenceCommitBatch` 已经是作者确认批次；无需另起候选与批次系统。
- 当前每本小说最多只有 281 条故事事实，尚无证据支持先建设物化当前态、独立时间线服务或专用事件库。
- 当前真实失败发生在 evidence 协议，不是缺少三张表；先扩表不会解决 DeepSeek 的失败。

因此，第二轮方案收敛为：**零新增业务表、一个线性迁移、四个必要字段、两个纯服务、一个轻量轨迹区。**

### 0.3 减重后仍不能删除的部分

以下内容看似增加施工量，但属于可靠性底座，不能继续删减：

- 短引用键与服务端逐字证据校验；否则当前真实失败无法根治。
- `story_ledger_version` 的真实 CAS 和递增；否则并发确认会产生不可解释的账本状态。
- 叙事位置与故事时间双坐标；否则闪回、时间跳跃和年龄推导必然混乱。
- 结果后确认；否则作者是在看不到模型结果时预先授权未知写入。
- 现有角色性格候选审阅、默认零选择、CAS、幂等、应用恢复和模型审计；删除后既降低安全性，也会在未来重复建设。
- 追加式事实、撤销批次和来源 revision 有效性；否则后期无法审计或恢复。
- 结构化失败诊断与同模型单次修复；否则思考模型的一次格式偏差仍会表现为长期转圈或模糊失败。

## 1. 审核依据与当前实现事实

### 1.1 本轮只读核查范围

本轮核查了当前源代码、迁移、相关自动化测试、开发文档以及本机当前项目数据库中的聚合统计。没有调用模型，没有修改正式小说数据，没有执行迁移，也没有操作 QwenPaw 核心代码。

### 1.2 已核实代码事实

- `NovelCharacter.details` 保存作者确认的人物基线，`version` 可用于角色资料 CAS。
- `StoryFact` 已包含 `novel_id`、类型、主谓宾、`details`、`source_revision_id` 和状态。
- `IntelligenceProposal` / `IntelligenceProposalItem` 已保存同步候选和逐项审阅状态。
- `IntelligenceCommitBatch` 已有幂等键、确认项、逆操作、预期故事账本版本及撤销时间字段。
- `DerivedSourceBinding` 已能在章节 revision 被替换或恢复时把派生事实切换为 `source_superseded` 或 `source_restored`。
- `Novel.story_ledger_version` 已存在，但当前确认服务没有锁定并递增它；`expected_story_ledger_version` 因而没有形成真正的 CAS。
- 当前 `commit_intelligence_items` 会在一个事务中创建 `StoryFact` 和 `DerivedSourceBinding`，但只保存通用 `details`，没有人物外键、维度、时间或轨迹语义。
- `IntelligenceProposal` 当前没有输入快照；任务启动后又从实时数据库拼提示，`input_hash` 也只覆盖章节哈希和模型信息，无法证明模型实际看到了哪些角色、事实和故事线。
- 当前情报结果规范化器会扫描输出文本中的多个嵌套 JSON 对象；这可能误收思考文本、示例或中间对象。
- 当前无效 `item_type` 可能被跳过，部分路径还会被降级为普通 `fact`；严格契约下不应静默降级。
- 当前 `source_text` 只要求非空，没有验证它是否逐字来自输入快照。
- 当前提示按创建时间取最早 200 条事实；单本已有 281 条事实时会遗漏较新的 81 条，模型可能重复建议或基于过时上下文判断。
- 当前前端在模型结果出现之前进行确认，随后自动提交所有返回项；这不是真正的结果后审阅。
- 当前事实提交先 `commit`，人物关系同步随后再执行第二个事务；后一步失败会留下“事实已确认、关系网未同步”的半完成业务动作。
- 当前章节正文生成已有 300 秒安全截止，但角色分析和同步进展的模型调用没有同等级的有界等待，进程异常还可能留下长期 `running`。
- 当前故事线聚合含有针对样例小说的关键词，并可能在读取路径中写数据库；这不具备通用性。

### 1.3 已核实数据规模

只读聚合统计显示：

- 当前共有 6 本小说、510 条 `StoryFact`；单本最多 281 条，平均约 102 条。
- 现有事实类型包括普通事实 172、故事线事件 129、人物状态 77、伏笔和关系等其他类型。
- 77 条既有 `character_state` 都没有结构化 `character_id`、`dimension` 或 `story_time`。
- 510 条事实都保留了模型建议、提案和来源摘要；495 条含确认批次 ID。
- 510 条来源绑定中，224 条当前有效、274 条因来源旧稿失效、12 条随 revision 恢复。
- 28 个确认批次均已提交，当前没有执行过批次撤销。

这些数据证明现有来源有效性机制正在发挥作用，也证明没有必要马上另建轨迹表；但既有 77 条非结构化人物状态不能安全自动回填成新语义。

### 1.4 真实失败证据

《刑侦1988:档案里消失的人》的首次真实 DeepSeek 角色分析任务：

- requested/actual 均为 `deepseek/deepseek-v4-flash`；
- 任务失败原因为模型返回的 evidence 来源 ID 不属于输入快照；
- 0 个应用批次，正式角色资料未修改。

这说明安全失败边界有效，但“让模型回显内部 UUID”这一协议不稳定。修复方向应是模型只使用短键，服务端解析内部 ID，而不是降低校验标准。

## 2. 目标、非目标与不变量

### 2.1 目标

- 身份、性格、年龄和成长均可形成按章节审计的追加式轨迹。
- 章节同步能识别人物变化，但任何正式写入都必须发生在作者看过结果之后。
- 闪回、时间跳跃和顺叙都能区分“第几章得知”与“故事中何时发生”。
- 下一章生成只使用叙事位置之前、来源仍有效且与目标故事时间相容的确认事实。
- 思考模型与非思考模型共用同一 final 输出契约，不依赖关闭思考模式。
- 失败明确显示阶段、错误码、证据键和是否已修复重试，不再无限转圈。
- 所有确认、撤销、来源失效和恢复都可审计、可幂等重放。
- 保留角色性格候选审阅、选择应用、CAS、幂等、失败诊断和应用批次恢复，同时把入口收敛为状态化的低频基线分析。
- 基线性格分析与人物轨迹在触发条件、权威写入和页面文案上互不重叠。

### 2.2 非目标

- 不建立模型档案、模型白名单、模型能力表或逐模型 Skill。
- 不修改 QwenPaw 上游核心，不读取其私有数据库或未公开模块。
- 不建设平行世界、多宇宙或任意分支时间线编辑器；v1 只支持 `main` 时间线。
- 不建设完整日历、农历、时区、历史历法或自动生日提醒系统。
- 不做医学、心理疾病或 MBTI 自动诊断。
- 不让模型直接覆盖 `NovelCharacter.details` 中的作者基线。
- 不自动把既有 77 条非结构化人物事实猜测性迁移为新轨迹。
- 不新建物化“人物当前态”表、缓存、向量库、任务队列或第二套 Runtime。
- 不在本计划中重做完整故事线产品；只修复同步链路中的 ID 和读取副作用。
- 不把“重新分析基线性格”做成每章必点任务，不因新章节、打开角色页或保存正文自动调用模型。
- 不把现有性格补全扩张为自动重写身份、年龄、成长方向或整张角色卡。

### 2.3 必须保持的不变量

1. 正式正文、角色基线和故事账本都是作者确认后的权威数据。
2. 模型输出始终先是候选；生成失败、修复失败、刷新或取消不得改变权威数据。
3. 内部 UUID、小说范围、章节范围、角色范围和故事线范围只由服务端解析和校验。
4. 一个确认批次的全部权威写入和账本版本递增必须在同一事务中完成。
5. 任何会改变“当前有效事实集合”的提交、撤销、来源失效或来源恢复都必须使账本版本在同一事务中递增一次；`story_ledger_version` 是单调并发令牌，不是事实条数。
6. 来源 revision 失效时，派生事实不得继续进入生成上下文；恢复来源时使用现有恢复机制。
7. 轨迹事实只追加或改变有效状态，不覆写历史事件文本。
8. 系统日期不得被用来推导小说人物年龄。
9. 基线分析只能候选式 patch `NovelCharacter.details.personality`，不得创建人物轨迹；章节同步只能确认 `StoryFact` 及其派生关系，不得 patch 人物基线。

## 3. 唯一领域模型

### 3.1 四层真相

| 层 | 现有权威实体 | 含义 | 模型是否可直接写入 |
| --- | --- | --- | --- |
| 人物基线 | `NovelCharacter.details` | 作者确认的初始设定，如初始身份、性格、年龄、成长方向 | 否 |
| 模型候选 | `IntelligenceProposalItem` | 从一次固定章节快照抽取的建议 | 可以生成，但不是权威 |
| 确认轨迹 | `StoryFact` + `DerivedSourceBinding` | 作者确认、带来源 revision 的状态事件 | 只能经确认服务写入 |
| 当前投影 | 纯服务返回值 | 基线与有效事件在指定双坐标下的计算结果 | 不持久化 |

此分层避免把“人物现在是什么样”复制到多张表，也避免每写一章就重写角色卡。

### 3.2 双坐标

每个确认事件同时具有：

- **叙事坐标**：查询时由服务端从 `DerivedSourceBinding.source_chapter_id -> Document.position`、来源 revision 和提案项顺序推导，表示读者/作者在第几章获得该信息；不把可变章节 position 冗余写死在事件 JSON 中。
- **故事时间坐标**：来自正文证据或作者的章节时间提示，表示事件在小说世界中何时发生。

投影必须先按叙事坐标排除目标章节及未来章节的信息，再按目标故事时间排除尚未发生的状态变化。不能只按数据库 `created_at` 排序，也不能把闪回章节误当成时间继续向前。

### 3.3 基线与轨迹的关系

- `details.identity`、`details.personality`、`details.age`、`details.growth_direction` 是作者基线。
- 同步进展不自动改写这些字段，而是追加结构化人物状态事实。
- 角色页显示“作者设定”与“截至当前的正文投影”，两者冲突时明确标红，不静默择一。
- 作者手工修改基线仍使用现有角色版本 CAS；该操作不会删除历史事件。

### 3.4 基线分析与章节同步的唯一分工

| 能力 | 角色列表“基线性格分析” | 章节“同步进展” |
| --- | --- | --- |
| 解决的问题 | 人物最初被作者设定成什么性格 | 人物在某章发生了什么变化 |
| 主要输入 | 正式大纲、人物小传、角色基线及作者主动调用时允许的正式章节证据 | 当前正式章节 revision、此前有效事实和轨迹 |
| 候选输出 | `personality` 补全或替换建议 | 身份、性格、年龄、成长、关系、故事线等事件建议 |
| 权威写入 | 作者选择后安全 patch `NovelCharacter.details.personality` | 作者选择后追加 `StoryFact`、来源绑定及确定性关系投影 |
| 正常频率 | 缺失时一次；以后仅作者主动或依据失效时复核 | 每个需要同步的正式章节一次 |
| 是否自动调用 | 永不自动 | 永不自动，作者点击“同步进展” |

两条入口共享 AI 小说作家 Agent、短 evidence key、严格 final、requested/actual 审计和有界等待，但不共享权威写入服务，不能互相调用或静默替代。

基线分析入口使用以下状态机，不再统一显示含义模糊的“重新分析”：

| 页面状态 | 主区域行为 | 可用动作 |
| --- | --- | --- |
| 任务 `running / repairing` | 显示实际阶段、次数和最长等待时间 | 禁用重复启动，显示“分析中 / 修复中” |
| 有未决定候选 | 显示候选数量和来源状态 | 主按钮“继续审阅” |
| 没有活跃角色，或缺少任何可核验的作者设定/正式证据 | 显示缺失条件，不把“资料不足”伪装成模型故障 | 禁用生成，保留“刷新状态” |
| 至少一个活跃角色缺少 `personality`，且最近一次补全失败 | 显示待补全数量、错误阶段、模型和安全失败摘要 | 主按钮“重试补全” |
| 至少一个活跃角色缺少 `personality`，且无可审阅候选 | 显示待补全数量 | 主按钮“补全角色性格” |
| 全部角色已有性格，但作者主动重新分析失败 | 保留现有性格，只显示非阻塞失败历史 | 次级菜单“重新分析基线性格” |
| 作者修改了大纲/人物设定，或已应用候选引用的 revision 失效 | 显示非阻塞“基线依据待复核” | 次级动作“复核基线性格” |
| 全部角色已有性格，依据仍有效 | 不占用角色列表主操作位 | 次级菜单“重新分析基线性格” |

状态优先级固定为：运行/修复中 > 有效待审候选 > 不具备分析条件 > 缺失且失败 > 缺失 > 基线依据待复核 > 已完成。可选重新分析失败不能把已经完整的角色卡重新降级成主待办。

“继续审阅”只表示同一个 ready job 尚无应用批次时可以重新打开候选。作者关闭弹窗不会丢失候选；但一旦点击“应用所选”，本次审阅即原子结束，未选候选明确视为**本次放弃**，不能在部分角色 version 已变化后继续从同一旧快照追加应用。确认按钮文案必须说明“应用所选并结束本次审阅；未选项不修改，如需重新评估请新建分析”。该语义可由 job 输出与 apply batch 已选 ID 确定审计，不新增逐候选决定表；仍缺少性格的角色随后回到“补全角色性格”，而不是伪装成仍有可应用的旧候选。

仅新增正式章节或新确认人物轨迹不进入上述待办状态，也不显示基线红点；变化由对应章节“同步进展”处理。新章节在作者主动“重新分析基线性格”时可以作为补充证据，但它本身不会让既有基线失效。已引用来源失效也只触发复核提示，不自动撤销作者已经确认的性格。

生成请求沿用现有角色补全 endpoint，但增加并校验 `analysis_intent = fill_missing / manual_reanalysis / evidence_review`，写入已有 `CreativeGenerationJob.input_snapshot`，并纳入 `input_hash` 和幂等键计算，不新增数据库字段。不同 intent 即使读取了相同内容也不能错误复用同一个 attempt；`force_new` 只控制同一语义下是否创建新 attempt，不能替代语义 intent。服务端拒绝与当前状态不相容的 intent，并始终执行同一候选审阅和应用安全链。

不得继续用“当前完整输入 hash 是否变化”这一个布尔值驱动入口。服务端分别计算并返回正交字段：

- `generation_input_changed`：任何可用输入变化，供幂等和作者主动重新分析时创建新 attempt；新增章节可以令它为真。
- `reason_codes`：可枚举数组，只含 `missing_personality / author_source_changed / cited_source_superseded`，决定是否存在基线待办；失败状态不混入来源原因。
- `additional_chapter_evidence_available`：仅作次级信息，不产生红点、主按钮或自动调用。
- `latest_attempt_state` 与 `latest_analysis_intent`：单独描述最近一次调用的 `never / running / repairing / ready / failed / applied / superseded` 及其语义；完整角色的可选重新分析失败只进入失败历史，不制造基线待办。

这样既保留完整调用证据，又不会把人物日常演进错误地包装成“角色基线过期”。

调用模型前，`input_snapshot` 保存 `authority_source_catalog` 和各目标角色 `base_version`：目录按短来源键记录正式大纲、人物小传、角色字段、正式 revision 等实际输入的类型、字段路径/版本和规范 hash，角色版本专用于候选应用 CAS。模型返回后，服务端先完成短键解析、quote 逐字校验和来源范围校验，再为**每个角色候选**以目标角色自身基线来源及该候选实际引用的目录项构造 `baseline_authority_fingerprint`，保存到已有 `CreativeGenerationJob.output_json.validation.candidate_authority[character_id]`；不能在调用前假装已经知道模型最终会引用哪些来源，也不能用一个全小说总指纹让无关角色变化造成全体误报，不新增数据库字段。

应用候选时逐个核对所选角色的 `baseline_authority_fingerprint`、角色 CAS、job 的 `input_hash` 自洽和 cited source 有效性；任一所选角色冲突仍整批零写入，但不能要求“当前完整 generation input hash”仍与生成时完全相等。写入成功后，以已有 `CharacterProfileApplyBatch.after_snapshot / result_versions` 作为应用后的角色锚点，并关联原 job 中该角色自己的来源与证据验证元数据；状态计算必须以这个**应用后锚点**比较当前资料，不能继续拿生成前 `base_version` 比较而导致刚应用就立即过期，也不能因未被该候选依赖的其他角色变化提示复核。

锚点必须**逐角色**解析：对每个角色选择最近一个包含该角色的 applied/restored batch，不能让全局最新批次遮蔽更早分批应用的其他角色，也不能复用当前“只取最近 30 条 job/batch”的 UI 历史窗口作为权威查询。施工采用按当前活跃角色做 PostgreSQL lateral/等价有界查询，利用现有 novel+created 索引为每个角色取最新一条，并按 `generation_job_id` 精确读取关联 job；最近 30 条只用于失败/调用历史展示。当前规模不新增 JSONB GIN 索引，只有第 15 节性能触发器满足后再评估。

恢复批次以恢复后的 `after_snapshot / result_versions` 成为该角色新锚点，不把已撤销候选的引用继续冒充当前性格依据。若关联 job 已因历史清理而为空，则已确认值仍按 author 基线保留。若作者随后通过角色编辑明确改了 `personality`，当前值与批次 after snapshot 不同且角色 CAS 已前进，则该角色的来源转为 `author`，旧 AI 引用不再决定其 freshness，也不提示“证据失效”；若作者只改姓名、描述、身份或其他实际分析来源而保留 AI 性格，则仍返回 `author_source_changed` 供作者选择复核。

因此，候选生成后单纯新增无关章节不会阻止应用；作者修改角色基线来源、目标角色版本变化或替换候选实际引用的正文会在应用前安全冲突并整批零写入。应用后新增章节仍不产生基线提醒；角色资料再次被编辑、作者来源变化或当前已采纳性格的有效引用失效时才提示复核。

## 4. 最小数据变更

### 4.1 一个线性迁移

施工时从**实际 Alembic 当前 head** 新建一个 revision；不得改写已经存在或可能执行过的迁移。迁移只增加：

1. `story_facts.character_id UUID NULL`
   - 复合外键 `(character_id, novel_id)` 指向 `novel_characters(id, novel_id)`；
   - 新建部分索引 `(novel_id, character_id, fact_type, status, created_at)`，只覆盖 `character_id IS NOT NULL`；
   - 增加兼容旧数据的检查：`character-state-v2` 必须有 `character_id`，legacy `character_state` 仍可为空；
   - 不设置“删除单个角色时级联删除事实”；现有角色归档流程必须保留历史，整本小说删除路径另做级联兼容测试；
   - 既有事实保持 `NULL`，不猜测性回填。
2. `chapter_briefs.story_time_context JSONB NOT NULL DEFAULT '{}'`
   - 保存作者对目标章节故事时间的可选提示；
   - 不形成第二张时间线表。
3. `intelligence_proposals.input_snapshot JSONB NOT NULL DEFAULT '{}'`
   - 保存有界、规范化的角色/轨迹/时间/故事线短键目录、版本和哈希；
   - 正文仍以不可变 `DocumentRevision` 为权威，只保存证据片段偏移与哈希，不重复整章；
   - 建提示、解析结果和提交复核都读取同一快照，禁止任务中途回读实时对象替换模型输入。
4. `intelligence_proposals.result_json JSONB NOT NULL DEFAULT '{}'`
   - 保存 `changes / no_changes` 结果摘要、解析/证据诊断、修复次数和被拒 final 哈希；
   - 不保存 chain-of-thought，不复制完整章节或完整无效模型输出。

角色补全任务使用已有 `CreativeGenerationJob.input_snapshot` 和 `output_json` 保存同结构的快照与最小诊断，不新增重复字段。

新同步提案的 `input_snapshot.schema_version` 固定为 `intelligence-sync-input-v2`，并与 `generation_contract_version` 一起进入 `input_hash`。升级前已经存在且 `input_snapshot = {}` 的未决定提案继续只读可见，但提交服务必须返回稳定的 `LEGACY_PROPOSAL_REQUIRES_RESYNC`，UI 提示“旧候选缺少固定快照，请重新同步”；不得把旧候选猜测性补成 v2，也不得在 GET/list 路径中偷偷改写其状态。已提交的旧事实保持原样。

角色基线任务同样区分协议代际：升级前未应用且缺少新验证元数据的 v1 ready/running job 在读取时派生为 `latest_attempt_state=superseded`，不修改原记录；应用接口稳定返回 `LEGACY_CHARACTER_CANDIDATE_REQUIRES_REANALYSIS`。过去已经由作者应用或恢复的角色性格保持不变，并作为 `origin=author` 的已确认基线处理，不因旧 job 没有新证据指纹制造复核红点；作者以后主动重新分析时才建立新协议证据。

### 4.2 为什么 `character_id` 不能只放 JSONB

人物外键是范围和删除行为的安全边界。若只让模型在 JSONB 中写姓名或 UUID，会出现同名、改名、跨小说 ID 和无约束孤儿数据。复合外键可以在数据库层证明该角色属于同一本小说。

### 4.3 为什么不回填旧事实

既有 `character_state` 缺少可靠人物 ID、维度、前后值和故事时间。按姓名或主谓宾自动推断会把模糊描述伪装成精确历史。旧事实继续可见并标记为“待结构化”，但不参与 v2 当前态计算。

## 5. `character-state-v2` 契约

### 5.1 外层字段

新人物事件仍使用 `StoryFact`：

- `fact_type = "character_state"`
- `character_id`：服务端由候选短键解析后的正式角色 ID
- `subject / predicate / object_text`：用于人类可读摘要
- `source_revision_id`：服务端固定为本次正式章节 revision
- `status`：沿用 `active / source_superseded / source_restored / reverted`

### 5.2 `details` 结构

```json
{
  "schema_version": "character-state-v2",
  "event_fingerprint": "server-generated-sha256",
  "dimension": "identity",
  "event_kind": "revealed",
  "track_id": "server-generated-uuid",
  "supersedes_story_fact_id": null,
  "before_value": {"identity_text": "档案管理员"},
  "after_value": {"identity_text": "专案组秘密调查员"},
  "permanence": "ongoing",
  "story_time": {
    "timeline_key": "main",
    "time_text": "1988年11月",
    "precision": "year_month",
    "normalized_start": "1988-11-01",
    "normalized_end": "1988-11-30",
    "elapsed_years_from_baseline": null,
    "elapsed_months_from_baseline": null,
    "elapsed_days_from_baseline": null
  },
  "visibility": {
    "identity_layer": "true",
    "knowledge_scope": "named_characters",
    "known_by_character_ids": []
  },
  "evidence_key": "E0007",
  "evidence_quote": "……"
}
```

现有审计键 `proposal_id`、`proposal_item_id`、`commit_batch_id`、`model_suggestion`、`reasoning_summary` 和来源摘要继续保留；`reasoning_summary` 只是简短可解释理由，不保存隐藏思考。v2 规范字段是服务端校验后的权威事件，原始模型建议只用于审计，不能在读取时反过来覆盖规范字段。

模型不得直接提供 `event_fingerprint`、`track_id`、内部 UUID、`supersedes_story_fact_id` 或权威叙事坐标。模型只返回本次快照中的短 `character_key`、`track_key`、`evidence_key`；服务端解析内部值，叙事坐标始终由来源绑定查询得到。

`normalized_start / normalized_end` 和相对基线增量也由服务端根据逐字证据和作者时间提示计算。模型只能返回原文 `time_text`、精度建议和引用，不得把自行补全的日期写成权威标准时间。

### 5.3 维度与事件种类

| 维度 | 允许的 `event_kind` | 语义 |
| --- | --- | --- |
| `identity` | `started`、`ended`、`concealed`、`revealed`、`corrected` | 新身份、结束身份、隐瞒、揭示或纠错 |
| `personality` | `expression_started`、`expression_ended`、`long_term_shift`、`corrected` | 临时行为模式和长期性格变化分开 |
| `age` | `birth_anchor`、`age_anchor`、`birthday`、`corrected` | 只记录证据锚点，不逐章制造年龄事件 |
| `growth` | `milestone`、`regression`、`turning_point`、`direction_completed`、`corrected` | 成长里程碑、倒退、转折和弧线完成 |

`before_value` 和 `after_value` 是按维度校验的对象，不接受自由形态任意 JSON：

- 身份至少包含 `identity_text`；
- 性格至少包含可观察的 `pattern_text`，长期变化还需 `trait_text`；
- 年龄只能使用非负 `age_years`、明确 `birth_date_text` 或服务端可验证的时间增量；
- 成长至少包含 `milestone_text` 或 `direction_text`。

单章中的一次情绪或行为默认只能成为临时 `expression_started`。首版只有当前正式正文明确表达“形成持续改变、此后长期如此”等持久语义时，才允许候选 `long_term_shift`；它始终属于高风险项，必须单独选择。多个章节出现同向行为时，投影可以并列展示重复模式并把摘要提供给下一章上下文，但不能在没有独立跨来源依赖协议的情况下自动合并成核心性格。不能把沉默、愤怒、哭泣等一次场景直接覆盖成长期变化。

### 5.4 稳定轨迹键

结束、纠错和揭示必须指向既有轨迹，不能靠文本近似匹配：

- 快照把当前轨迹映射为 `T001`、`T002` 等短键。
- 模型返回既有 `track_key` 或明确的 `new`。
- 服务端为新轨迹生成 `track_id`；既有键解析为同一本小说、同一角色、同一维度的 `track_id`。
- `ended`、`corrected`、`expression_ended` 若不能唯一解析目标，整项失败，不猜测。

### 5.5 身份可见性

身份至少区分真实身份、公开身份、掩护身份和职能角色，并记录知识范围：

- `identity_layer`：`true / public / cover / role`
- `knowledge_scope`：`author_only / reader_revealed / in_world_public / named_characters`
- `known_by_character_ids`：仅当范围为指定人物时使用，全部由服务端校验小说范围。

下一章上下文必须保留这些标签，不把“作者知道的真相”误写成“全体人物已经知道”。

## 6. 故事时间契约

### 6.1 时间锚点复用 `StoryFact`

章节中出现可确认的时间推进时，写入 `fact_type = "story_time"` 的普通故事事实，其 `details.schema_version = "story-time-v1"`，包含：

- `timeline_key = "main"`
- 服务端生成的 `event_fingerprint`
- `time_text`
- `precision = exact_date / year_month / year / relative / ordered_only / unknown`
- 可选 `normalized_start / normalized_end`
- 可选相对基线的年、月、日增量
- `evidence_key / evidence_quote`
- 来源绑定；叙事坐标查询时从绑定与当前章节顺序推导

不新建时间锚点表。若未来出现真实的平行时间线需求，再由独立 ADR 评估，而不是提前建设。

### 6.2 章节时间提示

`ChapterBrief.story_time_context` 只保存作者可编辑的目标提示：

```json
{
  "timeline_key": "main",
  "time_text": "1988年11月下旬",
  "precision": "year_month",
  "relation": "continues | advances | flashback | unknown",
  "reference_revision_id": null
}
```

- 默认 `timeline_key` 固定为 `main`；API 拒绝任意模型生成的其他 key。
- 没有提示时，系统可以继承最近一个已确认时间锚点，但必须标记 `unanchored`，不能伪装成精确日期。
- 闪回或明显跳时章节必须由作者给出提示，或由同步结果产生可确认的时间事实；系统不从章节序号猜年月。
- `reference_revision_id` 只能由 UI 从服务端候选中选择；保存和读取时都校验它属于同一本小说。引用失效时降级为 `unanchored` 并提示作者，不把 JSONB 中的旧 UUID 当成有效外键。

### 6.3 年龄推导规则

- 精确出生日期 + 精确目标日期：可计算整数年龄。
- 年/月级或只有年龄锚点：返回区间或“约 N 岁”，不得制造日级精度。
- 明确“过去三年”且基线可用：可按证据增量推导，并保留计算依据。
- 锚点冲突：返回 `conflicted` 和全部依据，不静默使用最后一条。
- 锚点不足：继续显示作者基线年龄并标记“未与故事时间锚定”。
- 绝不使用服务器当前日期或文档创建日期计算人物年龄。

## 7. 证据协议与思考模型兼容

### 7.1 快照短键目录

每次模型调用建立不可变目录：

- 角色：`C001…`
- 证据片段：`E0001…`
- 既有轨迹：`T001…`
- 既有故事线：`S001…`

短键只在本次 `input_hash` 内有效。目录的内部 UUID 映射只在服务端保存，模型看不到也不能覆盖范围校验。

人物状态使用 `character_key / track_key`，关系使用 `source_character_key / target_character_key`，故事线事件使用 `storyline_key`，下一章必现角色使用 `character_key`。新契约不再让模型用姓名承担实体标识；姓名只作为可读标签。

新关系候选规范化为 `details.schema_version = "relationship-v2"`，由服务端写入已校验的 source/target character ID、方向、分类、标签和证据；模型建议中的短键只作审计。旧关系事实继续保留，但不被猜测性转换为 v2。

证据片段按正式章节文本和允许的人物设定来源切分：章节证据保存 revision、规范化 `content_text` 的 Unicode code point 起止偏移和片段哈希；人物基线证据保存角色版本、允许的字段路径和字段值哈希。偏移只在 Python 服务端使用，不与前端 UTF-16 选区协议混用。模型只看到短键、来源标签和必要文本，不看到内部映射。

模型返回 `evidence_key + evidence_quote`，服务端只做换行规范化后验证 quote 是对应片段的逐字子串；不做模糊匹配、语义猜测或跨片段拼接。角色分析与章节同步使用同一个引用服务，避免再次出现两套 evidence 规则。

### 7.2 唯一 final JSON

新契约只接受一次完整 final JSON。为兼容不同模型的稳定输出习惯，只允许两种确定性外壳：纯 JSON 对象，或**恰好一个**无前后解释的 `json` Markdown 围栏。两者解析后都必须满足 `additionalProperties: false` 的版本化 schema：

```json
{
  "contract_version": "story-ledger-extractor-v4",
  "result_state": "no_changes",
  "summary": "本章没有新增可确认的故事账本变化",
  "no_changes_reason": "内容只延续了已确认场景，没有新的事实或人物状态",
  "items": []
}
```

- `result_state = changes` 时必须有 1–200 个合法 item。
- `result_state = no_changes` 时 `items` 必须为空，并提供非空 `no_changes_reason`；“正文不为空就必须至少一条”的旧规则删除。
- `no_changes` 是成功终态，页面明确显示“未发现需同步的变化”，不能伪装成失败。

- 不扫描思考文本中的嵌套对象；
- 不接受示例对象、围栏外文字或多个互相竞争的 JSON；
- 不跳过未知 `item_type`；
- 不把未知类型降级为 `fact`；
- 任一已返回项违反 schema、范围或证据规则时，本次输出进入修复或安全失败。

思考内容由现有运行时与 final 内容分离；本计划不关闭 Qwen 或 DeepSeek 的思考模式，也不要求模型特例。

### 7.3 一次受控修复

只对以下可修复错误进行同 Agent、同 provider/model 的一次修复调用：

- final JSON 语法错误；
- schema 字段、枚举或类型错误；
- evidence key 不存在或 quote 不逐字匹配；
- 短角色键、轨迹键或故事线键无效。

修复提示只包含契约、错误路径、短键目录和原始 final 的必要片段，不包含 chain-of-thought。以下情况禁止模型重试：

- requested/actual 模型不一致；
- Agent 或小说范围不一致；
- 章节 revision 已过期；
- 作者取消；
- 服务端、数据库、权限或网络基础设施错误。

两次均失败后进入终态 `failed`，前端停止转圈并展示可操作原因。

### 7.4 有界等待与失联恢复

- 角色分析和同步进展复用 `backend/generation_runtime.py` 的安全有界等待语义：首次模型调用上限与现有章节生成一致为 300 秒；只有首次已返回但契约无效时，修复调用再给 120 秒，总流程最多 420 秒，不维护逐模型超时档案。
- 超时任务被取消并丢弃晚到结果；晚到结果不得进入完成服务或任何权威写入。
- 首次调用超时、网络或模型不一致不进入修复；修复只处理第 7.3 节的结构/引用错误。
- 一次修复是第二次显式调用，因此界面显示“正在修复（第 2/2 次）”和累计耗时，不能继续显示无期限的单一转圈。
- 用户关闭弹窗或中断浏览器请求只停止本地等待；供应商调用可能完成为可审阅候选，但永远不会自动应用。
- `running / repairing` 超过 420 秒总流程上限再加 30 秒宽限的记录在读取时显示为 `stale`，下一次显式重新生成时由写接口锁定并标记旧记录 `failed(stale_timeout)`；GET 不借机写数据库。
- 本计划不为此引入后台任务队列或通用取消系统。

### 7.5 结果与失败诊断最小集

`IntelligenceProposal.result_json.validation` 或 `CreativeGenerationJob.output_json.validation` 保存：

- `error_code`
- `stage = invoke / parse / schema / evidence / scope / stale / commit`
- `json_path`
- `offending_short_key`
- 输入快照、短键目录和被拒 final 的哈希
- `call_count`、requested/actual provider/model
- 面向作者的安全摘要

首版冻结错误码：`FINAL_ENVELOPE_INVALID`、`SCHEMA_INVALID`、`EVIDENCE_KEY_UNKNOWN`、`EVIDENCE_QUOTE_MISMATCH`、`ENTITY_KEY_UNKNOWN`、`SCOPE_MISMATCH`、`MODEL_MISMATCH`、`REVISION_STALE`、`LEDGER_CONFLICT`、`SNAPSHOT_TOO_LARGE`、`DUPLICATE_EVENT`、`GENERATION_TIMEOUT`、`REPAIR_TIMEOUT`、`STALE_RUNNING`、`RELATION_PROJECTION_CONFLICT`、`LEGACY_PROPOSAL_REQUIRES_RESYNC`、`LEGACY_CHARACTER_CANDIDATE_REQUIRES_REANALYSIS`。未知内部异常统一映射为 `INTERNAL_ERROR`，不自动调用模型重试；日志和响应都不得泄露密钥或隐藏提示。

不得保存隐藏思考、密钥、完整系统提示或不必要的整章副本。

### 7.6 Skill 与服务端规则的边界

- 继续使用通用 `story-foundation` 和 `character-craft` 创作 Skill 约束“什么值得判断为事实、性格或成长变化”。
- 不为 Qwen、DeepSeek、MiniMax 建立不同 Skill，也不因一次模型失败建立模型档案。
- JSON schema、短键范围、逐字证据、外键、CAS、幂等和事务必须由服务端强制；Skill 只能提高模型遵循率，不能替代安全校验。
- 本计划不修改 Skill 文件；现有通用创作语义继续复用，新的机器契约留在运行时提示和服务端。真实验收若证明通用 Skill 本身存在独立缺口，只记录证据并另行裁决，不由本计划并行包顺带扩写。

## 8. “同步进展”产品流程

### 8.1 正常流程

1. 作者点击“同步进展”。
2. 服务端确认工作稿已保存为正式 revision；未保存时先提示保存，不从瞬时编辑器文本直接写账本。
3. 服务端固定 revision、角色版本、既有轨迹、故事线、时间锚点、账本版本和短键目录，把规范化 `input_snapshot` 与哈希一起持久化。
4. `input_hash` 覆盖完整快照、revision content hash、提示/Skill 契约版本和 requested 模型；另存最终 `prompt_hash`。提示只能从该快照及对应不可变 revision 构建，不能再读取实时对象替换内容。
5. 快照先排除叙事位置晚于当前章节的事实，再按相关性和最近叙事位置确定性选取；同一 revision 已确认事实单列用于幂等去重。记录总数、纳入数、遗漏数和 fingerprint，删除“按最早创建时间硬取 200 条”的旧逻辑。必需的角色、轨迹或故事线目录无法完整纳入时明确失败，不静默截断。
6. 按 AI 小说作家 Agent 当前 effective 模型生成提案；requested/actual 证据沿用计划 19。
7. 严格解析，必要时执行一次同模型修复；合法 `no_changes` 直接展示结果，不创建空批次。
8. 前端显示全部候选、前后值、维度、时间、证据和风险；此时尚未写账本。
9. 所有候选默认未选择。作者可逐项选择，或主动点击“选择全部低风险项”。身份真相/揭示、出生或年龄纠错、长期性格变化、成长方向完成永不进入低风险批选。
10. 作者点击“应用所选”，服务端执行 CAS、范围复核和单事务提交。
11. 页面返回实际创建的事实、相关派生实体、账本新版本和可撤销批次。

取消、关闭页面、刷新、模型失败或未选择任何项都不修改故事账本。

### 8.2 提交事务

确认服务必须：

- 锁定 `Novel`、`IntelligenceProposal`、对应正式 revision 和所选 proposal items；
- 核对工作稿当前基线仍与提案 revision 一致；
- 核对客户端 `expected_story_ledger_version`；
- 重新执行 schema、角色范围、轨迹范围、故事线范围和 evidence 校验；
- 为新 v2 事件生成确定性 `event_fingerprint`，拒绝当前有效账本中的完全重复事件；不让模型提示词独自承担去重；
- fingerprint 使用服务端规范化后的角色、维度、事件种类、轨迹、前后值、故事时间和可见性，不包含模型名称、摘要措辞或来源 revision；
- 禁止客户端通过 `item_overrides` 改写 v2 的角色、维度、事件、轨迹、故事时间、可见性或证据。旧通用项的文字 override 也必须使用白名单、长度限制并保留原始建议；不能注入内部 ID 或任意 details；
- 创建所选 `StoryFact` 与 `DerivedSourceBinding`；
- 在同一事务内调用**不自行 commit** 的关系投影 helper；它从当前有效 `relationship-v2` 事实确定性重算受影响人物对，手工 `manual_override` 永远优先；删除 API 层“事实先提交、关系后同步”的双事务路径和按姓名/关键词猜关系的 v2 路径；
- `storyline_event` 只关联既有故事线并由事实只读聚合，不在 GET 中改写故事线；
- 把创建事实 ID、受影响人物对、关系前后 revision ID 写入 `IntelligenceCommitBatch.inverse_operations`；
- 整批成功后把 `Novel.story_ledger_version` 只递增一次；
- 任一项失败时整批回滚，不允许部分隐藏写入。

重复提交同一 `commit_key` 返回原结果，不再次递增版本。

### 8.3 撤销与重新应用

- 撤销按确认批次执行，不物理删除事实。
- 撤销请求必须携带客户端看到的 `expected_story_ledger_version`；服务端锁定 Novel 和批次，版本不一致时要求刷新影响预览后再确认。
- 事务把该批次创建且仍有效的事实标记为 `reverted`，来源绑定标记为 `detached`，批次标记为 `reverted`，账本版本递增一次。
- 来源 revision 的 preview/reconcile 必须显式跳过 `detached` 绑定和 `reverted` 事实，不能因恢复旧正文把作者已撤销内容重新激活。
- 来源失效或恢复实际改变有效事实集合时，所在正文事务把 `story_ledger_version` 递增一次；没有事实状态变化时不递增。
- 撤销事实后，在同一事务按剩余当前有效 `relationship-v2` 事实重算受影响人物对：没有剩余依据的自动关系追加归档 revision，有其他有效依据的关系投影到剩余依据；手工 override 不被改写。
- 若事实已因来源 revision 失效，仍可撤销，但不得错误恢复为有效。
- 重新应用必须创建新的确认批次和新的事实 ID，并记录来源批次；不复活或改写旧事实。
- 重新应用请求显式携带 `reapply_of_batch_id` 和新的幂等键，二者进入 `commit_key`；仅当原 proposal revision 仍是当前正式基线时允许。`IntelligenceProposalItem.committed_story_fact_id` 更新为最新有效事实，旧事实仍通过自身 details 和旧批次完整保留。
- 章节 revision 的失效/恢复继续使用现有事实 `source_superseded / source_restored` 机制，并对受影响的 v2 人物对重算关系投影；它与“作者撤销批次”是两个不同动作，不能互相覆盖。

## 9. 当前态投影

### 9.1 纯计算服务

新增纯服务读取：

- 作者人物基线；
- `status in (active, source_restored)` 的 `character-state-v2`；
- 目标文档之前的叙事坐标；
- 与目标故事时间可比较且不晚于目标时间的事件。

服务不写数据库、不调用模型、不修改角色 details，也不维护物化缓存。

投影使用按 `novel_id + character_id` 的直接 SQL 查询，不复用当前最多返回 500 条的通用 `list_story_facts` API；因此小说事实超过 500 条时不会静默截断人物历史。

### 9.2 返回结构

投影至少返回：

- `baseline`（含 `origin = author / ai_applied`、当前角色版本及可选应用批次/证据状态）
- `as_of_narrative_position`
- `target_story_time`
- `identity.current / history / knowledge`
- `personality.core / observed_patterns / temporary_patterns`
- `age.display / precision / basis`
- `growth.direction / milestones / regressions`
- `conflicts`
- `unanchored_fields`
- `legacy_unstructured_count`
- `projection_fingerprint`

同一轨迹出现无法排序或互斥的有效事件时，返回 `conflicted`；不得按创建时间静默覆盖。

### 9.3 闪回和知识边界

生成闪回章节时：

- 人物物理状态按闪回目标故事时间投影；
- 叙事知识仍只允许使用目标章节之前已经确认的来源；
- 晚于闪回时间的年龄、身份结束或性格转变不能成为该场景中的当前状态；
- 作者秘密可作为约束携带，但必须保留 `author_only` 标签，提示模型不得提前揭示。

## 10. 下一章生成上下文

### 10.1 输入构建

章节生成上下文增加一个受限的 `character_trajectory_context`：

- 只包含目标 `Document.position` 之前的有效确认事实；
- 完全排除目标文档自身的旧同步事实，防止重新生成时自我污染；
- 按 `story_time_context` 投影，不可比较项进入警告而不是伪造顺序；
- 保留证据摘要和可见性标签，但控制总字符预算；
- `input_hash` 必须包含 brief 版本、`story_time_context`、`story_ledger_version` 和投影 fingerprint。

账本或章节时间提示发生变化后，旧生成候选继续可查看，但不得被误认为基于当前上下文。

### 10.2 防泄漏与防提示注入

- 正文和人物字段都是数据，不得覆盖系统契约。
- 证据引用使用结构化边界和长度限制。
- `author_only` 身份真相明确标记“用于一致性约束，禁止在未获授权的章节中直接揭示”。
- 不把模型 reasoning、无效候选或未确认提案放入下一章上下文。

## 12. API 与界面收敛

### 12.1 API

尽量扩展现有接口，只新增必要能力：

- 现有角色补全生成接口升级为短证据键与严格 final 契约。
- 同一生成接口接收服务端复核的 `analysis_intent`；不新增“轨迹重新分析”接口，也不让前端用 `force_new` 绕过入口状态。
- 现有 `GET /novels/{novel_id}/character-profile-completion/status` 采用加法式兼容扩展，不新增第二个角色分析 API：新增 `entry_state = ineligible / running / repairing / candidates_pending / missing / review_required / complete`、聚合 `reason_codes[] = missing_personality / author_source_changed / cited_source_superseded`、`latest_attempt_state`、`latest_analysis_intent`、`generation_input_changed` 和 `additional_chapter_evidence_available`；同时返回有界 `character_baselines[] = {character_id, origin, state, reason_codes}`，让页面能准确定位缺失或待复核角色，但不返回内部证据目录。现有 `state / stale` 在兼容期继续返回，但由同一领域状态确定映射：`stale=true` 只映射真正的 `review_required`，不能再等同于任意 generation input 变化；新前端也不得用它单独推断入口。单纯新增章节只计入证据摘要，不返回待复核原因。

- 新增 `GET /api/ai-novel-world-2026/novels/{novel_id}/characters/{character_id}/trajectory`，可选 `as_of_document_id`、`as_of_revision_id` 和目标故事时间；返回投影、事件、冲突和旧事实计数。
- 新增 `POST /api/ai-novel-world-2026/intelligence-commit-batches/{batch_id}/revert`，请求包含 expected ledger version 和幂等键。
- 重新应用通过现有提案提交接口的显式 `reapply_of_batch_id` 动作完成，必须使用新幂等键和新批次；revision 已变化时要求重新同步，不新增通用手工事件 CRUD。
- 现有章节 brief 读写 DTO 增加 `story_time_context`。

提案 API 不返回完整 `input_snapshot` 内部映射，只返回契约版本、快照哈希、纳入/遗漏计数和可供审阅的短键标签；服务端内部 UUID 目录及 author-only 输入不进入普通列表响应。

所有路由继续位于 PawApp 命名空间，不占用 QwenPaw 全局路由。

### 12.2 角色页

角色列表保留现有性格分析的候选审阅、选择应用、角色版本 CAS、幂等、失败诊断、应用批次恢复和 requested/actual 模型证据；只调整入口层级、文案和 stale 判定，不复制一套实现。

- 有性格缺失时显示主按钮“补全角色性格”；失败时显示“重试补全”；有候选时显示“继续审阅”。
- 全部性格已填写时不再渲染当前占据列表顶部的完整分析状态条；在角色列表页头的“更多/角色性格”次级菜单保留“重新分析基线性格”和最近失败/模型证据入口，桌面与窄屏都可达。
- 作者设定变化或已引用 revision 失效时显示“基线依据待复核 / 复核基线性格”；新增章节本身不显示此提示。
- 角色列表加载、正文保存、章节采用和同步完成都不得自动调用基线分析。
- 基线分析面板明确说明“只补全/复核作者基线性格，不记录章节人物变化”；轨迹区明确提示章节变化来自“同步进展”。
- 候选弹窗可关闭后继续审阅；“应用所选”改为“应用所选并结束本次审阅”，二次说明未选项本次放弃且不修改角色，避免暗示可以在部分 version 已前进后继续应用旧快照。

不建设四套独立页面。现有角色卡或弹窗只增加：

- 可编辑的作者基线 `growth_direction`；
- 一个可折叠“人物轨迹”区域；
- 当前投影摘要；
- 按章节/故事时间排列的事件列表；
- 身份可见范围、性格临时/长期标签、年龄依据、成长里程碑；
- 冲突、未锚定和“旧事实待结构化”提示。

### 12.3 同步结果页

结果面板必须支持：

- 每项独立选择，默认不选；
- 同屏显示当前值、建议变化、维度、永久性、故事时间和原文证据；
- 高风险标识与低风险批选；
- 失败阶段和一次修复结果；
- 提交后的批次 ID、账本版本和撤销入口；
- 通用事实与轨迹列表把 `reverted` 显示为“作者已撤销”，把 detached 来源与“基于旧稿”区分；
- 键盘操作、焦点返回、窄屏滚动和错误恢复。

章节编辑页只在现有章节目标区域增加轻量故事时间字段，不新增时间线向导或管理页。

## 13. 并发、幂等与状态机

### 13.1 提案状态

```text
running -> ready | no_changes | repairing | superseded | failed
repairing -> ready | no_changes | superseded | failed
ready -> partially_accepted | accepted | rejected | superseded
partially_accepted -> accepted | superseded
```

`no_changes` 和 `failed` 都是终态。用户关闭页面不等于服务端已取消供应商调用；重新打开时读取最终候选、失败或基于时间判断的 `stale` 展示，任何状态都不会自动应用。

提案是否可提交还受契约门禁约束：只有 `input_snapshot.schema_version = intelligence-sync-input-v2` 且结果验证元数据完整的 v2 提案能进入新提交服务。旧版 `ready / partially_accepted` 提案可继续审计，但必须重新同步，不能因状态名相同而绕过固定快照、短键和证据校验。

### 13.2 批次状态

```text
committing -> committed -> reverted
```

异常事务回滚后不得留下半完成 `committing`；恢复脚本只检查和报告，不自动猜测性补写。

### 13.3 CAS 冲突

以下任一变化都要求作者刷新提案或重新确认：

- 正式章节 revision 改变；
- 工作稿不再基于提案 revision；
- `story_ledger_version` 改变；
- 目标角色被归档、改属范围或版本发生影响候选语义的变化；
- 既有轨迹或故事线短键已失效。

不得通过静默重取当前数据后继续提交来绕过冲突。

## 14. 验收计划

### 14.1 后端单元与契约测试

- final 只允许一个完整 JSON，嵌套示例和思考对象不会被误收。
- 纯对象和单一 JSON 围栏可接受；围栏外解释、两个对象或尾随文本拒绝。
- `changes` 必须有合法 items；`no_changes` 必须为空且有原因，并以成功终态展示。
- 未知 item 类型、非法枚举和额外内部 UUID 失败，不降级、不跳过。
- evidence key 必须属于快照，quote 必须逐字位于对应片段。
- 同 Agent、同模型最多修复一次；两次失败进入终态并保留最小诊断。
- 首次 300 秒、修复 120 秒、总计 420 秒截止、晚到结果丢弃、`stale` 识别和下一次写请求收口旧记录通过。
- 提示、验证和提交使用同一个持久化 `input_snapshot`；启动后修改实时角色/故事线不会偷换模型输入，并会在提交 CAS 中显式冲突。
- 旧版空快照提案只读可见但提交稳定返回 `LEGACY_PROPOSAL_REQUIRES_RESYNC`；GET/list 不修改其状态，重新同步后才产生 v2 候选。
- 未应用的旧角色候选派生为 superseded 且应用返回 `LEGACY_CHARACTER_CANDIDATE_REQUIRES_REANALYSIS`；已应用/恢复的旧性格原值与版本不变，按 author 基线显示且不制造证据失效红点。
- 同步较早章节时排除叙事未来事实，并单列同 revision 已确认事实用于去重。
- 角色、轨迹、故事线短键无法跨小说解析。
- v2 `item_overrides` 不能替换角色、轨迹、时间、可见性或 evidence；旧文字 override 只能通过白名单。
- 四个维度及所有允许事件种类通过；非法前后值拒绝。
- 结束/纠错事件必须唯一命中既有 `track_id`。
- 完全相同的当前有效 v2 `event_fingerprint` 被拒绝，来源已失效事件允许从新 revision 重新确认。
- 旧 `character_state` 计数可见但不参与 v2 投影。
- 角色基线状态把 `entry_state`、`reason_codes`、`latest_attempt_state`、`generation_input_changed` 和 `additional_chapter_evidence_available` 分开；单纯新增章节不产生待复核原因。
- `character_baselines` 的逐角色 origin/state/reason 汇总与全局 `entry_state/reason_codes` 一致，不泄露 source catalog；一个角色变化不会污染未依赖该来源的其他角色。
- 性格缺失、上次失败、作者设定变化和已引用 revision 失效分别落到稳定且不混淆的状态/原因字段；完整角色的可选重新分析失败仍为 `entry_state=complete`，来源失效不自动回滚已应用 `personality`。
- `analysis_intent` 与当前状态不相容时服务端拒绝；intent 纳入 `input_hash` 和幂等键，相同内容下的不同 intent 不会错误命中同一 attempt；`force_new` 不能伪造补全、复核或轨迹语义。
- 调用前的 `authority_source_catalog` 只记录已知输入来源，不包含尚未知晓的模型引用；模型输出通过证据校验后才为每个角色生成独立 `baseline_authority_fingerprint` 并写入 output 验证元数据。
- 候选生成后只新增无关章节或修改未被候选依赖的其他角色仍可审阅和应用；目标角色基线来源变化或被引用 revision 替换会使该角色候选权威指纹冲突，任一所选角色冲突则整批零写入。
- 候选应用后，状态以 apply batch 的 `after_snapshot / result_versions` 为锚点，不会因本次应用自身造成角色 version 递增而立即显示“待复核”；恢复后不继续使用已撤销候选的引用作为当前性格依据。
- 两个角色分批应用时分别使用各自最新 batch 锚点；作者手工修改 AI 性格后该角色来源转为 author，不再因旧候选引用失效提示复核，未改性格但修改其他分析来源仍提示 `author_source_changed`。
- 构造超过 30 个 job/batch 后，较早但仍是某角色最新的应用批次仍能被逐角色锚点查询命中；最近历史窗口截断不改变基线 origin/freshness，关联 job 已空时保留 author 基线。
- 基线应用服务只能 patch `personality`，不会创建 `StoryFact`；同步提交服务不会修改任何 `NovelCharacter.details`。

### 14.2 时间与投影测试

- 1988 年年龄锚点到 1991 年目标时间只在证据充分时增加三岁。
- 年级精度返回区间或约数，不伪造生日精度。
- 闪回到更早年份时排除后续身份、年龄和性格变化。
- 叙事未来章节的事实即使故事时间更早，也不得泄漏到目标章节。
- 临时性格表达结束后不覆盖核心性格；长期变化保留前后轨迹。
- 单章一次行为和多个章节的同向行为都不能自动合并为 `long_term_shift`；只有当前正式正文明确表达持续转变时才生成高风险候选，重复模式仍按原事件可见并进入受限上下文。
- 身份真实层、公开层、掩护层和知情人范围分别投影。
- 冲突锚点和冲突事件返回明确冲突，不采用数据库最后写入。

### 14.3 PostgreSQL 与事务测试

- 复合人物外键拒绝跨小说人物。
- 同批次成功只递增一次 `story_ledger_version`；幂等重放不递增。
- 两个并发确认只有一个按预期版本成功，另一个返回 CAS 冲突。
- 任一所选项或关系派生失败时，事实、绑定、关系 revision、批次和版本全部回滚。
- 撤销不删除事实，绑定正确 detached，版本递增；重复撤销幂等。
- source revision 恢复不会重新激活 detached/reverted；restore preview 也不把它们列为将恢复。
- 关系投影随当前有效 `relationship-v2` 事实确定性重算；撤销/来源失效后无依据则归档，有其他依据则保留，人工 override 始终不改。
- 重新应用创建新批次和新事实，不复活旧记录。
- 同一 `reapply_of_batch_id + idempotency_key` 重放返回同一新批次；旧 revision 禁止重新应用。
- 来源 revision supersede/restore 与作者批次撤销互不覆盖。
- 来源 supersede/restore 只有在有效事实集合变化时才各递增一次账本版本；幂等重复恢复不递增。
- 升级迁移不改动既有 510 条事实；降级脚本只删除新增字段前先验证无新数据。

### 14.4 章节生成测试

- 上下文排除目标文档自身和叙事未来事实。
- `story_time_context`、账本版本和投影 fingerprint 均参与 input hash。
- 未锚定时间产生警告但仍可生成；不使用系统日期。
- 未确认提案、失败输出和 reasoning 不进入提示。
- 身份秘密带可见性约束，不被当作公开事实。
- 正文中的提示注入文本不能改变系统契约或短键范围。

### 14.5 前端测试

- 同步结果出现前不存在授权未知结果的确认动作。
- 候选默认未选；高风险项不会被低风险批选。
- 提交、CAS 冲突、失败、取消、刷新和撤销都有明确状态。
- 角色轨迹区正确区分作者基线、正文投影、历史、冲突和旧事实。
- 章节时间字段可清空、可保存、可回显，并支持键盘和窄屏。
- 长证据、长人物名和大量事件不会撑破弹窗或丢失滚动位置。
- 合法 `no_changes`、修复中第 2/2 次、首次 300 秒超时、修复 120 秒超时和失联 stale 都有不同文案，不共用无限 loading。
- 性格缺失、失败、候选待审、全部完成和依据待复核分别显示“补全角色性格 / 重试补全 / 继续审阅 / 次级重新分析 / 复核基线性格”。
- 不具备分析条件时显示准确缺失项并禁用生成；全部性格完整但可选重新分析失败时仍保持完整态，只在历史中显示失败。
- 全部性格完成时不存在抢占主操作位的“重新分析”按钮；次级菜单仍可到达，键盘和窄屏可操作。
- 新 UI 只依据 `entry_state / reason_codes / latest_attempt_state` 组合呈现；兼容字段 `stale=true` 不能单独把“仅新增章节”变成基线待办。
- 新章节采用、同步进展完成、角色页加载和正文保存都不会触发基线分析请求，也不会显示基线待办红点。
- 候选审阅、默认零选择、替换非空值二次确认、CAS 冲突、应用批次恢复和模型证据仍可用。
- 关闭未应用的 ready 候选后仍显示“继续审阅”；应用任意子集后同一 job 不再可追加应用，未选项有明确本次放弃提示，剩余缺失角色回到新一轮“补全角色性格”。

### 14.7 上线、回退与正式数据保护

1. 迁移前备份 PostgreSQL，并记录小说、角色、事实、绑定、提案和批次数量及关键哈希；不删除任何卷。
2. 先在隔离 PostgreSQL 从当前生产 schema/data 副本升级，核对四个新增字段、旧记录数量和查询计划。
3. 正式环境只执行 additive migration，再安装新 PawApp；迁移过程中不回填旧人物事实。
4. 升级切换使用单写者门禁：先停止旧版同步写请求，再切换新 PawApp；不能让旧、新提交服务同时接受作者确认。旧版空快照候选只读展示并要求重新同步。
5. UI 只有在新 DTO/API 均可用后才展示轨迹和新同步流程，不保留新旧两套提交按钮。
6. 应用层需要回退时优先退回旧 PawApp/基础镜像并保留新增列；回退前必须停止新写请求，并证明不存在 `running / repairing / ready / partially_accepted` 的 v2 提案。若存在，先等待结束并由作者处理，或在保留审计记录的前提下显式置为 `superseded`；条件不满足则中止回退，不能把可提交 v2 候选交给旧代码。
7. 旧代码只被允许读取已提交 v2 事实并忽略 additive 列，不进行破坏性 schema downgrade；回退后轨迹页和 v2 同步入口降级为不可用，不承诺旧版本继续编辑 v2 候选。
8. 只有四个新增字段尚无任何新数据时，隔离环境才允许验证 Alembic downgrade；正式环境已有 v2 事实、章节时间或提案快照后，downgrade 必须中止并先导出/恢复备份。
9. 《刑侦1988:档案里消失的人》的真实候选在作者确认前不得应用；测试应用前再次备份，撤销后核对事实状态、关系 revision、账本版本和角色 details 哈希。

## 15. 性能边界与未来升级触发器

当前单本最多 281 条事实，因此 v1 只用 SQL 索引和内存纯投影：

- 隔离性能样本使用 2,000 条总事实、至少 500 条结构化人物事件；
- 单人物轨迹 API 在本机 PostgreSQL 热缓存下 p95 目标不高于 300 ms；
- 下一章上下文只选相关角色和受限事件数，避免把整本账本塞入提示。

只有同时满足以下条件才允许重新评估专用事件表或物化投影：

- 真实单本超过 5,000 条结构化人物事件，或经查询/index 优化后 p95 仍持续不达标；
- 有可复现 profiling 证据证明瓶颈来自 JSONB/投影，而非 N+1、无索引或过量响应；
- 新 ADR 明确迁移、双写禁止、回退和权威来源。

这是一条未来触发器，不是本计划的隐藏第二阶段。

## 16. 子代理并行施工设计

### 16.1 组织原则

本计划值得并行，但只能并行**新增、互不重叠的纯模块和测试**。`backend/models.py`、`backend/services.py`、`backend/app.py`、`backend/creative_services.py`、`frontend/src/types.ts`、`frontend/src/chapter-workflow.ts`、`frontend/src/workbench-studio.ts` 等共享文件必须由唯一集成责任人串行修改。

当前工作区已有大量其他专项未提交改动，且多个目标共享文件正在变更。因此施工前必须先完成 `CST-G0` 所有权核查；未能证明不覆盖用户改动时，不得派发写代码包。

主代理是唯一集成责任人，唯一可以执行最终暂存、提交和推送的人。子代理不得提交、推送、执行生产迁移、操作真实 Agent 状态或修改未分配文件。

### 16.2 冻结接口

并行前由主代理冻结：

- `character-state-v2`、`story-time-v1`、短键目录和错误码；
- 迁移字段、复合外键和索引；
- 投影输入/输出 DTO；
- 提案、批次状态机；
- 角色轨迹 API 和前端类型；
- `story_ledger_version` CAS 规则。

冻结后的更改只能回到主代理裁决，不能由子代理各自演化。

共享资源锁由主代理持有和释放：

| 锁 | 唯一持有者 | 覆盖范围 |
| --- | --- | --- |
| `LOCK-MIGRATION-HEAD` | `CST-DB` | Alembic head、`backend/models.py`、升级/降级顺序 |
| `LOCK-BACKEND-INTEGRATION` | `CST-BE-INTEGRATION`，随后 `CST-CONTEXT` | 后端共享服务、API、Runtime 和事务入口 |

## 17. 工时、重量和缺陷复核

### 17.1 减重后的估算

| 模块 | 估算 |
| --- | ---: |
| 基线状态拆分、输入快照、短键、严格证据、修复、超时与诊断 | 5–8 小时 |
| 最小迁移、轨迹 schema、纯投影 | 5–8 小时 |
| 同步提交、关系原子化、账本 CAS、撤销、上下文和故事线窄修复 | 7–11 小时 |
| 基线入口收敛、角色页、同步结果和章节时间轻量 UI | 5–8 小时 |
| PostgreSQL、真实模型、真实页面与回归 | 4–6 小时 |
| **合计** | **26–41 小时** |

第二轮深查发现输入快照、关系原子提交和有界等待也是 P0；第三轮又补入基线入口状态拆分、文案和非重复回归，因此估算从 24–39 调整为 26–41 小时。这仍是一个中等规模可靠性专项，但相较第一版 38–60 小时方案已删除三张表、完整时间线 CRUD、物化当前态、独立事件编辑器、四区 UI 和过早的大规模性能架构。保留现有候选安全能力只增加小幅接线与测试成本，远小于删除后未来重建；继续压缩只能通过删除证据、CAS、撤销或双坐标，风险大于节省。

### 17.2 已发现并修正的计划缺陷

| 原缺陷 | 本版修正 |
| --- | --- |
| 重复建设人物事件和来源表 | 复用 `StoryFact`、`DerivedSourceBinding`、提案和批次 |
| 泛化“重新分析”与章节演进含义重叠 | 保留低频基线性格分析，章节变化只走“同步进展” |
| 完整输入 hash 一变化就提示基线过期 | 分离输入变化、基线复核原因和新增章节证据状态 |
| 失败、缺失和来源失效混在一个状态/原因枚举中 | 拆成入口状态、复核原因、最近 attempt 状态和 intent；可选失败不降级完整角色卡 |
| 调用前无法知道候选最终引用，却预设候选权威指纹 | 调用前只固化来源指纹目录；输出证据校验后再生成并保存候选权威指纹 |
| 一个全小说指纹会让无关角色改动导致所有人物基线误报 | 调用前保存来源目录，输出后按角色和实际引用生成独立权威指纹 |
| `analysis_intent` 未明确参与幂等，可能复用错误语义的 attempt | intent 纳入 `input_hash` 和幂等键；`force_new` 只控制同语义重试 |
| 生成前角色 version 被直接当作应用后 freshness，可能刚应用就过期 | 候选应用仍用生成前 CAS；应用后改用 apply batch 的结果版本和 after snapshot 作为新锚点 |
| 只看全局最新应用批次会遮蔽分批角色，手工性格也可能继续继承旧 AI 证据 | 逐角色选择最新锚点；作者手工改性格后来源回归 author，旧候选证据不再主张当前值 |
| 用最近 30 条历史窗口查权威锚点，长篇频繁分析后会丢失早期角色来源 | 历史窗口与锚点查询分离；按每个活跃角色精确取最新批次及关联 job |
| 部分应用后角色 version 已变化，却仍暗示剩余旧候选可以继续应用 | 关闭弹窗可继续；一旦应用即结束该 job 审阅，未选项明确本次放弃，缺失角色新建分析 |
| “补全角色卡”可能误导为会改全部字段 | 页面使用“补全角色性格 / 重新分析基线性格”，明确只 patch `personality` |
| 为消除重复而直接删除现有安全能力 | 保留候选审阅、默认零选择、CAS、幂等、恢复和模型审计 |
| 提案只有 input hash、没有实际输入快照 | 增加有界 `input_snapshot`，提示/验证/提交共用一份目录 |
| 只谈历史，没有稳定结束/纠错目标 | 增加短 `track_key` -> 服务端 `track_id` |
| 用两个章节的同向行为直接推断长期性格，却没有跨来源依赖失效协议 | 首版只接受正文明确的持久转变；跨章重复模式并列展示，不自动合并核心性格 |
| 只按章节或只按日期会处理错闪回 | 明确叙事坐标 + 故事时间双过滤 |
| 让模型回显内部来源 UUID | 改为快照短键，服务端解析 |
| 宽松 JSON 恢复可能误收思考对象 | 新契约只接受唯一完整 final JSON |
| 无效类型被跳过或降级 | 整体修复或安全失败 |
| 正文非空强制至少一条会诱发编造 | 增加结构化 `no_changes` 成功终态 |
| 最早 200 条事实截断了较新上下文 | 相关性/叙事位置确定选取并记录遗漏与 fingerprint |
| 预先确认后自动提交未知内容 | 结果出现后逐项确认，默认不选 |
| 升级前旧提案没有 v2 快照却仍可能被提交 | 旧提案只读可审计，提交稳定拒绝并要求重新同步；GET 不改状态 |
| 旧角色候选缺少新指纹，但已应用性格又不能被协议升级否定 | 未应用旧候选要求重分析；已由作者应用/恢复的性格保留并按 author 基线处理 |
| 回退旧 PawApp 时遗留可提交 v2 候选 | 增加单写者与回退前 pending-v2 清零门禁，不满足就中止回退 |
| 事实与关系分两个事务提交 | 同事务按有效 `relationship-v2` 事实重算关系投影并记录 revision |
| 年龄可能被系统日期或章节号误推 | 只用小说内锚点，并返回精度/冲突 |
| `story_ledger_version` 名存实亡 | 锁 Novel、CAS、每批事务递增一次 |
| revision 失效/恢复改变事实却可能不改版本 | 有效集合变化与同一正文事务一起递增，空变化不递增 |
| 撤销字段存在但没有行为契约 | 明确批次撤销、detached 和新批次重新应用 |
| 来源恢复可能复活作者已撤销事实 | restore preview/reconcile 永久跳过 detached/reverted |
| 同步与角色分析没有安全截止 | 首次 300 秒 + 修复 120 秒总上限、晚到丢弃和 stale 收口 |
| 身份变化可能提前泄密 | 区分身份层和知识范围 |
| 样例故事线规则污染通用项目 | 删除关键词和 GET 写入，只认服务端短键 |
| 全量旧事实自动迁移风险高 | 旧事实只读展示，不自动结构化 |
| 前一版性能目标脱离真实规模 | 以 281 条现状和 2,000 条验收样本定边界 |
| 并行可能覆盖当前大量脏文件 | G0 先做所有权门禁，共享文件串行 |

### 17.3 仍然存在但可接受的限制

- 旧 `character_state` 不参与 v2 投影，早期章节需要作者按章重新执行“同步进展”生成 v2 候选，不能自动还原完整历史；本计划没有隐藏的手工事件 CRUD。
- 渐进式性格变化会以多条临时/观察模式进入轨迹与下一章上下文，但首版不会仅凭跨章相似行为自动合并为核心 `long_term_shift`；这是避免缺乏跨来源失效链时误改人物核心的有意限制。
- `main` 单时间线无法表达真正平行宇宙；当前没有产品证据证明必须支持。
- 自然语言故事时间可能只能得到区间或顺序，页面必须诚实显示精度。
- 隐藏真相即使带禁止揭示标签，模型仍可能违反约束；候选审阅和正文采用流程仍是最终保护层。
- 真实模型会持续升级，因此只有通用契约和每次调用证据可以长期维护，不能承诺任意未来模型零适配。
