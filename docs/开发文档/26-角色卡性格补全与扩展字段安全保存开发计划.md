# 角色卡性格补全与扩展字段安全保存开发计划

状态：已于 2026-08-26 完成功能施工、专项自动化、隔离 PostgreSQL 验收、生产迁移与 PawApp 热升级；真实页面已显示候选分析入口。2026-08-27 首次真实 DeepSeek 分析因 evidence 来源 ID 不属于输入快照而安全失败，0 个应用批次且正式角色资料未修改；证据协议可靠化已转入[计划 27](./27-人物状态轨迹与章节同步进展可靠化开发计划.md)，修复前不得表述为跨模型可用。2026-08-27 用户进一步批准把现有“重新分析”能力收敛为低频“基线性格分析”：保留候选审阅、CAS、恢复和审计，删除“新增正文即提示重新分析”的目标行为；该调整已纳入计划 27，尚未施工。全量共享门禁仍被另一个未收口的“朗读”专项测试阻塞，不得把本文状态表述为全仓零失败。

计划日期：2026-08-26（Asia/Shanghai）

适用范围：QwenPaw 2.1.x 中的“AI小说世界2026”PawApp，以及专用 `ai-novel-writer`（AI 小说作家）Agent。

## 1. 结论与当前证据

### 1.1 已核实事实

- 小说《刑侦1988:档案里消失的人》当前有 6 个正式角色、1 章正式正文，正文约 2673 个字符。
- 6 个角色的 `details` 已包含年龄、身份、核心缺陷、核心动机、秘密、人物互锁和成长方向等丰富资料，但都没有 `personality`。
- 角色弹窗只读取 `details.personality`，所以该字段不存在时必然显示空白。
- `outline_characters` 当前只强制模型返回四值性别，没有强制返回 `personality`；大纲完成服务只会保存模型实际返回的 `details`。
- 章节“同步进展”当前可以产生 `character_state` 故事事实和人物关系，但不会把它们写回正式角色卡。
- 前端保存角色时只发送性别、年龄、身份、性格四个 detail 字段，后端随后整体替换 `character.details`；这可能删除 `secret`、`core_flaw`、`core_motivation`、`growth_direction` 等未在弹窗展示的扩展资料。

### 1.2 根因裁决

性格空白的首要原因是**产品实现缺少性格生成、候选审阅和安全回填链路**，不是章节数量不足，也不是模型无法分析。

一章正文不足以证明稳定的“行为型人格”，但正式大纲、人物小传、核心缺陷和动机已经足够生成第一版“设定型性格”。因此本计划不要求作者先写更多章节，也不把 `core_flaw` 静默伪装成 `personality`。

## 2. 唯一方案与不可退回原则

本专项只采用以下一套生产路径：

1. 新建大纲时，`outline_characters` 必须显式生成 `details.personality`。
2. 已有小说通过作者主动点击当前“补全角色卡”入口，由 AI 小说作家 Agent 生成可审阅的性格候选；计划 27 施工后文案收敛为更准确的“补全角色性格 / 重新分析基线性格”。
3. 候选必须展示当前值、建议值、依据类型、置信度和原文证据；默认不勾选，作者逐项选择后才能应用。
4. 应用使用角色版本 CAS、输入快照哈希、幂等键和单事务写入；任何一个目标角色冲突时整批不写。
5. 角色手工保存改为 detail 字段合并，不再整体替换未知扩展字段。
6. 当前实现会在正文新增后把候选标记为“可重新分析”；计划 27 施工后，单纯新增正文不再触发基线性格提醒，章节人物变化统一进入“同步进展”。
7. 模型始终跟随 `ai-novel-writer` 的当前有效模型；不建设模型档案、模型白名单、逐模型 Skill、固定模型模式或静默回退。
8. 使用现有通用 `character-craft` Skill 约束人物分析；不为 MiniMax、Qwen、DeepSeek 分别复制 Skill。

禁止退回以下临时方案：

- 不用 `core_flaw`、人物小传或描述字段作为 UI 的无提示回退值。
- 不按姓名、性别、职业或题材刻板印象猜测性格。
- 不在“同步进展”或打开页面时自动调用模型。
- 不直接用模型结果覆盖正式角色资料。
- 不以“章节太少”为由长期保留空白，也不把单章行为表述成稳定人格。

## 3. 目标与非目标

### 3.1 目标

- 新角色进入正式角色卡时不再无故缺少性格。
- 为已有角色提供一次可恢复、可审计、可重复运行的批量补全流程。
- 区分创作设定与正文行为证据，避免把一时行为固化成人格。
- 保存任何可见字段时保留未展示的扩展资料。
- 兼容思考模型，并保留 requested/actual provider、model 和 Agent 证据。
- 失败、取消、冲突、刷新、重装和模型切换均不得改变正式角色资料。

### 3.2 非目标

- 不自动诊断心理疾病，不产生医学或人格类型结论。
- 不建立全书实时人物画像、向量检索或第二套 Agent Runtime。
- 不自动重写人物小传、核心动机、缺陷、秘密和人物弧。
- 不修改 QwenPaw 核心，不新增 PawApp 之外的模型选择器。
- 不在本专项中重构所有角色字段为完整 revision 系统。

## 4. 产品行为契约

### 4.1 性格的语义

正式字段仍为 `NovelCharacter.details.personality`，内容是作者确认的、用于持续写作的人物行为倾向，不能只是一串空泛标签。

候选必须标记依据类型：

- `designed`：来自正式大纲、人物小传、核心动机、核心缺陷或成长方向。
- `observed`：来自已采用正式正文中的可观察行动、回避、语言、习惯或代价。
- `mixed`：同时有设定资料与正文行为证据。

单章只能支持 `designed`，或带“样本有限”警告的 `mixed`；只有至少两个不同正式章节都提供有效行为证据时，才允许输出 `observed` 稳定判断。

### 4.2 新建大纲

`outline_characters` 的每个角色必须返回：

- `name`
- `role_type`
- `description`
- `details.gender`
- `details.personality`

`personality` 必须是 8–120 个中文可见字符，至少包含一个可指导人物选择的倾向或矛盾，不接受“聪明、善良、冷酷”等无行为含义的单标签。缺失或无效时生成任务失败并安全重试，不采用残缺结果。

大纲重新生成时：

- 已有正式角色的非空 `personality` 与 `gender` 都必须保留。
- 模型新结果只能进入大纲草稿；作者完成大纲时才物化新角色。
- 不按姓名静默匹配后覆盖作者已编辑的人物资料。

### 4.3 已有角色补全

当前实施在角色列表页提供“补全角色卡/分析角色性格”入口。点击后先读取状态和来源摘要，再由作者明确确认模型调用；计划 27 将按缺失、失败、待审、完成和依据失效显示状态化文案，完整角色卡只保留次级“重新分析基线性格”。

生成完成后显示批量审阅面板，每个角色包含：

- 当前性格；
- 建议性格；
- `designed / mixed / observed` 依据类型；
- 0–100 置信度；
- 1–5 条带来源的原文证据；
- “样本有限、已有人工值、证据冲突”等警告；
- 独立选择框，默认不选择。

已有非空性格默认只显示“保留当前值”，除非作者主动展开并选择替换。证据不足的角色返回 `insufficient_evidence`，不得编造候选。

### 4.4 正文增加后的演进

当前实现事实：新的正式章节或已确认 `character_state` 会让最近一次输入快照变为 stale，界面提示“有新正文，可重新分析”；它不会自动生成、自动应用或覆盖当前性格。

计划 27 冻结的目标行为：

- 新增正式章节或新确认人物轨迹只影响章节“同步进展”，不再把基线性格分析标记为待办。
- 基线性格入口只在性格缺失、作者修改大纲/人物设定、已应用候选引用的来源 revision 失效，或作者从次级菜单主动要求时出现。
- 新章节可以在作者主动重新分析时作为补充证据，但“有更多证据”不等于原基线失效，也不产生提醒红点。
- 已引用来源失效只显示“基线依据待复核”，不自动撤销作者已经确认的 `personality`。
- 重新分析仍只产生候选和证据；替换非空性格继续要求作者显式选择和 `replace_existing`。
- 人物在正文中的临时或长期变化写入 `StoryFact` 轨迹，绝不由本入口覆盖角色基线。

## 5. 模型输入、输出与证据校验

### 5.1 服务端构造输入

前端不得提交任意小说正文作为模型输入。服务端按小说范围构造不可变快照：

- 活跃角色的 ID、version、姓名、层级、人物小传；
- allowlist 中的 `personality`、`core_flaw`、`core_motivation`、`growth_direction`、`identity`；
- 已完成大纲的背景和主情节；
- 已确认 `character_state` 故事事实；
- 正式 revision 中精确出现该角色姓名的局部证据窗口。

正文证据按正式 revision、章节顺序和字符位置稳定排序。每个角色最多 8 个窗口，每个窗口最多 400 个可见字符，全任务正文证据最多 16000 个可见字符；超限时记录截断信息，不静默换用 working copy、候选正文或未同步稿。

### 5.2 输出契约

```json
{
  "characters": [
    {
      "character_id": "uuid",
      "base_version": 2,
      "status": "candidate",
      "personality": "重事实、强控制，在压力下会把求真变成对他人的逼迫；面对无辜者受伤时又会迟疑。",
      "basis": "mixed",
      "confidence": 86,
      "evidence": [
        {
          "source_type": "character|outline|chapter|story_fact",
          "source_id": "stable-id",
          "quote": "可在输入快照中逐字验证的短证据"
        }
      ],
      "warnings": []
    }
  ]
}
```

证据不足时使用 `status=insufficient_evidence`，并省略 `personality`；不得返回未在输入角色集合中的 ID。服务端必须校验：

- `character_id` 唯一且属于当前小说；
- `base_version` 与快照一致；
- 性格长度和非空规则；
- basis 枚举合法；
- evidence 的来源 ID 存在，quote 能在相应快照文本中逐字命中；
- `observed` 至少覆盖两个不同正式章节；
- 模型 actual provider/model 与 requested 证据可核验；
- 思考内容、工具轨迹和中间消息不能混入最终 JSON。

任何结构错误只使任务失败，不改变正式角色卡。

### 5.3 Agent 与 Skill

- 运行时只读取 `ai-novel-writer` 当前有效模型。
- 使用现有 `character-craft` Skill 的“特征必须绑定可观察证据”原则。
- 结构化 JSON、证据和长度约束放在任务契约中，不建立模型档案。
- 模型切换后新任务自然使用新模型；旧任务继续保留原 requested/actual 审计信息。

## 6. 数据与恢复设计

### 6.1 生成任务

复用 `creative_generation_jobs`，新增受控 kind `character_profile_completion`。只能通过专用领域服务由服务端构造输入快照，不能让通用 API 接受客户端伪造的角色范围。

同一小说同一 kind 只允许一个 running 任务；`force_new` 也不能绕过 single-flight。相同 input hash 默认复用最近结果，作者明确重新分析时才创建下一 attempt。

模型调用必须发生在数据库长事务之外：先用短事务固化任务与输入快照，事务提交后调用 Agent，再用短事务核验并保存输出。网络超时或进程退出只能留下可诊断的任务状态，不能持有角色行锁或产生半次应用。

### 6.2 应用审计

新增 `character_profile_apply_batches`：

- `id`、`novel_id`、`generation_job_id`；
- `idempotency_key`；
- `decisions_json`；
- `before_snapshot`、`after_snapshot`；
- `base_versions`、`result_versions`；
- `state`、`created_at`、`applied_at`；
- 可选 `restored_from_batch_id`。

一次应用在同一数据库事务内：按 UUID 稳定顺序锁定所有目标角色，校验小说范围、active 状态、base version、任务 input hash 和幂等键，合并被选择的 `personality`，写入角色 version 和应用批次。任一冲突则整批回滚。

恢复不倒拨版本：作者可以基于 `before_snapshot` 创建一次新的 restore 批次；只有当前角色版本与被恢复批次的 result version 一致时才允许恢复。

### 6.3 手工保存安全修复

角色 API 改为显式 `details_patch` 语义：

- 只更新作者实际提交的字段；
- 未提交的扩展字段原样保留；
- 清空某字段必须显式提交该字段的空值；
- 删除未知 key 必须使用单独、受 allowlist 约束的删除操作；
- 继续使用 `expected_version` CAS。

兼容期内旧 `details` 请求也按 patch 合并处理，并记录契约弃用测试；不能继续整体替换 JSON。

## 7. API 与前端边界

专用 API 保持项目命名空间：

- `GET /api/ai-novel-world-2026/novels/{novel_id}/character-profile-completion/status`
- `POST /api/ai-novel-world-2026/novels/{novel_id}/character-profile-completion/generate`
- `GET /api/ai-novel-world-2026/novels/{novel_id}/character-profile-completion/jobs/{job_id}`
- `POST /api/ai-novel-world-2026/novels/{novel_id}/character-profile-completion/jobs/{job_id}/apply`
- `POST /api/ai-novel-world-2026/novels/{novel_id}/character-profile-completion/apply-batches/{batch_id}/restore`

UI 状态必须区分：读取中、不可生成、尚未生成、生成中、候选就绪、已过期、应用冲突、模型失败、应用成功和可恢复。刷新页面后从持久任务恢复，不依赖内存中的弹窗状态。

移动窄屏使用单列角色审阅；桌面使用当前值/建议值/证据三段布局。所有选择框、证据展开和操作按钮必须支持键盘、焦点恢复与非颜色状态提示。

## 8. 当前小说的安全补全流程

本专项代码通过全部门禁后，才对《刑侦1988:档案里消失的人》执行：

1. 备份数据库并记录小说 ID、6 个角色 ID、version 和 details 哈希。
2. 运行一次“补全角色卡”，输入只使用该小说的正式大纲、正式角色资料和已采用章节。
3. 核对每条候选证据与角色 ID，禁止按姓名猜测映射。
4. 由作者在审阅面板明确选择需要采用的性格。
5. 应用后确认 6 个角色原有 `secret/core_flaw/core_motivation/growth_direction/interlock` 均未丢失。
6. 执行一次恢复演练；恢复应创建新版本，不删除生成任务或历史批次。

计划阶段不直接为这 6 个角色写入推测性格。

## 10. 测试与验收矩阵

### 10.1 后端单元与契约

- 新大纲缺失/空白/超长 personality 必须失败。
- 大纲重生成不得覆盖现有非空 personality。
- `details_patch` 保存性格后，扩展字段哈希保持不变。
- 证据 quote 不存在、来源越界、角色 ID 越界、重复 ID、错误 base version 均失败。
- 单章不能产出无警告的 `observed`。
- 思考模型只有 reasoning、没有 final JSON 时任务失败。
- requested/actual 模型不一致或无法核验时不得应用。
- running 任务在 `force_new=true` 下仍保持 single-flight。
- 相同 idempotency key 重试只产生一次应用批次和一次角色版本增长。

### 10.2 PostgreSQL 集成

- 多角色应用单事务；一个角色 CAS 冲突时全部不写。
- 并发生成只保留一个 running 任务。
- 并发 apply 不重复写入。
- apply batch 保存 before/after、决策和版本；恢复创建新版本。
- 小说、角色、任务跨 scope 访问全部拒绝。
- migration 从当前 head 升级成功，历史数据不变，重复升级幂等。

### 10.3 前端

- never/running/ready/stale/failed/conflict/applied 状态文案和按钮正确。
- 默认没有任何候选被选择；应用按钮在零选择时禁用。
- 已有人工性格不会默认替换。
- 刷新后恢复候选和选择前状态，不伪装为已应用。
- 证据、警告、置信度不只靠颜色表达。
- 角色保存只发送 patch，不删除未展示字段。

## 12. 自查结果

### 12.1 已通过的自查

| 自查方向 | 发现 | 计划中的修正 |
| --- | --- | --- |
| 根因 | 空白来自字段未生成，不是模型能力不足 | 同时补新建契约和已有角色候选流程 |
| 章节样本 | 一章不能代表稳定行为人格 | 区分 designed/observed/mixed，observed 至少两个章节 |
| 数据丢失 | 角色保存整体替换 details | 改为 patch 合并并增加哈希回归测试 |
| 模型幻觉 | 性格容易变成空泛标签或刻板印象 | 行为化长度规则、来源证据逐字校验、证据不足显式返回 |
| 作者权威 | 自动回填会覆盖正式角色卡 | 默认不选择、显式应用、CAS、整批原子写入 |
| 可恢复性 | 现有角色没有专项应用历史 | apply batch 保存 before/after，恢复创建新版本 |
| 模型切换 | 固定模型会重新形成硬编码 | 只跟随 AI 小说作家 Agent，保留 requested/actual 证据 |
| 思考模型 | reasoning 可能污染 JSON | 只解析独立 final，reasoning-only 安全失败 |
| 并发 | force new 可能产生重复任务 | 小说级 single-flight、幂等 apply、稳定锁顺序 |
| 事务边界 | 模型调用可能长期占用数据库事务 | 任务快照、外部调用、结果保存分成短事务，apply 另用单一短事务 |
| 上下文成本 | 全书正文会膨胀输入 | 服务端局部证据窗口、稳定排序、总量上限和截断披露 |
| 语义污染 | core_flaw 不等于 personality | 禁止 UI 静默 fallback，只生成明确候选 |
| 工作区冲突 | 当前有朗读等并行专项修改共享文件 | G0 明确共享锁，重叠文件只由主代理串行集成 |

### 12.2 计划完整性结论

本方案覆盖了新角色、已有角色、一章样本、后续章节、作者确认、模型切换、思考模式、证据、并发、幂等、数据丢失、恢复、安装和卸载非回归。没有保留第二套模型方案，也没有把 Skill 绑定到具体模型。
