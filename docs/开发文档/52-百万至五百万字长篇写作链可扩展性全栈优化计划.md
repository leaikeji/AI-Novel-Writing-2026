## 1. 当前实现事实

### 1.1 存储规模本身不是主要危险

以下按中文可见字符、UTF-8 约 3 bytes／字和当前 `800` 字块、`120` 字重叠作数量级估算；实际值受 Markdown、段落边界、历史 revision 和索引代数影响：

| 活跃正文规模 | 纯正文数量级 | 活跃正文 chunk 数量级 | 2048 维 float4 向量原始数量级 |
| ---: | ---: | ---: | ---: |
| 1,000,000 字 | 约 3 MB | 约 1,500 | 约 12 MB |
| 5,000,000 字 | 约 15 MB | 约 7,400 | 约 60 MB |

PostgreSQL 可以保存这种规模。工作副本、当前正式 revision、历史检查点和多代语义索引会按保留数量放大空间，但这仍然首先是生命周期和查询形状问题，不是“500 万字必然存不下”。不得为了减小数字自动删除用户 revision、恢复证据或旧迁移。

### 1.2 现有安全机制必须保留

- 写作检索默认只输出 Top 10 语义命中，向量失败可降级为本地词面检索。
- Context V4 按实际正文模型有效窗口计算硬预算；required／作者显式块放不下时返回 `context_overflow`，可选完整块放不下时记录 `budget_omitted`，不静默截断逻辑块。
- 最终 prompt 在调用正文模型前还有独立的有效窗口估算检查。
- 生成任务先冻结不可变上下文快照；模型失败或超长输入不能自动覆盖正式 working copy／revision，候选仍需作者确认采用。
- 计划 51 已把账本列表改为数据库有界分页：默认每页只实例化 20 个 StoryFact，2,000 条下索引扫描 21 行；这项成果是长篇方案的基础，不重建第二套账本。

### 1.3 已核实的全书线性路径

#### A. 打开作品会返回整部正文

`backend/services.py::get_novel_tree` 会查询全部文档、全部 working copy 和当前 base revision；`_versioned_document_payload` 又把每篇文档的完整 `content_markdown` 写入树响应。前端 `workbench-v2.ts::loadNovel` 先保存整个 `/novels/{id}` 响应，再单独加载选中章节。

结果是打开或刷新作品时，服务器和浏览器都会处理整部小说；500 万字正文会在 HTTP JSON、Python 对象、浏览器字符串和 React 状态中形成多份瞬时副本。它不必然导致 OOM，但响应体、解析暂停和内存峰值都随全书字符数增长。

作品库 `list_novels` 还会逐作品读取所有章节 working copy，并在 Python 中重新计算全文可见字数。它会让“只看作品列表”也随全部作品正文总量增长。

#### B. Context V4 先装载全书，再按模型预算裁剪

`backend/context_v4_loader.py` 当前会：

- 读取小说全部 StoryFact v2、StoryEventLink 和相关来源有效性；
- 读取全部人物历史 revision 后在 Python 中选最新版本；
- 查询全部章节，并逐章读取 working copy 和 base revision 的完整正文；
- 为每篇正式章节创建完整 ContextBlock、估算 token，最后才交给 assembler 做预算取舍。

因此“模型最后没收到 500 万字”不等于服务器没有先读过 500 万字。这个路径会出现在正文生成、章纲、审稿和采用 Context V4 的其他写作入口。

#### C. 最终 prompt 预算还没有覆盖全部组成部分

Context V4 的 `included_blocks` 有预算，但 `current_story_facts` 在 `build_chapter_generation_prompt` 中被再次完整拼接；当前草稿、诊断和固定指令也不是同一个组件级预算结果的一部分。最后一道模型窗口检查会阻止明显超长输入，却发生在全量事实解析、全量章节对象构造和 prompt 拼接之后。

章前 brief 目前既以 required Context block 进入 assembler，又由最终模板直接拼接，并可能再次拼接 `chapter_requirements` 块；这属于必须通过组件账本消除的重复。当前章 manuscript 在 CHAPTER_BODY assembler 中会被排除，不能误报为它已经重复进入最终 Prompt，但 loader 仍无必要地读取并构块。V4 envelope 缺失时现有 builder 还能静默走 legacy 分支，这会绕过统一预算目标。

这能保护模型调用，却不能证明上游内存／耗时有界，也可能让一个 assembler 内部“预算通过”的快照在最终 prompt 阶段失败。

#### D. 语义结果有 Top-K，但数据库／Python 候选仍全量

当前 Dense 通道按 cosine 排序后 `.all()`，词面通道也取得全部合格 source／chunk，再在 Python 组装候选和融合。当前没有 HNSW／IVFFlat，这符合计划 24／34 和 ADR-0008 的既有决定；约 7,400 个正文 chunk 未必需要 ANN，但必须先把数据库返回给 Python 的候选集有界化，并用真实 EXPLAIN／P95 决定是否还需索引。

不得为了 ANN 截断 2048 维向量或静默更换向量空间。任何 ANN／表达式索引只有在真实规模证据、pgvector 当前版本能力和检索质量门禁都通过后才可另行批准。

#### E. 助手与搜索的输出有界，上游读取不完全有界

- 助手 workspace context 最终限制在 40,000 字，但部分流程会先联表取得全书 `DocumentWorkingCopy.content_markdown`，再按输出预算选择。
- 作品内搜索使用 `ILIKE '%query%'` 扫描 working copy 正文，并把匹配正文加载到 Python 生成片段；返回最多 50 条不等于扫描最多 50 条。
- 单章读取、自动保存和 IndexedDB 恢复是按文档工作的，应继续保持；不得用整书缓存替代它们。

### 1.4 现有验收不能证明百万字稳定

- 计划 37 的真实样书是三章、约 2,000 字／章，证明写作闭环，不证明百万字性能。
- 计划 51 的 500／2,000／10,000 是 StoryFact 数量基准，证明账本页面有界，不代表 100 万／500 万字正文链有界。
- 2026-08-30 的真实证据记录当时有效正文模型输入窗口为 1,000,000；这是当时公开配置事实，不是未来模型永久承诺，也不表示应当把窗口填满。
- 当前仓库没有 100 万／500 万字合成作品的打开、生成上下文、搜索、助手、保存、恢复和浏览器联合证据。

当前发布口径只能是：**数据库可承载该数量级，但完整写作链未验收；100 万字为需要专项验证的黄色状态，500 万字为不得承诺稳定支持的红色状态。**

### 1.5 2026-09-02 向量与账本现状复核

本轮只读运行态与源码复核确认：

- 当前向量 Profile 为阿里云百炼 `qwen3.7-text-embedding`、2048 Dense、cosine，active generation 为 12，连接状态 `ready`，冻结评测为 `passed`。
- 施工基线复查时，长期环境保留 3 本小说：1 本为 `granted` 且允许写作 query，语义索引为 `ready/current`，共有 3 个 source、31 个 chunk、0 个失败；另 2 本未授权、索引状态为 `not_authorized`。因此不能再沿用“3 本均未授权、向量检索关闭”的旧审计结论；后续验收必须同时覆盖已授权 hybrid 与未授权本地降级两条真实状态，但不得读取或压力测试这些真实小说正文。
- 当前 V1 索引语料只有 `manuscript`、`planning`、`private_asset`。StoryFact 账本由 Context V4 通过共享 fact authority resolver 直接读取，不依赖向量索引，不存在“第二套向量账本”。
- 已有小说级 `novel-embedding-consent/2` 能明确授权正文／规划／已绑定私有素材及写作 query，但不存在“作者一次同意后，后续新小说自动建立逐书授权”的偏好契约。
- 当前 UI 请求中的 `acknowledged_scopes` 还是任意字符串数组，后端实际固定写入三类 corpus 而未以该字段完成集合等值校验；GET 的 `version` 是按状态合成的 0／1／2，不是持久化 CAS。授权幂等键又固定包含小说和 notice version，同 notice 撤销后的重新授权／批量重试必须在新契约中明确修复，不能直接复用现状冒充安全默认。
- Dense 通道在数据库完成距离排序但没有候选上限；已索引 lexical 通道会把全部合格 source／chunk 返回 Python；无索引时的本地降级会读取当前合格正文并在 Python 重新渲染、分块和评分。这三个路径在输出 Top-K 的情况下仍可能有 O(全书) 的上游成本。
- 迁移 `0030` 已为 `semantic_chunks.content_text` 建立 trigram GIN，但当前 indexed lexical 查询没有相似度 WHERE 候选谓词，不能据此宣称索引已经限制扫描；必须先修正查询形状再看 EXPLAIN。现有增量 refresh 发布仍有全书 authority digest 重算和 source／chunk ID 全量物化计数，长篇连续保存时也需要有界化。
- `WritingContextSnapshot V1` 已冻结 `mode`、`degraded_reason` 和命中证据，但正文生成前端没有向作者显示本次实际使用了向量增强、本地降级、无相关命中还是检索异常。
- 当前部分生成任务 HTTP projection 会原样带出内部 `input_snapshot`，正文完成响应还可包含完整 `generation_context_snapshot`；这些内部快照可能含 `writing_retrieval` 命中 snippet 和 Context。新增 UI 状态前必须先分离“数据库内部审计快照”和“公开脱敏任务载荷”，不能为了显示模式把更多内部内容交给浏览器。
- `retrieve_for_writing` 的通用可降级异常当前直接生成 `mode=lexical_only`、空 hits 的 degraded snapshot，但该分支没有实际再次执行 local lexical；因此现有 mode 不能直接用于“已改用本地检索”文案。新契约必须区分真正执行 lexical 与只剩基础 Context 的 `context_only/not_run`。

据此裁决：**向量模型和 PostgreSQL + pgvector 底座暂不更换；必须优化查询形状、候选上限、本地降级、索引生命周期、Context／Prompt 去重和作者可见状态。ANN、搜索索引或 schema 变更继续服从 G0 证据门禁。**

## 2. 目标与非目标

### 2.1 目标

1. 作品库、打开作品、卷章导航和切换章节不再传输或常驻未选章节的完整正文。
2. 生成上下文在查询正文大字段和结构化事实之前先完成范围选择；一次写作任务读取的正文／事实记录数由版本化策略和当前任务决定，不由全书总字数决定。
3. 最终 prompt 的固定指令、章前要求、当前草稿、正式规划、人物状态、故事事实、正文证据、私有素材、语义证据和诊断统一纳入同一可审计预算。
4. Dense／lexical 检索只把有界候选返回 Python；是否继续使用精确扫描由 1,500／7,500 chunk 的真实查询计划和延迟裁决。
5. 助手上下文、全文搜索、字数统计和 revision 列表不因输出有界而在上游静默读取全书正文。
6. 保留 CAS 自动保存、IndexedDB 崩溃恢复、不可变 revision、候选审阅、时间线隔离、StoryFact 权威和语义来源证据。
7. 用不含用户正文的 100 万／500 万字合成小说完成后端、数据库、前端和真实 QwenPaw 浏览器验收；UI 固定覆盖 1080P 和 2K。
8. 发现替代完成且无调用者的内部冗余后同版本删除，不留下永久双轨；公开契约按明确兼容窗口退出。
9. 新建小说默认启用当前有效向量模型；每本小说仍有独立授权证据、独立撤销和独立索引状态。现有未授权小说不自动批量启用。
10. 每次 AI 写作完成或降级后，前端以易懂文案显示本次上下文来源和检索状态，不要求作者理解 Dense、RRF 或 generation 等内部术语。
11. 章节／规划／私有素材变更后的增量索引成本与变化 source 数相关，不因小说总字数增长而每次重算整书正文和物化全部索引 ID。

### 2.2 非目标

- 不把整部 100 万／500 万字正文一次发送给正文模型。
- 不建设第二套 Agent Runtime、通用聊天前端、向量数据库、数据库、任务队列或模型选择器。
- 不修改 QwenPaw 上游核心，不读取私有内部配置或数据库结构。
- 不自动生成或维护一套新的“AI 全书摘要权威”；若有界原文 + 正式规划 + StoryFact + 语义证据仍无法满足质量，层级摘要必须另过来源哈希、失效、重建和作者可解释性门禁。
- 不把 ANN 当成立项前提，不为了索引限制截断 2048 维向量。
- 不自动删除历史 revision、旧 embedding generation、真实 StoryFact、恢复证据或迁移历史。
- 不建立工作区未来偏好表；告知版本、Provider、模型或数据范围变化时，既有逐书记录必须转为 `requires_reconsent`，不得沿用旧记录静默扩大外发范围。
- 不因默认开启而阻断写作：未配置 Key、索引尚未就绪、超时、网络失败或无命中时继续走有界本地路径，并明确显示状态。
- 不在本计划直接解决计划 44／45／47／49 的剩余听检、Provider 或长期发布事项。
- 不用伪造的固定毫秒数宣布成功；绝对性能阈值必须由 `L52-G0` 在注明硬件、容器和数据分布后冻结。

## 3. 冻结方案

### 3.1 作品清单、卷章导航与正文分离

新增一个前端工作台专用的轻量 manifest 契约，至少分离：

- 小说元数据和版本；
- 卷元数据；
- 文档 ID、卷 ID、类型、标题、位置、状态、版本、draft version、base revision ID、内容哈希、可见字数和更新时间；
- 当前选择／路由所需的稳定标识；
- **不包含** `content_markdown`、revision 正文、候选正文或来源摘录。

正文继续使用现有单文档读取路径按需获取。前端只常驻当前文档、尚未安全保存的 dirty 文档和有界最近文档缓存；任何缓存淘汰不得丢弃 dirty 状态或 IndexedDB 恢复稿。

卷章数量需要分页或虚拟化。G0 根据 500／2,500／10,000 文档三档决定 manifest 是服务端游标分页还是“轻量全树 + 前端虚拟化”；无论选择哪一种，响应体都不能随正文字符数增长。

现有 `/novels/{id}` 和 `/novels/{id}/tree` 是否属于公开契约由 G0 分类：

- 若仅为第一方内部接口，在前端完全切换、调用者搜索和回归通过后同版本删除重载正文的旧形态；
- 若已公开，则新增 successor、Deprecation／Sunset 和有限兼容窗口，到期后删除，不永久保留两套第一方实现。

作品库总字数不得继续读取全部正文。候选方案是在 `DocumentWorkingCopy` 保存事务中维护单文档 `visible_character_count`，作品列表只做数值聚合；是否需要新列由 G0 的模型／迁移体检确认。若新增列，只能追加新 Alembic revision，覆盖建章、保存、候选采用、checkpoint／restore 和迁移回填，且以内容重新计算值作为一致性校验，不在 `Novel` 上再维护第二份易漂移总计数。

### 3.2 Context V4 改为“先选 ID，再读正文”

一次写作任务按以下层级形成候选集合：

1. 当前章任务书、作者本次显式素材和当前工作稿；
2. 正式大纲／设定及当前时间线必要人物状态；
3. 由当前位置、时间线、实体、事实类型和冲突／待核对状态筛出的结构化故事事实；
4. 有界相邻正式章节证据；
5. 写作检索返回的 Top-K 正文／规划／私有素材证据；
6. 其余允许但非必要的完整块。

数据库先选 source／fact／revision ID 和轻量元数据，再只读取被选中的正文大字段。禁止先把全部章节、全部人物 revision 或全部 StoryFact 构造成 ContextBlock 后再裁剪。

W1 必须冻结 `context-source-selection/1`：在同一一致性读快照中先验证 novel／document／timeline／cutoff 和账本／head 证据，再只查询 ID、排序键、hash、字符／字节长度等轻元数据；对有界 fact candidate 才加载 binding、owning batch、incoming supersedes 并调用共享 resolver；最后只 hydrate 已选 source／revision／range，并复核 head／hash。选择计划至少记录 purpose、position、timeline mapping、策略版本、各类 candidate cap、selected refs、eligible／selected／omitted 计数和 `selection_complete`。

每个 purpose 的 `max_adjacent_chapters`、`max_fact_candidates`、`max_character_instances`、`max_private_assets`、`max_semantic_hits` 和稳定排序只能由 G0 后冻结，本文不猜数。查询使用 `cap + 1` 检测溢出；若无法证明多出的候选均可安全省略，返回 `context_selection_incomplete`。大字段 hydration 前必须使用可信 token 元数据或 `octet_length`／`char_length` 保守上界筛选，不能换一个 helper 后继续先读全文。

结构化事实选择必须复用计划 51 的权威 resolver、时间线／位置隔离和 snapshot 语义，不建立第二套事实生命周期规则。W1 必须冻结：

- 哪些事实属于不可省略的作者显式约束；
- 哪些事实按当前章实体／时间线／故事位置相关；
- 冲突、歧义、来源失效和未来事实如何排除或显式报告；
- 候选超过可用窗口时怎样产生可理解的 omission，而不是静默取“最近 N 条”。

非法 fact、缺失／过期多时间线 mapping 或坏 segment 不能只 `continue` 后继续声称上下文完整；若它们影响 required／安全选择，返回 `context_selection_incomplete`，若只是可选证据则写入可审计 omission。不得猜测修复，也不得泄漏兄弟线／未来内容。

第一阶段不引入模型生成的层级摘要。若 500 万字质量测试证明只有有界原文、正式规划、StoryFact 和语义证据仍不足，再提出独立的派生摘要设计；摘要必须绑定源 revision 集合和内容哈希，可重建、可失效、不可替代正式正文或故事事实。

### 3.3 最终 prompt 使用统一预算账本

最终 prompt builder 必须以组件方式记录每一段输入的：来源、字符数、估算 token、required／explicit／preferred 等级、纳入／省略原因和内容哈希。预算至少覆盖：

- 系统固定指令和长度控制；
- 章前要求；
- 当前草稿；
- 正式规划、人物状态和当前故事事实；
- 相邻正文、语义证据和私有素材；
- 时间线信息和诊断。

W1 必须冻结 `prompt-budget-ledger/1`。每个组件至少具有 stable component ID／kind、source kind／ID／revision／range、content hash、字符数、估算 token、requirement、priority、included／omission code；总账记录有效 Provider／model window、reserved output、estimator／renderer／selection policy versions、hard budget、included／omitted／remaining token、component manifest hash 和 final prompt hash。

同一 brief／chapter requirement 只允许以一个组件身份进入；当前 draft、标题、模板分隔符和全部固定文案都要占预算。同一 source／revision／range 同时被完整上下文和语义检索命中时，只保留优先级更高的一份内容并合并来源证据，禁止按文本字符串做不稳定去重。

硬上限继续从当前有效正文模型窗口派生，遵守 ADR-0008，不用随意固定总字符上限替代真实模型能力。选择策略可以有版本化的章节数／候选数和按用途配额，但不得伪称模型窗口等于推荐填充量。

assembler 预算通过、最终 prompt 估算和实际发送前 guard 必须使用同一输入清单；不再允许 `current_story_facts` 或诊断在预算结束后无界追加。required 内容超限继续失败关闭，正式正文保持不变。

新路径稳定后删除最终 Prompt 的 legacy 无 V4 生产分支；若历史快照展示仍需读取旧结构，只能留在只读展示适配器。Prompt 构建／窗口 guard 失败时，已经创建的 generation job 必须进入明确 terminal failure，不能永久停在 `running`。

### 3.4 语义检索和本地词面通道

保持当前 2048 Dense、cosine、PostgreSQL + pgvector 和 Top-K 输出契约。先完成：

1. Dense SQL 使用有界 per-channel candidate limit，只向 Python 返回融合所需的最小候选和距离；精确 cosine 在数据库内部是否扫描全部向量由 EXPLAIN 记录，不把全部行传回应用层。
2. Lexical SQL 在数据库完成阈值、排序和 candidate limit，再只对有界 source／chunk 做 enrichment。
3. current revision、binding、timeline、knowledge 和 visibility 必须在候选 limit 前过滤，或使用有硬上限的 refill；先 limit 再丢弃大量失效候选会造成 underfill。Dense／lexical 先只取有界 ID／score，合并后批量 enrichment，并为入选 anchor 单独取有界邻块，消除逐候选 `_source_is_current` N+1。
4. 无 active index／未授权／Provider 失败时的本地词面路径也必须先选有界 source，再读取正文和分块；禁止每次写作重新读取并评分整部小说。它仍只读当前权威，不建立第二份本地全文权威。
5. candidate limit 根据 `top_k`、RRF 和逐 corpus 配额派生并进入策略版本；不得通过过小固定值破坏 Recall@5／MRR 和相邻块扩展。
6. 在约 1,500／7,500 chunk 上记录冷／热查询计划、P50／P95、返回行、应用峰值和检索质量，同时分别覆盖 hybrid、indexed lexical 和 authority local lexical 三种模式。
7. current source replacement、retired／invalid source 和 active generation 隔离继续沿用现有不可变生命周期；清理只针对已证明无 current 引用的派生向量，不删除正文、账本、授权或历史 generation。
8. 正式内容增量 refresh 只处理变化 source；authority digest 改用可组合元数据或等价有界方案，current source／chunk／embedding 计数用数据库聚合，不把全书 ID 集合物化到 Python。全量重建只保留给模型空间／renderer／chunker generation 变化和作者显式 rebuild。
9. 只有精确扫描超过 G0 冻结的产品门槛，才重新核验 pgvector 0.8.6 对 2048 维索引的实际能力并提出窄索引方案；不能把半精度表达式、降维或换模型作为静默优化。

数据库裁决分三层：

| 项目 | 当前裁决 | 放行条件 |
| --- | --- | --- |
| PostgreSQL + pgvector、2048 Dense、cosine | 保留 | 现有底座能承载预计 chunk 数，暂无替换证据 |
| SQL 候选上限、scope／generation／current 过滤、增量发布和派生清理 | 必须优化 | W1 冻结策略后进入生产代码施工 |
| HNSW／IVFFlat、新建或替换 pg_trgm／全文 GIN、新辅助列 | 暂不批准 | G0 必须 A/B 精确 `similarity ORDER BY + LIMIT` 与可索引 trigram predicate + LIMIT；只有中文 Recall／MRR、EXPLAIN、P95 和内存共同放行，才接入现有或新增索引并完成隔离升级／回退验证 |
| 第二套向量数据库、降维或更换 embedding 模型 | 否决 | 只能由独立需求、迁移与质量计划重新立项 |

### 3.5 助手、搜索、revision 与导出

- 助手 workspace context 从数据库先选择有界文档／revision，再读取正文；40,000 字输出上限必须同时对应有界上游读取。
- 作品搜索先做 100 万／500 万字 `ILIKE` 基线。若查询计划或 P95 不通过，再裁决 pg_trgm／全文索引；结果片段在数据库或有界候选上生成，禁止先加载所有匹配正文。
- revision 列表只返回元数据，查看某一 revision 才读取正文。检查点和恢复继续保留不可变全文，不用性能优化删除历史。
- 全书导出是合法的 O(全书) 操作，但应流式或分批读取并显式显示进度；它不能和打开工作台、章节切换或生成上下文共用全量内存路径。

### 3.6 可观测性和失败语义

规模测试和运行诊断只记录：作品规模档、章节／事实／chunk 数、SQL 数、扫描／返回行、响应字节、上下文来源数、估算 token、耗时分位数、峰值内存和结构化错误。不得记录真实正文、完整 prompt、完整向量、密钥或来源摘录。

必须区分：

- `context_overflow`：必要作者输入超过真实模型窗口；
- `context_selection_incomplete`：权威选择策略无法在安全边界内证明完整；
- `context_source_stale`：选择与大字段 hydration 之间的 head／hash 漂移，有限重试后仍不一致；
- `prompt_budget_mismatch`：渲染后的 Prompt hash／token 与预算账本或发送前 guard 不一致；
- `retrieval_degraded`：Dense／lexical 派生检索降级但仍可写作；
- `workspace_page_stale`：导航游标或 manifest 版本过期；
- `provider_timeout`／`model_output_invalid`：外部模型失败。

前四类 Context／Prompt preflight 失败的 Provider 调用必须为 0，并且不得留下 running job、候选、revision、账本或 active embedding generation 变化。`retrieval_degraded` 只适用于可选派生检索；确定性 scope、timeline 或 fact authority 错误不得降级掩盖。

### 3.7 新小说直接默认开启的产品契约

1. 不新增工作区未来偏好表、全局 consent 或浏览器开关。产品固定行为是：active embedding 配置有效时，新小说创建事务同时创建自己的 `novel-embedding-consent/2` 记录，提交成功后异步请求增量索引。
2. 两个建书入口共用同一领域服务。索引等待、失败、Key 缺失或 Provider 故障不回滚小说创建，也不阻断本地写作；无法形成有效配置时云端请求为 0，前端显示本地路径／配置不可用。
3. 每书 consent 继续记录 Provider、model、notice、scopes、actor、授权和撤销时间；它是逐书外发审计，不是第二套账本。单书撤销不影响其他小说。
4. 现有未授权小说保持不变，不因为本计划上线而自动批量上传。作者可逐本启用；未来如需全部启用，另做精确预览和明确动作。
5. Provider、model、notice 或 scopes 改变时，既有逐书记录进入 `requires_reconsent`，不能静默授权新目标；新小说按创建当时有效配置生成自己的记录。
6. 同 notice 撤销后重新授权不再使用会命中旧撤销行的固定 key；CAS version 由现有 consent 历史记录派生，无需新增 version 列。
7. 删除派生向量与撤销授权保持两个动作：清理向量不改变授权，撤销授权也不删除正文、revision、StoryFact 或审计历史。

前端面向作者只显示以下稳定语义：

| 内部事实 | 作者可见文案 |
| --- | --- |
| Dense + lexical 正常完成 | `已使用向量增强查找相关内容` |
| 未授权、索引未就绪或未配置，但本地检索正常 | 检索阶段先显示 `已改用本地检索`；只有整次生成成功后才能组合 `本次写作已继续完成` |
| Provider 超时／网络失败后本地成功 | `向量服务暂不可用，检索阶段已自动改用本地路径`；不得提前宣称正文生成成功 |
| 检索完成但无合格命中 | `未找到额外相关片段；本次仍使用已纳入的写作上下文` |
| 语义检索异常且本地检索未实际执行 | `语义检索暂不可用；本次继续使用基础写作上下文`，mode 必须为 `context_only` 或冻结的等价值，不能伪报 `lexical_only` |
| 确定性 scope／timeline 无法建立 | 显示结构化错误并停止该次生成，不把安全边界错误伪装成普通降级 |

完整 `writing-retrieval-snapshot` 与 Context snapshot 继续留在服务端数据库／审计边界；内部 task record 和公开 HTTP projection 必须分离。所有创建、轮询、完成、失败和历史列表／详情响应剥离服务端注入的 `writing_retrieval`、`writing_context` 与完整 generation context，只派生脱敏的顶层 `retrieval_summary`，至少包含契约版本、outcome／mode、reason code 和 hit count。正文、章纲、审稿与适用选区操作共用这一摘要；前端不得接收 query 原文、完整 Prompt、向量、密钥、snippet 或私有素材摘录。

## 5. 验收矩阵

### 5.1 结构性硬门禁

无论绝对毫秒数如何，以下必须满足：

1. 作品 manifest／卷章页面不返回任一未选章节的 `content_markdown`。
2. 打开作品和翻页的正文大字段返回量不随全书字符数增长；选择章节只取得目标章节正文，不再随 manifest 重复。
3. `list_novels` 不装载所有 `DocumentWorkingCopy.content_markdown` 计算总字数。
4. 一次 Context V4 组装不读取全部章节正文、全部人物历史 revision 或全部 StoryFact；正文大字段／fact enrichment 返回数由冻结策略约束。
5. 最终 prompt 每个组成部分都在同一预算清单中，纳入 token 不超过当前有效窗口，任何超限在模型调用前结构化失败。
6. Dense／lexical 返回 Python 的候选数有界，最终结果不超过请求的 Top-K；无候选时仍可合法返回空或降级。
7. 分页／切章／切作品的迟到响应不能覆盖新状态，dirty 草稿和恢复稿不能因缓存淘汰丢失。
8. 模型、搜索、检索或上下文失败均不产生正式 revision、StoryFact 或 active generation 变化。
9. 当前 embedding 配置有效时，新小说必须具有自己的 consent 记录；配置无效时新书仍可创建且云端请求为 0。逐书撤销、配置不可用和 `requires_reconsent` 不得互相混淆。
10. 本地降级、indexed lexical 和 hybrid 三条路径都只向 Context 返回有界候选；同一 source／revision／range 不得同时以完整块和语义证据重复占用 Prompt 预算。
11. 正文生成、章纲、审稿和适用的选区操作完成后，前端必须能显示本次实际检索模式、降级或无命中状态；不得把“索引已配置”冒充“本次已使用向量”。
12. 普通单 source 变更后的 refresh 不读取其他章节正文，索引计数不向 Python 返回全书 source／chunk ID；全量 rebuild 必须是显式的独立动作。
13. brief／chapter requirements 在组件账本中只出现一次；V4 缺失不能回退到无统一预算的生产 Prompt，选择不完整和 Prompt guard 失败均有结构化错误，已创建 job 必须进入 terminal 状态。
14. 所有写作任务公开 HTTP projection 只能包含脱敏 `retrieval_summary`；创建、轮询、完成、失败、历史列表和详情响应均不得带出内部 retrieval/context snapshot、query、snippet 或 Prompt。

### 5.2 性能和内存门禁

G0 报告注明 CPU、内存、PostgreSQL／pgvector、容器和数据分布后冻结绝对阈值。发布至少记录：

- API：响应字节、SQL 数、扫描／返回行、P50／P95、峰值 RSS／tracemalloc；
- 浏览器：网络响应、解析／长任务、DOM 节点、可取得时的 heap、console 和水平溢出；
- Context：候选 source 数、实际读取正文行、fact 行、prompt 各组件 token、snapshot 序列化体积；
- Retrieval：约 1,500／7,500 chunk 的 EXPLAIN、冷／热 P50／P95、数据库返回行、Recall@5／MRR；
- 恢复：连续切章、自动保存冲突、页面重载、IndexedDB 恢复和 checkpoint／restore。

打开作品、切章和 Context 大字段装载的返回规模必须接近页大小／策略大小，而不是从 100 万到 500 万随正文增长约 5 倍。精确向量扫描允许数据库 CPU 随 chunk 数变化，但应用返回行和内存必须有界；是否需要进一步索引由实测延迟和质量共同裁决。

检索 SQL 证据统一使用 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`；Dense 返回行不得超过 frozen dense candidate cap，lexical 不得超过 frozen lexical cap，enrichment 不得超过两路 ID 并集加冻结邻块上界，并且逐候选 current-head N+1 为 0。capped 结果必须与同数据集未截断 exact oracle 比较，继续满足 Recall@5 ≥ 0.85、MRR ≥ 0.70、hybrid 不低于 lexical-only、无答案正确拒答率 ≥ 0.90、隔离泄漏为 0；W1 另冻结允许的 cap 相对质量回退。

### 5.3 真实 UI 标准

以后所有真实页面验收固定覆盖：

- 1920×1080；
- 2560×1440；
- 两档均测试 QwenPaw 左栏和原生助手的展开／折叠组合；
- 记录 Browser 目标 viewport 与实际截图内容面的差异，不把内嵌容器扣除像素伪称为精确截图尺寸；
- 窄屏／200% 等效路径作为补充自动化和可访问性诊断，不能替代 1080P／2K 实测。

500 万字合成作品必须验证卷章虚拟滚动、随机跳章、连续切换、搜索定位、返回列表、dirty 提示、恢复稿和无页面级横向溢出。

向量相关页面与正文生成链在 1920×1080、2560×1440 均覆盖：新书默认开启、现有小说保持原状态、单书启用／撤销、索引 building／ready／outdated／partial_failed、hybrid、本地正常降级、Provider 失败降级、无命中和 `requires_reconsent`。交互必须具备焦点圈、键盘操作和 `aria-live` 状态；助手展开后不得遮挡逐书状态或本次检索状态。

本次检索摘要若提供“管理索引”，目标深链冻结为 `/chat?novel_workbench=1&novel_id={N}&section=settings&settings_tab=semantic-index`。设置页必须消费并保留 `settings_tab`，四个设置 tab 使用 `tablist/tab/tabpanel`、`aria-selected`、`aria-controls` 和 roving tabindex；前进／后退、刷新和助手展开／折叠不得丢失当前 tab。实际 route 解析／序列化与设置 tab 状态由 `L52-FE-RETRIEVAL` 独占实现，`L52-FE-NAV` 和 `L52-INT` 不并行修改这些文件。

### 5.4 真实模型质量门禁

真实模型调用不是规模压测工具。获授权后只发送由新选择器生成的有界 prompt，至少验证：

- 能召回早期相关伏笔而不依赖整书输入；
- 当前人物／关系／知识状态正确；
- 不泄漏未来章节或兄弟时间线；
- prompt 来源和 omission 可复核；
- 输出仍进入候选审阅，不自动采用。

## 6. 冗余清理与兼容边界

替代完成后应及时清理：

- 第一方对重载 `/novels/{id}` full-tree 正文形态的调用；
- 只为整书正文树存在的前端 DTO、转换 helper、重复 selected-document 缓存和专用旧测试；

- Dense／lexical 全候选 `.all()` 后再裁剪的应用层路径。

删除前必须证明：新路径覆盖全部调用者；不是公开兼容窗口；不是恢复、负向或跨版本测试；不覆盖用户／其他计划未提交改动。删除后运行受影响回归、`rg` 调用者检查和 `git diff --check`。

不得以“长篇减重”为由删除：

- 用户 working copy、不可变 revision、checkpoint 或恢复稿；
- StoryFact、来源 binding、commit batch 和 inverse evidence；

- 已执行迁移和历史验收原始证据。

若未来需要 revision／embedding 的归档或保留策略，必须给出精确对象、备份、恢复、作者可见性和单独授权，不在本计划自动执行。
