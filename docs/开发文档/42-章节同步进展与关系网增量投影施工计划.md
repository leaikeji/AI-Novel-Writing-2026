## 1. 已核实问题

当前关系读取已经能把有效 `relationship_state` StoryFact 投影到关系卡，但章节同步的写入链存在三个断点：

1. 情报快照只把已经存在的 `CharacterRelationship` 放进 `relationship_catalog`；提示又要求 `relationship_state` 必须引用该目录。因此空关系网无法提出第一条关系，形成“没有关系 → 不能提关系 → 永远没有关系”的循环。
2. `sync_relationships_from_intelligence_proposal()` 已退化为只读兼容函数，明确不创建或更新关系实体。即使章节关系事实被确认，也不会补齐关系根。
3. 前端在模型结果出现后立即把全部候选提交，作者看到的是已写入结果，不是待确认候选。这与项目“模型只提案、作者结果后确认”的权威边界不一致。

关系网整书生成适合初始化或重建，不应成为每章关系演进的强制前置步骤。

## 2. 目标与非目标

### 2.1 本轮目标

- 每次作者点击“同步进展”，模型输入都包含人物目录、已有关系目录和本章正式正文。
- `relationship_state` 同时支持引用已有关系，或使用两个服务端人物短键提出第一条新关系。
- 模型结果先进入提案，默认不选择；作者勾选后点击“应用所选”才写入权威数据。
- 一次应用在同一事务中完成：关系根创建/复用、关系 revision、StoryFact v2、来源绑定、提交批次和账本版本递增。
- 人工关系定义优先。匹配到人工关系时只把本章事件挂到该关系，不改名称、分类、方向、描述或 `manual_override`。
- 提交响应返回关系网 `created / updated / skipped` 计数，章节结果页明确区分“待确认”和“已写入关系网”。
- 既有“生成关系网”保留为可选的全书初始化/重建工具，页面不再暗示它是章节同步前置条件。

### 2.2 非目标

- 不新增数据库表或 Alembic revision；复用现有 StoryFact v2、关系根/revision、提案、批次和来源绑定。
- 不把模型结果直接覆盖人物卡、关系人工定义或正式正文。
- 不在保存正文、采用正文或打开页面时静默调用模型。
- 不在本轮完成计划 27 的人物身份/性格/年龄/成长四维轨迹和完整撤销 UI。
- 不修改 QwenPaw 上游核心，不新增第二套模型选择器或任务队列。

## 3. 冻结契约

### 3.1 模型候选

已有关系候选继续使用 `entity_key = relationship_N`。新关系候选必须提供：

```json
{
  "fact_type": "relationship_state",
  "entity_key": "",
  "source_character_key": "character_1",
  "target_character_key": "character_2",
  "directionality": "directed|undirected",
  "relation_kind": "family|colleague|mentor|ally|enemy|romance|other",
  "relationship_label": "关系名称"
}
```

服务端只接受快照中的人物短键并解析人物根、人物实例与正文区间时间线；拒绝姓名定位、自造 UUID、同一人物两端、跨小说实体和非法枚举。新字段由模型规范化器显式保留，客户端 override 不能改写关系两端或关系定义。

### 3.2 原子提交

提交所选候选时按以下顺序执行，直到末尾才 `commit`：

1. 锁定 working copy、提案、Novel 和 proposal items，复核正式 revision/CAS。
2. 对已有关系复核小说范围、生命周期和快照身份；对新关系解析两端稳定 ID。
3. 若相同人物对、方向和分类只有一个现有关系，则复用它；人工关系只读优先。否则创建 `created_by=ai_auto / manual_override=false` 的关系根及首个 revision。
4. 把实际 `relationship_id` 写入待创建 StoryFact v2，创建来源绑定。
5. 提交批次记录创建的事实 ID、创建的关系 ID 和受影响关系 ID；账本有新增事实时只递增一次。
6. 返回 `relationship_sync` 计数。任一步失败整批回滚。

重复提交同一 commit key 返回原批次，不再次创建关系、事实、revision 或递增版本。

### 3.3 页面交互

“同步进展”的确认弹窗只授权调用模型并生成候选。模型完成后：

- 打开“同步进展候选”弹窗；每项有复选框，默认不选。
- 关系候选展示“已有关系更新”或“将新建关系”，并显示两端、关系名、分类、证据和置信度。
- 主按钮为“应用所选（N）”；N=0 时禁用。
- 提交成功后刷新同一提案，已确认项显示“已写入”；状态提示包含关系网新增/更新数。
- 关闭、刷新、取消或模型失败都不修改故事账本或关系网。

## 4. 数据一致性、恢复与兼容

- 旧提案和旧 StoryFact 保持可读，不猜测性回填新字段。
- 本轮不改 schema，回退代码无需降级迁移；停用/卸载 PawApp 后 QwenPaw 原生能力不受影响。
- 新建 AI 关系保留不可变 revision 和来源章节 revision；来源事实失效时，默认关系列表、关系图和 AI 关系计数不再展示这条仅由失效章节支持的增量关系，但 `include_archived=true` 仍可读取关系定义根供审计和后续章节复用。恢复原来源 revision 后关系自动重新显示。
- 人工编辑任一 AI 关系后沿用现有逻辑提升为 `manual_override=true`，后续章节事实只能更新投影，不能覆盖人工定义。
- 若候选中的已有关系在提交前已被归档或改成其他小说范围，提交失败并要求重新同步，不静默创建替代关系。

## 6. 子代理并行施工设计

本任务**不并行写代码**。原因是核心改动集中在 `backend/services.py`、`backend/model_runtime.py`、`frontend/src/chapter-workflow.ts` 和已包含用户现有 UI 改动的 `frontend/src/styles.ts`；事务契约、公共 DTO 与唯一长期浏览器也都是共享锁。拆分写入会增加关系字段漂移、覆盖用户改动和双事务回归风险。

唯一集成责任人是当前主代理。精确文件所有权：

- `RSP-CONTRACT`：`backend/model_runtime.py`、`backend/services.py` 的快照/提示/规范化区、相应测试。
- `RSP-TX`：`backend/services.py` 的提交区、必要的关系模型引用、`tests/test_domain_integration.py`。
- `RSP-UI`：`frontend/src/types.ts`、`frontend/src/chapter-intelligence.ts`、`frontend/src/chapter-workflow.ts`、相关测试；`frontend/src/styles.ts` 只追加本弹窗所需样式，保留当前未提交人物卡样式。
- `RSP-INT`：只读复核全仓；打包、热安装、浏览器和 Git 均由主代理串行执行。

禁止触碰：QwenPaw 核心、旧项目 `Data`、真实密钥、正式小说正文、未分配的用户改动、既有迁移历史。共享锁为 `LOCK-PUBLIC-CONTRACT`、`LOCK-SHARED-BACKEND`、`LOCK-USER-DIRTY-FILES`、`LOCK-TEST-DB`、`LOCK-LONG-RUNTIME`、`LOCK-BROWSER` 和 `LOCK-GIT`。

## 7. 验收清单

### 7.1 后端

- 空关系网 + 两个人物 + 一条新关系候选，确认后创建 1 个 AI 关系、1 条 relationship StoryFact、1 个来源绑定和 1 个提交批次。
- 同一提交幂等重放为 0 个额外关系/事实/revision，账本版本不重复递增。
- 第二章引用已有关系时不创建重复根，返回 `updated=1`，关系投影包含两章事件。
- 匹配人工关系时名称/分类/描述/version/manual_override 不被 AI 改写。
- 无效人物短键、同端点、非法方向/分类、跨小说/已归档关系整批零写入。
- 非关系候选原有提交、revision 失效/恢复和 StoryFact 投影回归通过。

### 7.2 前端

- 模型返回后尚未调用 commit；候选默认零选择。
- 单选、全选/取消、应用按钮计数、忙碌态、失败恢复和关闭重开正确。
- 关系候选明确显示新建/更新、关系名称、分类、两端、证据和置信度。
- 提交后显示已写入与关系网计数；无候选显示合法 `no_changes`，不伪装成失败。
- 桌面页面键盘可达、焦点和滚动正常；本轮按用户要求不以移动端尺寸作为产品验收门禁。
