## 1. 授权、问题与目标

作者在复查交互方案后于2026-09-12明确要求“开始实施”。本记录只处理章节正文生成的并发与恢复死锁，不扩大计划70的语义路由发布范围，不调用真实模型，不引入后台队列、第二套任务系统或数据库迁移。

已核实故障是：正文任务已经以`failed`结束，但对应受管写作动作保守停在`unknown`；客户端只看动作状态，导致再次点击立即报“原任务结果尚未确认”，既没有查询中的任务，也没有显式重试出口。

本轮目标：

- 同一章节任一时刻最多一个`running`正文任务；`force_new`不能绕过。
- 同一标签页重复操作复用原动作；跨标签页重复操作返回原任务，不进入模型、Skill目录或正文调用。
- `unknown + running`继续查询；`unknown + terminal/no body job`由服务端判定为`confirm_required`，作者确认后才能新建动作。
- 已知失败、取消、过期或已结束任务可重新生成；正式正文仍只在候选采用链中修改。
- UI只做现有按钮、状态卡和确认文案的轻量改动；不增加新页或任务中心。

## 2. 冻结契约与状态机

服务端响应新增非持久化`retry_policy`：

| decision | 含义 | 客户端行为 |
| --- | --- | --- |
| `blocked_active` | 章节仍有进行中任务或动作未终结 | 只查询/刷新原任务，不POST新生成 |
| `confirm_required` | 远端结果无法完全确认，但没有进行中正文任务 | 显示风险，作者明确确认后才POST新动作 |
| `allowed` | 原任务已经明确结束 | 允许正常重新生成 |

跨标签页并发命中返回HTTP 409、`type=chapter_generation_in_progress`、原`job`和`blocked_active`策略。该响应不是“新生成失败”，客户端不得显示失败弹窗。最终并发裁决位于服务层，以章节维度PostgreSQL事务 advisory lock 串行化；早期只读检查用于避免不必要的配置、检索和辅助路由，不能代替最终锁。

不新增持久字段。动作、dispatch、job、候选和正式正文的既有证据链不变；外部模型调用仍在任务快照提交后、数据库事务外执行。

## 4. 验收标准

- 两个并发`force_new`请求只有一个创建`running`job，另一个得到同一job的进行中结果。
- 已存在`running`job时，新受管动作在模型/目录/正文调用前退出。
- `unknown + failed job`恢复响应为`confirm_required`；无确认不发送，有确认才生成新action。
- 跨标签页409不会留下客户端幽灵ticket，不显示“章节正文生成失败”，按钮变为“查看生成进度”。
- 进行中状态只有一张靠近按钮的状态卡；刷新结束后可重新生成或打开候选历史。
- 所有失败路径不修改正式正文，不自动重放可能已计费的远端请求。
