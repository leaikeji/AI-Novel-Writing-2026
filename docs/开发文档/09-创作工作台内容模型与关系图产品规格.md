## 1. 决策摘要

如果启用完整创作工作台，本项目采用以下原则：

1. 卷、章、章纲、正文各有稳定 ID；改标题、移动分卷或重新排序不改变正文身份。
2. 章节创建与正文生成分离；空章节壳、手写正文、AI 候选正文是不同状态。
3. 保存正文只保存 working copy；发布 revision、调整分卷、提取情报必须是显式且可独立重试的动作。
4. 大纲重新生成只产生候选版本和 Diff，不直接覆盖正式大纲、角色、章节或设定。
5. AI 提取角色、关系、线路事件和伏笔时先形成 `intelligence_extraction_proposal`，作者逐项采用后才改变正式数据。
6. 所有提取项绑定来源 `chapter_revision_id`、文本范围、模型任务、置信度和输入哈希。
7. 同一章节 revision 的重复同步必须幂等；正文产生新 revision 后才能创建新的提取提案。
8. 角色匹配使用稳定 ID 与显式合并流程，不能只按姓名静默新增或覆盖。
9. 关系图把“关系语义”和“画布布局”分离；节点拖动不改变角色，布局只有显式保存才持久化。
10. 关系线必须明确有向/无向；视觉箭头、编辑器文案和数据语义保持一致。
11. 线路和事件都是一等实体；事件支持编辑、移动、重新分类、合并、删除和恢复。
12. “感情线”不能充当所有人物关系的兜底分类；项目使用可配置的线路类型。
13. 伏笔是有生命周期的叙事承诺，进展以追加记录保存，不用一个可覆盖文本框充当历史。
14. 模板快照、当前故事设定、正式大纲和正文事实分层；冲突要提示，不自动决定哪一份为真。
15. 本项目不建设计费或额度系统；AI 操作只需要稳定任务、幂等、进度、取消和错误恢复。
16. “正文已生成”“生成历史已记录”“情报已提取”和“正文已采用”是四种不同状态；界面必须逐一说明，不能用一个模糊的“已更新”代替。
17. AI 写回线路、关系、角色和伏笔前先做实体解析；近义名称、别名和同来源上下文必须进入合并候选，不能默认新增。
18. 删除或恢复章节时，所有来源派生数据必须事务化失效或恢复；不能让用户手工寻找并删除孤儿角色记忆和线路事件。
19. 编辑器、章节树、作品卡和导出使用同一个可见正文计数器；生成服务的原始长度只作为内部诊断。
20. 角色/线路选择是生成约束，必须明确 hard/soft；模型引用未选实体或把选中线路写到另一线路时要在采用前报告。
21. 历史恢复必须建立新的当前 revision，并事务化更新派生数据有效性；不能只替换编辑器和本章情报，再把旧情报重复追加到全局账本。
22. 手写稿与 AI 候选使用同一 revision 体系；工作稿保存必须做乐观并发控制，并有可跨刷新和标签关闭恢复的本地草稿。
23. 作品、分卷和章节聚合统计由同一权威查询或同一事务维护；章节归档/删除后不得留下分卷幽灵计数。
24. 本章与全书搜索必须返回稳定卷章定位和上下文；批量替换先生成 Diff 提案，作者确认后才建立 revisions。
25. 正/倒序查看是本地视图偏好，真实章节排序是带乐观锁的独立命令；两者不能共用同一个箭头状态。
26. 跨卷移动和批量移动必须原子完成，不能要求“先移出、再添加”而暴露中间未分卷状态。
27. “复制正文”“复制章节”和“保存并新建下一章”是三种独立生产力操作，连续写作不强迫返回列表。
28. 全书导出固定到一组明确 revisions，保留卷章边界、空章策略、顺序和哈希；视图排序不得影响导出，且本工具应能重新导入自己的结构化导出。
29. A→B 与 B→A 是两个可并存的有向关系；同一角色对多边必须分 lane 显示并提供角色对关系清单，不能让标签重叠后只能猜测点击。
30. 角色列表必须直接提供入边、出边和关系 CRUD；只有 Canvas 节点能打开关系表单视为功能缺失。
31. 关系图提供搜索、聚焦、适应画布、过滤、自动排布、布局 dirty/保存/重置和可访问镜像树；子视图进入可恢复路由状态。
32. 角色删除默认软归档，并先生成带精确引用数量和处理策略的影响预览；已有正文或故事账本引用时禁止直接硬删除。
33. 工作台的作者体验验收使用连续剧情、真实角色动机和可追踪伏笔；最小探针只验证计数、并发、导出等结构行为，不进入正式作品的可见命名和正文。
34. 角色选择的语义必须显式标注 `required / allowed / context_only / forbidden`；“禁止新增角色”只约束新实体，不能冒充既有角色出场白名单。
35. 章节壳创建时一次确定可选目标分卷；正文保存不得再次弹分卷选择，更不能把移动分卷当成保存的必经步骤。
36. 候选正文、当前标签临时稿、云端 working copy 和正式 revision 分别显示状态；页面可见字数不能让作者误以为新标签已能读取。
37. 情报复核必须逐项采用；调查、线索交换、同盟和对立全部被模型建议为 romance 时，作者应能批量改为 relationship/mystery，而不是只能整包保存或取消。
38. 取消情报采用可以保留审计候选，但全局故事账本逐项不变；状态名使用“候选已生成 / 未采用”，不使用含混的“已更新”。
39. 章节向导新建伏笔和全局伏笔编辑器使用同一写入协议；名称、内容、状态与初始进展必须一起持久化，不能在第二个入口丢失进展。
40. `target_word_count` 是章节壳的单一字段；向导确认、修改章纲、重生成和正文任务必须读取同一值，不能在后续表单悄悄回落到默认值。
41. 内容策略拦截只把生成 job 标为 failed，并返回可定位的问题范围和安全改写建议；失败任务不得创建正文候选、角色记忆、关系、线路或伏笔。
42. 任何人工改稿都会改变正文哈希并使旧情报提案进入 `source_superseded`；页面不得继续把旧提取显示成“本章情报”而不警告。
43. 作者显式“建立检查点/正式保存”永远建立可恢复 revision；“AI 生成历史”可以记录成功或失败候选，但不能遗漏最终人工稿并成为唯一恢复入口。
44. 正文保存、候选生成和情报同步都不能绕过复核页自动新建全局伏笔；所有派生写入都必须有可审计 proposal item 和作者采用动作。
45. 长篇审稿读取章序、前文摘要、角色、设定和当前 revision，并把每条建议绑定到精确文本范围与可选 Diff；第五章不能被当作独立开篇评价。

## 2. 范围与非阻塞边界

本文覆盖：

- 卷章树和章节编辑生命周期。
- 章节章纲向导。
- 大纲编辑与重新生成。
- 角色资料和关系图。
- 线路、事件与章节进展同步。
- 作品设定和伏笔管理。

本文不覆盖：

- 不做平台投稿、审核、签约和收费。
- 多作者实时协作。
- 自动连续生成数百章正文。
- 无审核地把模型输出写入正式故事账本。
- 不复制竞品视觉、文案、价格或私有接口。

核心 MVP 仍可只实现手动建书、卷章树、编辑器、自动保存、revision、AI 候选 Diff 和历史恢复。完整关系网、自动线路提取与伏笔联动属于可独立裁剪的扩展包。

## 4. 领域模型

### 4.1 卷、章与正文

`volumes`：

- id、novel_id、title。
- position_key：支持稳定排序，避免每次拖动改写整卷序号。
- created_at、updated_at、archived_at。
- expected_version：编辑和排序的乐观锁版本。

`chapters`：

- id、novel_id、volume_id 可空。
- title、position_key。
- lifecycle_state：shell、drafting、has_content、archived。
- outline_document_id 可空。
- body_document_id。
- target_word_count 可空。
- created_at、updated_at、archived_at。
- expected_version：标题、归属和生命周期命令的乐观锁版本。

正文沿用 `document_working_copies` 和不可变 `document_revisions`。working copy 至少保存 `base_revision_id`、`expected_version`、`content_hash`、`updated_by_session_id` 和 `updated_at`；旧标签基于过期版本保存时返回冲突，不能 last-write-wins。章节标题不进入正文 Markdown，也不计入“正文字数”。统计至少分成 `body_visible_character_count` 和内部可选的 `body_storage_character_count`：前者按统一规范排除 Markdown 标记与换行等非可见字符，作为作者看到的作品字数；后者只用于存储诊断，不能混入同一个 UI 数字。标题字符数可单独展示，但不与正文总数混算。

`chapter_generation_jobs`：

- id、chapter_id、kind：outline 或 body。
- source_revision_ids、input_hash、model_profile_fingerprint、idempotency_key。
- target_word_count、selected_storyline_ids、selected_character_ids、selected_foreshadow_ids。
- allow_new_characters、allow_character_exit。
- selection_policy_json：每组选择是 hard allowlist、required、preferred 还是 context_only。
- creative_asset_snapshot_ids、generation_context_snapshot_id。
- expectation_text。
- state、stream_checkpoint、result_document_proposal_id、constraint_validation_report_id。
- failure_kind、failure_ranges_json、safe_rewrite_suggestions_json：内容策略或模型失败的可定位诊断；不保存敏感规则细节，但必须让作者知道改哪一段。

AI 章纲和 AI 正文是两个不同 job。生成结果只能成为候选 document revision。章节壳创建时固化 `target_word_count`；修改章纲只显式修改该字段，所有后续 job 通过 chapter_id 读取同一当前值，不从表单默认值重新推断。

### 4.2 大纲与作品设定

大纲 section 沿用类型化 document：

- story_background。
- main_plot。
- theme_highlights。
- synopsis。
- optional_pitch。

`novel_setting_snapshots`：建书时使用的模板、动态字段和创作思路不可变快照。

`novel_story_settings`：作者当前可编辑的故事设定；字段带 schema_id、schema_version、working copy 和 revisions。

模板快照解释“作品如何被创建”，当前设定表达“现在的创作约束”。两者不能共用一条可覆盖 JSON。

### 4.3 角色与关系

`characters`：

- id、novel_id、canonical_name、display_name。
- role_level：protagonist、major、supporting。
- gender_text、age_text、identity、personality、biography。
- lifecycle_state：active、inactive、exited、merged、archived。
- merged_into_character_id 可空。
- current_revision_id。

`character_aliases`：

- character_id、alias_text、normalized_alias、source_revision_id。
- 同小说内 `(normalized_alias, active)` 唯一性只做候选提示，不自动合并同名人物。

`character_relationships`：

- id、novel_id、source_character_id、target_character_id。
- directionality：directed 或 undirected。
- relation_kind：亲属、同事、师徒、盟友、敌对、情感、其他，可扩展。
- label、description。
- current_revision_id、created_by、archived_at。
- 无向关系必须用规范化端点唯一键，防止 A—B 与 B—A 重复。
- 有向关系的反向端点是另一条合法边；完全相同 source、target、relation_kind、规范化 label 和 active revision 的重复创建返回合并候选。
- relation_pair_key：按规范化端点生成，供同角色对多边分组；不改变有向 source/target 语义。

`relationship_graph_views`：

- id、novel_id、owner_profile_id、name。
- zoom、pan_x、pan_y、layout_algorithm、layout_version。
- `relationship_graph_positions`：view_id、character_id、x、y、pinned。
- `relationship_graph_edge_lanes`：view_id、relationship_id、lane_index、curve_direction、label_offset。

关系语义和布局分表。默认拖动仅修改浏览器视图；只有点击“保存布局”才以 CAS 写入 view。页面还需“自动排布”“适应画布”“重置未保存布局”。

`character_retirement_plans` 在角色归档/合并前固化影响预览：character_id、expected_character_revision、relationship_ids、chapter_reference_counts、storyline_event_ids、outline_reference_ranges、foreshadow_ids、memory_ids 和每类处理策略。确认提交时再次校验引用图版本；预览过期则重新生成，不能按旧清单删除新引用。

### 4.4 线路与事件

`storyline_types`：项目默认提供 main、subplot、relationship、romance、faction、mystery，可由作品配置；“人物关系线”和“感情线”必须分开。

`storylines`：

- id、novel_id、type_id、title、description。
- status：planned、active、paused、resolved、abandoned。
- owner_character_ids 或 faction_ids 可选。
- position_key、current_revision_id、archived_at。

`storyline_events`：

- id、storyline_id、title、description、event_kind。
- source_chapter_revision_id、source_start、source_end。
- sequence_key、status、confidence。
- created_by：manual、ai_proposal、import。
- current_revision_id、archived_at。

事件允许：

- 直接编辑标题和描述。
- 移到另一条线路。
- 更改线路类型。
- 合并重复线路或事件。
- 查看来源正文与产生它的模型任务。
- 软删除和恢复。

### 4.5 伏笔

`foreshadows`：

- id、novel_id、name、description。
- status：planned、planted、developing、resolved、abandoned。
- planted_chapter_revision_id、planned_resolution_chapter_id 可空。
- resolved_chapter_revision_id 可空。
- importance、current_revision_id、archived_at。

`foreshadow_progress_entries`：

- id、foreshadow_id、chapter_revision_id 可空。
- note、event_time、created_by、proposal_item_id 可空。
- created_at、archived_at。

最新进展由进展记录按时间派生，不覆盖旧进展。标记已解决必须保留埋设、推进、回收链，并允许重新打开。

### 4.6 章节情报提案

`intelligence_extraction_proposals`：

- id、novel_id、chapter_id、chapter_revision_id。
- input_hash、model_task_id、model_profile_fingerprint、idempotency_key。
- state：queued、running、ready、partially_accepted、accepted、rejected、superseded、failed。
- created_at、reviewed_at、last_error。

`intelligence_proposal_items`：

- id、proposal_id、item_type。
- suggested_payload_json。
- matched_entity_id 可空、match_candidates_json。
- confidence、source_start、source_end、reasoning_summary。
- review_state：pending、accepted、edited_and_accepted、rejected、conflicted。
- committed_entity_type、committed_entity_id 可空。

项目不使用一次按钮同时不可逆写入角色、关系、线路和伏笔。复核页允许逐项勾选、编辑、重新分类、匹配现有实体，并在提交前展示精确变更集。

`intelligence_commit_batches`：

- id、proposal_id、chapter_revision_id、commit_key。
- state：committing、committed、reverted、failed。
- accepted_item_ids_json、inverse_operations_json。
- committed_at、reverted_at、expected_story_ledger_version。

`derived_source_bindings`：

- derived_entity_type、derived_entity_id。
- source_chapter_id、source_chapter_revision_id、proposal_item_id。
- validity_state：current、source_superseded、source_archived、source_restored、detached。
- invalidated_at、restored_at。

线路事件、角色记忆、关系变化和伏笔进展都必须绑定来源。章节归档不硬删派生项，而是把 binding 标为 `source_archived` 并从“当前故事事实”查询中排除；恢复同一 revision 时可恢复有效性，恢复其他 revision 时要求重新比较。

### 4.7 搜索、批量编辑与导出清单

正文搜索索引只索引作者可见正文与可选标题字段，并保存 novel_id、volume_id、chapter_id、chapter_revision_id、文本范围和索引版本。搜索结果跳转到稳定 chapter_id 和 revision 上下文；working copy 比索引新时要显示“结果可能过期”并允许仅在当前工作稿内搜索。

全书替换先建立 `bulk_text_change_proposal`：

- id、novel_id、query、replacement、scope、base_tree_version。
- 每个 item 保存 chapter_id、base_revision_id、命中范围、前后摘要和 proposed_content_hash。
- state：preview、partially_selected、committing、committed、conflicted、cancelled。

作者逐章勾选并查看 Diff 后，服务端对所有选中章节做 revision CAS。任一基线变化时默认整体停止并返回冲突清单，不静默替换新稿。

`novel_export_manifests`：

- id、novel_id、format：txt、markdown、bundle。
- tree_version、view_sort_ignored=true、empty_chapter_policy。
- state：preparing、ready、partially_failed、failed、expired。
- encoding、content_hash、file_ref、created_at、expires_at。

`novel_export_items` 按权威 position_key 固化 volume_id/title/position、chapter_id/title/position、chapter_revision_id、body_hash、visible_character_count 和导出状态。导出过程中新保存的章节只能进入下一次 manifest，不能形成半新半旧文件。

可重新导入的 bundle 至少包含 UTF-8 正文文件和 JSON manifest；文本边界使用显式、转义安全的稳定标记，而不是只依靠“第 N 章”自然语言标题猜分章。

## 5. 卷章树产品规格

### 5.1 分卷

P0 操作：新增、重命名、排序、归档、恢复。真正删除只能针对空卷，且二次确认；有章节时必须先移动章节或选择归档。

卷名由前后端共享 schema 校验。建议默认最大 100 个 Unicode 字素；服务端是权威，不能只依赖浏览器 `maxlength`。

移动章节使用独立命令，不与正文保存绑定：

```text
move_chapter(chapter_id, target_volume_id, before_chapter_id, expected_tree_version)
```

### 5.2 创建章节

最小创建只需要 novel_id、可选 volume_id 和可选 title，先得到稳定 chapter_id 与空 body document。作者可立即手写，不必完成 AI 向导。

AI 章纲路径的推荐步骤：

1. 选择待推进线路和事件。
2. 选择必需/可选角色；模型建议和作者选择分开显示。
3. 选择已有伏笔或新增伏笔候选。
4. 填写本章期望与禁区。
5. 设置目标正文范围。
6. 启动可恢复的章纲生成任务。
7. 预览、编辑章纲候选。
8. 采用章纲到章节 outline document。

要求：

- 没有线路时允许继续，不制造虚假“主线”实体。
- “允许新增角色/安排退场”默认关闭；开启后也只产生情报候选。
- 目标字数规则在创建和后续编辑中使用同一服务端配置。
- 标题和章纲内部标题只保留一个权威字段；生成文本不重复嵌入标题。
- 创建确认页明确说明只会创建章纲还是还会生成正文。

### 5.3 编辑和保存

正文输入流程沿用：浏览器内存 → IndexedDB → PostgreSQL working copy。保存 working copy 不执行以下动作：

- 重新选择分卷。
- 更新正式角色记忆。
- 删除退场角色信息。
- 生成线路或伏笔。
- 创建正式 revision。

作者显式“建立检查点”或触发 AI 前保存屏障时才建立 revision。情报同步只读取不可变 revision，避免在分析过程中正文变化。

竞品真实章节暴露的反例是“保存 → 再选分卷 → 再确认同步角色记忆和最新进展”。只完成前一两步时，当前标签显示 1853 字，新标签仍显示 0 字；全部确认后才落库。本项目拒绝这种多义提交：working-copy 保存、移动章节、建立 revision、生成情报提案和采用情报必须拥有独立按钮、独立命令 ID、独立成功状态和独立重试。

本地草稿和并发协议：

1. 编辑后按防抖把正文、标题、`base_revision_id`、服务端 working-copy version、内容哈希和本地时间写入 IndexedDB；不能只等待作者点“保存”。
2. 页面重开时比较本地草稿、服务端 working copy 和基线 revision。存在差异则展示正文 Diff、两个时间和来源设备/会话，允许恢复、另存为检查点或丢弃。
3. 服务端保存使用 `If-Match` 或请求体 `expected_version`。版本过期返回 `409 working_copy_conflict`，同时返回基线摘要和当前服务端 version；保留本地全文，不自动覆盖。
4. 同浏览器标签页使用 BroadcastChannel 或等价事件广播新 version。后台标签收到后立即显示“服务器已有新稿”，但最终正确性仍由服务端 CAS 保证。
5. 站内跳转的 dirty guard 只负责提醒；刷新、崩溃和标签关闭的恢复依赖已经落盘的本地草稿，不能依赖不可靠的 beforeunload 弹窗。
6. “保存后离开”和普通“保存”调用同一 working-copy command；成功后再执行目标导航，不切换路由格式、不使用原生 alert。
7. 当前标签中的 AI 候选或本地工作稿必须显示耐久级别：`仅本页 / 已写本地草稿 / 已保存云端工作稿 / 已建立正式 revision`；跨标签读取结果与该标识一致。

手写检查点、已采用 AI 候选和历史恢复建立的新 revision 出现在同一历史时间线，并明确标注来源。AI “生成历史”可以作为候选筛选视图，但不能替代正文 revision 历史。

真实第 4 章中，AI 原稿和人工修订稿都进入“生成历史”，却没有来源标签；历史字数分别为 2011/1880，编辑器对应显示 1969/1853，历史“伏笔 4”也只是章内候选而非全局已采用数量。因此历史项还必须保存并展示 `source_kind`、权威可见字数、候选/working-copy/revision 状态，以及情报 `proposed_count / accepted_count`，不能只显示一个含混的“伏笔 N”。

真实第 5 章暴露了相反且更危险的情况：生成历史只保留一次失败任务和 2870 字 AI 原稿，1782 字人工正式稿没有形成历史项。唯一可恢复的成功项反而含有错误年份和人物事实。由此不能把竞品“生成历史”当作稳定 revision 机制；作者点击显式“建立检查点/正式保存”时必须无条件写入统一正文历史，失败 AI job 只能留在候选任务日志。

第 5 章还固定了统一计数用例：章节页 1782 字、作品聚合增加 1832 字、DOM `innerText` 1833。权威 `body_visible_character_count` 必须在保存时由同一库计算并随 revision 固化；所有页面读取该值，不在客户端、章节服务和聚合任务中分别计算。

### 5.4 章节状态与工具可见性

```text
shell
  -> drafting
  -> has_content
  -> archived

任何有正文状态
  -> create_checkpoint
  -> request_outline_proposal / request_body_proposal / request_intelligence_proposal
```

重新生成正文必须产生候选全文和 Diff。当前正文不清空，只有用户接受候选后才创建新 revision。

正文生成的 UI 状态至少显示：

```text
generation_job: running / complete / failed
candidate: none / ready / rejected / adopted
working_copy: saved / saving / dirty / save_failed
intelligence: none / extracting / ready_for_review / committed / stale
```

候选流式完成时不能把 working copy 标成“有未保存修改”，除非作者已经明确点击采用。历史卡记录生成候选不等于正文已经保存；提取任务也只能读取被采用后的不可变 revision。

### 5.5 历史恢复与故事账本切换

选择历史 revision 时先进入恢复预览，不立即覆盖当前工作稿。预览必须显示：

- 当前 revision、目标 revision 和正文 Diff。
- 将从当前故事查询中失效的角色状态、关系、事件和伏笔进展。
- 目标 revision 已采用且可重新生效的 commit batches。
- 只存在于历史版本、继续保留审计但不再作为当前事实的项目。
- 尚未保存的 working copy 及其处理方式。

作者确认后，用一个 restoration command 建立新 revision 或切换当前指针，并在同一事务更新 `derived_source_bindings`。恢复历史正文不能自动重新提交旧 proposal；若作者选择重新采用目标 revision 的既有情报，服务端必须复用原 commit batch 或创建带唯一来源键的 reactivation，不能追加第二套相同事件。

恢复是可审计、可再次恢复的版本动作，界面不能一边宣称“不可撤销”，一边仍保留可恢复的较新版本。恢复完成后，正文、角色当前状态和默认故事账本必须指向同一有效 revision 链。

### 5.6 归档、删除与恢复章节

默认操作是软归档：

1. 展示章节、正文 revisions、生成候选、情报采用批次和所有派生项数量。
2. 作者选择只归档章节，或同时回滚某个情报 commit batch。
3. 同一事务更新章节状态和 derived_source_bindings。
4. 全局故事账本查询立即排除来源已归档的派生项。
5. 恢复章节时展示将重新生效的派生项；来源 revision 不同则保持失效并要求重新提取。

只有没有正文 revision、没有生成候选、没有采用情报的空章节壳可以直接硬删除。硬删除仍需二次确认和幂等键。

作品总章数、总字数和各分卷章数必须来自同一未归档章节集合。可实时聚合，也可在同一数据库事务更新物化计数；禁止分别成功。归档、恢复、移动和允许的硬删除都要在事务提交前校验：`novel.chapter_count = Σ volume/unassigned active chapters`，且每个 `volume.chapter_count` 与实际列表一致。

### 5.7 搜索、连续创作、排序与导出

编辑器 P0 提供本章查找/替换，全书搜索页提供跨卷章结果。替换操作绝不直接批量写库：先显示命中数、章节数、每条前后文和 Diff，再让作者选择本章、选中项或全部合规项。正文发生变化时提案标记冲突并重新预览。

生产力动词必须精确：

- “复制正文”只写剪贴板，并显示是否包含标题。
- “复制章节”创建新的章节壳和正文候选，默认不复制派生情报，先展示会复制的章纲/正文/标签。
- “保存并新建下一章”先完成 working-copy CAS；保存失败则不创建下一章。
- 上一章/下一章按权威 position_key 导航，不按当前倒序视图偷换方向。

章节树提供两个分离控件：

- 浏览排序：正序/倒序，只是用户本地视图偏好，可选择是否跨设备同步。
- 真实重排：拖拽或键盘上移/下移，预览新 position_key 后显式保存；使用 expected_tree_version。

批量移动和跨卷移动使用单事务命令，提交后章节不会短暂进入“未分卷”。键盘和屏幕阅读器用户可通过复选框、范围选择和目标卷下拉完成同一操作，不依赖拖拽。

导出页在执行前展示格式、范围、空章策略、卷章顺序、固定 revision 时间和预计文件清单。TXT/Markdown 均保留卷名与章名；bundle 额外保留 manifest 和哈希用于可靠回导。导出使用权威顺序，忽略正/倒序浏览状态。空章可以“包含并标记”或“跳过并列入报告”，不得静默处理。

## 6. 大纲编辑与重新生成

已有大纲点击“重新规划”前展示：

- 当前各 section revision。
- 将使用的章节、角色、设定和模板快照。
- 生成范围、会使用的上下文和可能被标记为冲突的实体。
- 不会被自动修改的模块。

生成完成后展示新旧差异，并按 section 独立选择：保留当前、采用候选、人工合并。角色建议进入单独的实体匹配页：

| 候选状态 | 作者选择 |
| --- | --- |
| 姓名和别名明确匹配 | 更新候选 / 保留当前 / 新建 |
| 同名但资料冲突 | 合并字段 / 新建另一人 / 跳过 |
| 候选角色被正文稳定引用 | 不得直接删除，只能标记 inactive 或替换引用 |
| 当前角色不在新大纲 | 保留 / 标记暂不使用 / 归档；默认保留 |

大纲采用后不重写现有章节。系统执行一致性扫描并报告：未解析角色名、设定冲突、目标数字冲突和已写章节与新主情节的偏差，但不自动改正文。

## 7. 角色列表和关系图交互

### 7.1 列表是关系图的无障碍替代视图

Canvas 不能成为唯一操作入口。同一数据必须提供可键盘操作的表格/列表：

- 角色名称、层级、身份、关系数。
- 展开后列出方向、目标、关系类型、标签和描述。
- 新增、编辑、归档与合并都能在列表完成。
- 搜索角色后可展开其全部入边/出边，按关系类型、方向和状态过滤，并能聚焦相同 Canvas 节点。
- 反转方向、拆分双向、合并为无向和同角色对多边管理都能在列表完成。

Canvas 节点提供屏幕阅读器可访问的镜像控件或隐藏列表，并支持 Tab 聚焦、Enter 打开、方向键移动选中节点、`+/-` 缩放。

### 7.2 图形交互

- 单击节点：选择角色并打开侧栏。
- 拖动节点：修改当前视图坐标，边实时跟随。
- 单击边或标签：打开关系编辑器。
- 双指/滚轮：围绕指针缩放，限制合理最小/最大值。
- 拖动空白：平移画布。
- 双击空白或工具栏：适应全部节点。
- 保存布局：显式持久化个人视图。
- 重置布局：恢复自动排布，不删除关系。
- 搜索与聚焦：按名称/别名定位节点并将其移到视口中心。
- 关系过滤：按类型、方向、状态、角色组隐藏或高亮边。
- 同角色对多边：使用稳定 lane/曲率和标签避让；点击任一边也能打开该角色对的完整关系抽屉。

视图显示当前缩放比例和未保存布局标志。关系编辑器中“有向/无向”使用单选或开关，并立即改变预览箭头；不能用“未勾选单向 + 仍显示箭头”的模糊表达。

`/relationships` 子视图、选中角色、过滤条件和可选 view_id 进入 URL 查询参数或同等可恢复导航状态。刷新可以重新自动排布未保存布局，但不能无提示跳回角色列表并丢失当前任务入口。

## 8. 章节进展同步与线索编辑

### 8.1 提取流程

```text
作者建立章节 revision
  -> 幂等启动提取任务
  -> 返回逐项候选：
       角色新增/更新/退场
       角色关系
       线路新增/匹配
       线路事件
       伏笔新增/推进/解决
       设定或事实候选
  -> 作者逐项编辑、分类、匹配和拒绝
  -> 预览提交变更
  -> 单事务幂等采用
```

提取页始终显示 `source_revision_id`、正文哈希和当前正文是否仍匹配。作者继续编辑或建立新 revision 后，旧 proposal 立即标为“基于旧稿”，不能继续以无警告的“本章情报”展示，更不能在随后保存正文时自动采用。

### 8.2 幂等与重复防护

唯一键至少覆盖 `(chapter_revision_id, extractor_profile_fingerprint)`。同一 revision 重复点击：

- running：返回同一任务。
- ready：返回同一提案。
- accepted：打开已采用结果，不再新增事件。
- 模型或提取规则确需重跑：创建带 parent_proposal_id 的新提案，仍需人工比较。

采用时每个 item 使用稳定 commit key；网络重试不得重复创建角色、线路、事件或伏笔进展。

正文保存与情报采用没有隐式级联。即使生成阶段已经提取出“新增伏笔”，它也只存在于 proposal；作者取消同步或尚未复核时，全局伏笔数量必须保持不变。

### 8.3 匹配与分类

角色匹配综合稳定别名、已知关系、身份和来源上下文，显示候选置信度，但最终由作者决定。无法匹配时可：新建完整资料、绑定已有角色、暂存未知角色、拒绝。

分类器只提供建议。复核页可把“同事/师徒”改为 relationship，把真正恋爱叙事改为 romance；也允许把漏掉的事件新建到 main。线路类型必须可编辑，不由模型输出锁死。

线路匹配还必须计算近义候选：规范化标题、参与角色、类型、最近事件和来源章节共同参与。出现“周晓琳的追查线”与“沈砚与周晓琳的追查线”这类高相似项时，默认动作是追加到已有线路；新建必须由作者显式选择。人物亲属关系不能因为包含“线”而默认成为 subplot。

真实第 4 章提取把“同盟线、调查线、线索交换线、长期对立线”四项全部归到“感情线”，还把已有无向“共同记忆锚点”重新建议为单向关系。这不是低概率边角问题，而是分类器和实体匹配同时失效。复核页至少提供：按列批量改类型、按已有关系端点和方向匹配、合并/新建对比、来源句定位、置信度、拒绝理由，以及“除真正恋爱叙事外不得批量默认 romance”的规则校验。

真实第 5 章进一步确认：人工改稿并正式保存后，旧情报仍描述 AI 原稿；显式重新同步虽读到新正文，却继续把“林默与郭晓霞的信任线”归为 romance、把已有无向“共同记忆锚点”建议成同名单向关系，并把一段录音同时拆成“已解决警告”和“新增录音机异常”。因此提取前必须先做正文哈希校验，提取后必须先做方向、类型和实体去重校验；发现同来源、同参与者、同语义的冲突项时默认阻止整批一键采用，但仍允许作者逐项修正后提交。

“下一章必现角色”也只是建议项，不是模型可直接写入的硬约束。若提取结果遗漏当前主角却选中两名配角，页面必须允许增删和降级为 preferred；下一章生成任务只读取作者确认后的约束集合。

### 8.4 直接编辑

全局线路页支持：

- 新建线路和手工事件。
- 编辑标题、描述、类型、状态与排序。
- 修改来源引用时保留审计记录。
- 将事件移动到另一线路。
- 合并重复线路，保留旧 ID 重定向。
- 删除进入回收站；恢复时检测目标线路是否仍存在。

修改章节正文不会静默改写已经采用的事件。系统标记来源 revision 已非当前，并提供“重新提取与比较”。

## 9. 设定、事实与伏笔的权威边界

权威层次：

```text
建书模板快照（只解释初始输入）
  -> 当前故事设定 revisions（作者主动维护的规则）
  -> 正式大纲 revisions（规划）
  -> 章节正文 revisions（故事实际发生）
  -> 带来源的事实/线路/伏笔派生数据
```

较下层不自动覆盖较上层，较上层也不能篡改已写正文。发生冲突时产生报告，例如：

- 设定写 4:44，大纲写天亮。
- 设定写 37 个锚点，大纲写 38 个。
- 正文引用不存在的角色。
- 伏笔标为解决，但来源章节已经恢复到未解决版本。

作者可以选择更新设定、修订大纲、建立正文提案或接受“有意矛盾”。决定本身进入审计记录。

伏笔的所有创建入口调用同一 command。章节向导中的“+ 添加伏笔”可以同时创建实体与第一条 `foreshadow_progress_entry`；全局伏笔页必须立即读到相同进展。若任一子写入失败，整次创建回滚或返回可重试的部分失败计划，不能表现为“伏笔卡存在、初始进展为空”。后续编辑默认追加进展；修改既有进展必须明确选择某一条记录并保留 revision。

真实第 5 章同时出现了两个反例：向导明确填写的“张子涵的注销单”初始进展在向导卡和全局页都为空；作者取消显式同步后，全局页却已出现 AI 提取的“林启年的录音警告”。本项目因此禁止两种不对称写入：作者直接创建的伏笔不得丢子记录，AI 提取的伏笔不得绕过 proposal 自动落库。两者都必须经过同一事务、来源绑定和审计事件。

## 10. AI 任务、取消和权限

- 生成章纲、生成正文、重生成大纲和同步情报分别创建稳定 job。
- job 保存输入哈希、模型配置 fingerprint、状态、流检查点、结果哈希和错误诊断。
- 内容策略失败返回 `failure_kind`、可定位范围和安全改写方向；失败 job 可审计，但不建立 0 字正文 revision，也不触发任何故事账本写入。
- “取消任务”请求服务端停止尚未完成的工作；“拒绝候选”只改变候选状态，二者不能混用。
- 不实现字包、额度、余额、价格、报价、扣费或作者 token 账单。
- AI 工具只能写 proposal/candidate；正式采用是 PawApp UI 应用命令，不注册为 Agent 自主工具。
- 删除和合并角色、线路、关系、伏笔使用服务端引用检查与软删除。

审稿是独立只读 job，输入包含当前 chapter revision、章序、作品摘要、前文必要事实、角色与设定快照。输出每条建议保存 `source_start/source_end`、原文、建议文本、理由和置信度；“采用”先产生正文 Diff，不直接覆盖 working copy。AI/人工比例和总分只作可选参考，不能进入正文权威状态或发布门槛。

## 12. 失败与恢复矩阵

| 场景 | 必须行为 |
| --- | --- |
| 保存正文网络失败 | 保留 IndexedDB 和数据库上一稿，不触发任何情报副作用 |
| AI 候选在当前标签可见但尚未采用 | 明确标注“仅候选”；新标签读取正式 working copy，不把两个状态都显示成“章节正文” |
| 保存 working copy 时章节尚未分卷 | 正文正常保存，`volume_id` 保持空；是否移动分卷由独立命令处理 |
| 保存正文成功、情报任务失败 | 正文 working copy/revision 状态可确认；情报任务独立失败并可重试，不回滚正文也不产生半套全局数据 |
| 两标签从同一基线先后保存 | 后保存的旧标签返回 409；保留 mine/theirs/base，提供比较、合并和另存检查点 |
| 后台标签检测到其他窗口保存 | 标记当前工作稿基线过期；不替换用户正在输入的正文，也不等到保存后才告知 |
| 有未保存修改时刷新或关闭 | 草稿已先落 IndexedDB；重开显示恢复预览，不因 beforeunload 未出现而丢稿 |
| 手写稿被新保存覆盖 | 旧检查点仍在统一 revision 历史中可恢复；AI 生成历史不是唯一历史 |
| “保存后离开”执行失败 | 停留编辑器并保留 dirty 稿；成功时使用与普通保存相同的命令和反馈后再导航 |
| 移动章节冲突 | 返回最新树版本，不影响正文 working copy |
| 章纲生成中刷新 | 恢复同一任务和流检查点，不重复执行 |
| 正文生成被内容策略拦截 | job 标为 failed 并返回问题范围与改写方向；正文、revision、情报和全局账本全部不变 |
| 向导目标字数为 2200，修改章纲却回到 2500 | 章节壳返回持久化的 2200；所有入口读取同一字段，默认值只用于首次新建 |
| AI 正文被拒绝 | 当前正文和 current revision 不变 |
| 大纲重生成后未采用 | 正式大纲和角色完全不变 |
| 大纲采用时角色冲突 | 阻止事务，要求逐项合并 |
| 同一章节重复同步 | 返回同一提案/采用结果，不创建重复事件 |
| 人工改稿后打开旧情报 | 明确标记 source superseded 并展示旧/新正文哈希；不能把旧提取冒充当前情报 |
| 取消情报同步，但生成阶段提取出新伏笔 | 新伏笔只留在 proposal，全局伏笔查询逐项不变 |
| 提取出未知角色 | 停留候选，不能写入只有“未知”的正式角色 |
| 事件被误分类 | 复核页可直接重分类；保存后保留原模型建议 |
| 多条调查/同盟/对立线都被归为 romance | 显示批量规则冲突并允许整列改为 relationship/mystery；未确认前一项也不写入全局 |
| 已有无向 A—B，提取建议同名 A→B | 默认匹配失败并展示方向冲突；作者选择保留无向、新建有向或编辑，不静默重复 |
| 来源章节恢复历史版 | 事件标记来源非当前，保留并提示重新比较 |
| 恢复 A 前已保存 B 情报 | B 派生项退出当前故事查询；重新激活 A 的既有 commit batch，不重复追加 A 事件 |
| 恢复只完成正文、情报事务失败 | 整体回滚到恢复前 revision；不能出现正文 A、全局事实 B 的半成功状态 |
| 关系图布局保存冲突 | 保留本地布局副本，允许另存为视图 |
| 删除仍被引用角色 | 阻止硬删除，提供合并、inactive 或归档 |
| 反向创建 B→A 且已有 A→B | 保存为独立有向边；不覆盖 A→B，并为同角色对分配独立 lane |
| 完全相同有向关系重复创建 | 返回已有边和合并/新建理由，不静默追加重叠副本 |
| 多条平行边标签重叠 | 自动分 lane/避让；列表抽屉仍能无歧义选择每条边 |
| 关系图只获得 Canvas 焦点 | 镜像树和关系列表仍可用键盘完成节点选择及全部关系操作 |
| 刷新关系网子视图 | 恢复子路由、过滤和选中项；未保存布局按明确规则恢复或重置 |
| 角色归档预览后新增正文引用 | retirement plan 失效并要求重新预览，不按旧清单提交 |
| 伏笔解决后恢复旧章节 | 产生一致性警告，不静默重开或删除回收记录 |
| 向导创建伏笔含初始进展，但全局页只收到伏笔卡 | 创建事务失败并可重试；不能以“保存成功”掩盖进展丢失 |
| 生成候选完成但未采用 | 历史可见候选；working copy 和正式情报均不变化 |
| 模型引用未选角色或线路 | 候选冲突报告列出差异，作者可允许、替换或拒绝 |
| 提取出近义线路 | 默认匹配已有线路，必须显式确认才能新建 |
| 章节归档且已有派生情报 | 同事务标记来源失效；故事账本不再把它当当前事实 |
| 章节恢复到另一正文版本 | 派生项保持失效，要求重新提取与比较 |
| 章节空壳硬删除请求重放 | 返回既有删除结果，不影响后续章节或树顺序 |
| 删除/归档章节后聚合更新失败 | 整体回滚；作品总数、分卷计数和实际列表不能出现部分成功或幽灵计数 |
| 搜索索引落后于 working copy | 标记索引 revision，当前章可直接搜工作稿；全书结果不冒充最新 |
| 全书替换期间某章已更新 | 整体停止或只提交明确无冲突项；冲突章保留 mine/theirs/base，不静默覆盖 |
| 批量跨卷移动一项失败 | 整批回滚，所有章节仍在原卷；不出现暂时未分卷状态 |
| 保存并新建下一章时保存失败 | 停留当前章并保留 dirty 稿，不建立空的下一章 |
| 倒序浏览时执行导出 | manifest 仍按权威 position_key；浏览偏好不进入内容顺序 |
| 导出期间有章节新保存 | 本次固定旧 revision；新稿进入下一次导出，不形成混合快照 |
| 导出包含空章 | 按预选策略标记或跳过，并在 manifest 列出；不静默产生未知空块 |
| 导入无法识别卷章边界 | 只返回预览错误和待人工映射项，不创建半本作品 |

## 13. 验收用例

### P0：卷章与手写闭环

1. 新增一卷三章，刷新后顺序、归属和标题不变。
2. 空章节可直接手写，不要求调用模型。
3. 编辑正文自动保存时不弹分卷选择，也不修改角色、线索或伏笔。
4. 编辑器、章节列表和作品总数使用同一“可见正文字符”计数库；换行、Markdown 标记和标题的处理规则有测试并在 UI 可解释。
5. 章节移动与正文保存可分别失败和重试，互不污染。
6. 手写章节可以有空章纲；目标字数的校验在所有入口一致。
7. “重新生成正文”只产生候选和 Diff，拒绝后正文哈希不变。
8. AI 候选流式完成但未采用时，离开页面不出现“正文未保存”；候选仍可从历史恢复查看。
9. 生成上下文把角色和线路选择标为 required/preferred/context-only；违反 required 时阻止一键采用。
10. A、B 两标签从同一 working-copy version 编辑；A 保存后 B 保存得到 409，A 正文不被覆盖，B 全文仍可复制、合并或另存。
11. 未保存正文在刷新、关闭标签重开和应用崩溃重启后均进入恢复预览；选择恢复后逐字节一致。
12. 手写检查点、已采用 AI 候选和恢复动作在同一 revision 时间线可见并可比较。
13. “保存后离开”与普通保存使用相同 API、CAS、错误反馈和路由；保存失败绝不离开。
14. 删除经用户明确确认的一次性临时章后，作品总章数、所属卷章数、实际章节集合和总字数在同一次查询中一致。
15. 本章查找和全书搜索都能跳到稳定章节与正文范围；working copy 更新后旧索引结果明确标记过期。
16. 全书替换先展示逐章 Diff；任一章节基线变化后不覆盖新稿，未冲突项也不会在未确认时自动提交。
17. “复制正文”不创建章节；“复制章节”不复制正式故事账本；两者反馈和撤销边界明确。
18. 当前章保存失败时，“保存并新建下一章”不创建空壳；成功后下一章 position_key 紧随当前章。
19. 正序/倒序切换不改变 position_key；真实重排保存后刷新、导出和其他标签使用新顺序。
20. 选中多章跨卷移动要么全部成功，要么全部留在原卷；过程中查询不到临时未分卷状态。
21. 连续输入后本地和云端保存状态、时间与冲突可见；刷新恢复的字数和统一计数器完全一致。
22. TXT/Markdown 导出保留卷名、章名、空章策略和权威顺序；倒序浏览不改变文件顺序，bundle 回导后卷章树和正文哈希一致。

补充保存状态验收：AI 候选生成后，当前标签、新标签、本地草稿、云端 working copy 和正式 revision 的可见状态逐一可辨；普通保存不弹分卷选择，也不附带情报采用确认。

补充第五章验收：向导输入 2200 后，确认页、章节壳、修改章纲和正文任务都返回 2200；内容策略失败只新增 failed job；人工校订并正式保存后，统一 revision 历史必须出现该 1782 字版本，且章节页、作品聚合与导出 manifest 的可见字数完全一致。

### P1：大纲、角色和情报

23. 整套重生成前可看覆盖范围、使用的上下文和不会被修改的模块。
24. 未采用候选时，正式大纲、角色和章节查询结果逐字节不变。
25. 各大纲 section 可独立采用；角色冲突必须人工处理。
26. 同名角色不能仅凭姓名自动覆盖或重复新增。
27. 对同一章节 revision 连点两次同步，只得到一个模型任务和一套事件。
28. 复核页可把“师徒”从 romance 改到 relationship 后采用。
29. 取消复核不会写全局数据；已完成的生成任务与被拒绝候选仍可审计。
30. 事件可直接编辑、移动线路、合并、软删除和恢复。
31. 每个 AI 事件都能回到精确来源章节 revision 和文本范围。
32. 近义追查线默认追加已有实体；显式新建后仍可合并并保留旧 ID 重定向。
33. 归档有情报的章节后，相关角色记忆、线路事件和伏笔进展不再进入当前故事账本；恢复后行为可预览。
34. 顺序保存 A、B 再恢复 A 后，默认故事账本只查询 A 的有效情报；B 仍可审计但不作为当前事实，A 的事件数量不因恢复重放而增加。

补充分类验收：同一提案包含调查、同盟、线索交换和对立四条线路时，不得全部默认 romance；作者能逐项或批量改类。取消后章内候选仍可审计，全局线路、关系和伏笔数量逐项不变。

补充正文哈希与审稿验收：AI 原稿提取情报后再人工改稿，旧 proposal 立即显示“基于旧稿”且不能提交；重新提取只绑定新 revision。第五章审稿能识别自己是第 5 章，引用前四章必要事实，每条问题均可跳到精确正文范围并预览修改 Diff。

### P2：关系图与伏笔联动

35. 点击节点和边都能编辑；有向/无向语义与箭头一致。
36. 双指缩放不滚动页面；显示比例并能适应画布。
37. 拖动未保存时刷新恢复旧布局；显式保存后跨刷新保留。
38. 不使用 Canvas 也能通过键盘列表完成全部关系操作。
39. 伏笔进展按时间追加，修改最新一条不会丢失旧记录。
40. 伏笔从埋设到推进再到解决，所有来源 revision 可追溯。
41. 建立 A→B 后再建 B→A，两条边分别保留 source、target、名称和描述；刷新后均存在且不会互相覆盖。
42. 同一角色对至少三条关系时，Canvas lane 和标签可区分；关系抽屉与键盘列表能精确选中任一边。
43. 不点击 Canvas，仅用键盘角色列表即可查看入边/出边、新增、编辑、反转、归档和恢复关系。
44. 拖动节点后显示布局 dirty；选择不保存并刷新时语义边不变，选择保存后跨刷新恢复坐标和缩放。
45. 归档被正文和关系引用的角色前显示精确影响清单；引用变化使旧预览失效，提交后历史 revision 仍能解释原角色与关系。

补充方向与伏笔验收：已有无向 A—B 时，同名 A→B 提取项显示方向冲突而不自动采用；章节向导创建伏笔和初始进展后，全局页一次读取到两者，后续进展以追加记录呈现。

补充伏笔写入验收：正文生成或正式保存即使识别出新伏笔，也只能生成 proposal；作者取消复核后全局伏笔数与 ID 集合逐项不变，不得出现绕过复核的自动条目。

## 14. 功能内部优先级

### P0

- 稳定卷章树和独立章节移动。
- 手写章节壳、正文自动保存、检查点、历史。
- 章纲作为独立 document；手填路径不依赖 AI。
- 统计口径统一并解释。
- 保存正文无跨模块隐式副作用。
- 本章/全书搜索、替换 Diff、连续新建和原子跨卷移动。
- 固定 revision 的 TXT/Markdown 导出，保留卷章边界和空章策略。

### P1

- 章纲/正文候选生成与 Diff。
- 大纲局部重新生成和角色冲突合并。
- 角色列表与结构化关系列表。
- 幂等章节情报提案。
- 可直接编辑、重分类和合并的线路事件。
- 伏笔及追加式进展。

### P2

- 可保存多视图的关系图。
- 自动布局、图筛选和大规模性能优化。
- 同角色对多边 lane、标签避让、角色搜索/聚焦和可访问镜像树。
- 跨大纲、设定、正文、事实的冲突报告。
- 卷级批量规划候选和复杂故事线分析。
- 结构化 bundle 回导、跨格式映射和复杂导入修复。

## 15. 非目标与禁止实现

- 不把标题、换行或 Markdown 标记偷偷计入“正文字数”而不解释。
- 不把保存正文与移动分卷或情报写入绑定成一个不可撤销动作。
- 不用模型按姓名直接改正式角色。
- 不把未采用的分析草稿加入正式上下文。
- 不把同事、导师、亲属默认归为恋爱感情线。
- 不让重复请求追加重复线路、事件或伏笔。
- 不把生成完成、候选入历史、正文保存和情报采用伪装成一个状态。
- 不把历史恢复实现为“覆盖编辑器 + 重放旧情报”；恢复必须更新派生有效性且保持 commit 幂等。
- 不允许旧标签以 last-write-wins 静默覆盖新稿，也不把手写保存排除在版本历史之外。
- 不依赖 beforeunload 作为唯一草稿保护；正文编辑必须先有耐久本地副本。
- 不删除章节后保留仍被查询为当前事实的孤儿记忆、事件或伏笔进展。
- 不让章节删除、归档或移动产生作品总数与分卷计数不一致的部分成功。
- 不把跨卷移动实现成需要作者先“移出”再“添加”的两次写操作。
- 不让正/倒序浏览开关承担真实章节重排，也不让它改变导出顺序。
- 不导出只有章节标题、却丢失卷名和卷边界的不可回导 TXT。
- 不把空章静默包含或跳过；策略和清单必须在导出前后可见。
- 不让搜索/替换绕过 revision CAS，更不能用全书替换静默覆盖新稿。
- 不把近义线路默认新建，也不把兄妹/师徒关系塞进普通支线或恋爱线。
- 不用 Canvas 作为关系操作的唯一入口。
- 不让只有 tabindex、却没有角色/名称/节点语义的 Canvas 容器冒充可访问关系图。
- 不让节点坐标成为关系语义的一部分。
- 不把 A→B 与 B→A 错误去重或互相覆盖，也不允许完全相同关系无限静默重复。
- 不在只显示笼统“后果不可估量”的确认框后硬删被引用角色；必须先有可复核影响计划。
- 不把模板快照、当前设定、大纲规划和正文事实混成同一份可覆盖 JSON。
- 不建设字包、额度、价格、报价、扣费确认或作者 token 账单。
