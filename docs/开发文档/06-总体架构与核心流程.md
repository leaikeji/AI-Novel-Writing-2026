# AI小说世界2026 总体架构与核心流程

状态：阶段一统一架构基线；MVP-0 的数据库、工作台、原生助手组合、Skills 与只读工具已于 2026-08-23 完成运行验证。

基线日期：2026-08-22（Asia/Shanghai）。

本文回答小说工作台如何与 QwenPaw 共存、浏览器和后端如何调用，以及正文如何保证不丢失。

> **当前范围优先级**：MVP-0 只建设写作工作台、自动保存、QwenPaw 原生助手、小说 Skills 和只读小说工具。第 10、12、13、15 节所述确认、提案、Diff、接受、事实派生和 TTS 是测试后的候选架构，不是当前实施范围。MVP-0 不注册任何 AI 正文写入工具。

## 1. 推荐方案与当前阻塞

**项目建议**：把 AI小说世界2026 实现为 QwenPaw 2.1.0 中的独立 PawApp。它拥有自己的页面、PawApp 后端、领域服务、类型化工具、Skills、数据库迁移和媒体适配器，但不复制或修改 QwenPaw 核心。

当前没有证明方案不可实现的技术性阻塞。阶段一必须先完成需求边界和公开契约复查；阶段二再用最小工程验证 PawApp 前端 Blob 加载、Monaco Worker、应用级模型设置、专用小说 Agent/Skill 作用域和聊天模型流式 tool-call。验证失败时缩小或调整插件实现，不修改 QwenPaw 上游。

## 2. 页面关系：共存，不替换

```text

    │   ├── 中栏：Markdown 编辑与预览
    │   └── 可选并排：QwenPaw 原生 AI 助手（公开接口允许时）
    └── 小说应用设置
        └── 后续：Embedding / TTS / 媒体 / 图片配置
```

固定命名空间：

```text

PawApp 后端 API：/api/ai-novel-world-2026/...
小说内部页面：由上述 PawApp 内部管理，不占用 /novels 等 QwenPaw 全局路径
```

边界规则：

- QwenPaw 原生页面、入口、路由和设置一项不删、一项不改。
- 小说 PawApp 只新增页面和应用级设置，不覆盖 QwenPaw 核心组件。
- 聊天大模型仍在 QwenPaw 原生 Provider 中配置。
- 原生助手能否嵌入 PawApp 只使用公开接口验证；若不支持，使用原生 `/chat` 页面或公开导航切换，不复制、不改写聊天组件。
- 小说 Embedding、TTS、媒体和后续图片参数优先显示在 QwenPaw 的 PawApp 插件设置体系内，但由小说适配器调用。
- 卸载或禁用小说 PawApp 后，QwenPaw 原生功能必须继续正常运行。

## 4. Docker 端口登记

容器内部端口保持原值；容器间通过服务名和内部端口访问。Mac 主机发布端口必须同时满足：

1. 只绑定 `127.0.0.1`。
2. 必须是五位数。
3. 第一位必须为 `1`。
4. 必须登记且不得冲突。

对一至四位内部端口，默认把内部端口左侧补零到四位，再加前缀 `1`。

| 服务 | 内部地址 | Mac 主机地址 | 说明 |
| --- | --- | --- | --- |
| QwenPaw | `qwenpaw:8088` | `127.0.0.1:18088` | 唯一默认 Web 入口 |
| PostgreSQL | `postgres:5432` | `127.0.0.1:15432` | 应用走内网；主机端仅供维护 |
| Portkey | `portkey:8787` | `127.0.0.1:18787` | 可选 profile |
| TEI | `tei:80` | `127.0.0.1:10080` | 可选 profile |
| Ollama（若未来容器化） | `ollama:11434` | `127.0.0.1:11434` | 已满足五位、首位 1 |

禁止使用 `0.0.0.0:18088:8088`、裸 `18088:8088` 或其他可能发布到局域网的写法。

持久卷登记：

| 卷/挂载 | 容器目标 | 内容 |
| --- | --- | --- |
| `qwenpaw-data` | `/app/working` | QwenPaw 配置、workspace、记忆和 Skills |
| `qwenpaw-secrets` | `/app/working.secret` | Provider 等服务端密钥；与普通工作数据隔离 |
| `qwenpaw-backups` | `/app/working.backups` | QwenPaw 备份 |
| `postgres-data` | PostgreSQL 数据目录 | 小说权威数据库与 pgvector |
| `novel-media` | 小说插件配置的媒体根目录 | TTS、封面和后续图片二进制 |

固定镜像已核实上述三个容器路径；当前验证环境使用带项目前缀的实际卷名 `ai-novel-2026-qwenpaw-data`、`ai-novel-2026-qwenpaw-secrets`、`ai-novel-2026-qwenpaw-backups`。阶段二 Compose 再固定最终服务/卷命名。备份必须同时覆盖 PostgreSQL、`novel-media` 和 QwenPaw 必要卷，不能只复制数据库。

## 5. 前后端调用关系

### 5.1 普通业务请求

```text
小说 PawApp 页面
  -> 同源 PawApp API
  -> 小说领域服务
  -> Repository
  -> PostgreSQL
  -> 返回带 revision / draft_version / hash 的结果
```

前端不得直接连接数据库，不得自己实现版本接受、事实合并或向量状态变更。UI API 与 Agent 工具必须调用同一领域服务。

### 5.2 MVP-0 AI 对话请求

```text
QwenPaw 原生聊天
  -> QwenPaw Agent / 专用小说 workspace（公开能力验证后）
  -> QwenPaw Provider 中配置的聊天模型
  -> Agent 自主选择小说 Skill 与 novel_* 工具
  -> 只读小说领域服务
  -> PostgreSQL
  -> 流式返回 QwenPaw 原生聊天
```

小说 PawApp 不直接调用聊天模型 API，不保存聊天模型 Key，也不运行第二套 Agent Runtime。

当前 MVP-0 没有依赖未公开的 QwenPaw 会话状态注入。工作台“复制 AI 上下文”明确提供 `novel_id` 和 `document_id`，三个只读工具校验 UUID 后读取同一领域服务。个人单用户环境下，这足以验证最小讨论链路，但不是自动会话绑定。

后续若要让 Agent 无需用户复制标识即可自动感知当前小说，必须先核实公开的 session/PawApp context 绑定接口，再设计 `novel_conversation_bindings`。在此之前不能从私有前端状态取 ID，也不能把 Agent 自报参数提升为多用户授权依据。

## 6. 组件职责边界

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| QwenPaw 核心 | 原生 UI、Agent、会话、聊天 Provider、Skills、MCP、工具调度、任务进度 | 小说正文事务、小说账本、小说向量和媒体权威数据 |
| 小说 PawApp 前端 | 小说页面、编辑体验、自动保存状态、基础历史 | 自建聊天界面、直接持有密钥、直接写数据库、让 AI 直接改正文 |
| 小说领域服务 | 业务校验、并发控制、working copy、基础 revision 和只读上下文查询 | Agent 通用编排、通用模型网关；MVP-0 不实现 AI proposal |
| 小说类型化工具 | 把 Agent 意图映射到同一领域服务 | 复制一套 UI 业务逻辑、建立内部小说 MCP Server |
| PostgreSQL | 权威正文、working copy、revision、事实、提案、任务状态和媒体元数据 | 保存浏览器临时状态之外的 UI 偏好 |
| pgvector | 可重建的小说语义索引 | 替代正文、revision 或正式事实 |
| IndexedDB | 尚未同步的崩溃恢复草稿 | 作为正式正文或长期数据库 |
| 模型/媒体适配器 | 隔离公开供应商接口差异 | 运行第二套 Agent、读取 QwenPaw 私有内部配置 |
| QwenPaw PawTask | 向 UI 展示当前进度和事件 | 充当持久任务账本或唯一取消保障 |

## 8. 数据关系文字图

```text
novels
├── short_story_profiles（可选短篇专有目标与完成状态；正文仍复用 documents/revisions）
├── volumes（稳定排序、乐观锁）
│   └── chapters（章节壳、卷归属、章纲/正文 document 引用）──► documents
│                              ├── document_working_copies（每文档当前可变稿）
│                              ├── document_revisions（不可变，多版本）
│                              │   ├── content_markdown（权威源码快照）
│                              │   ├── content_text（固定解析器生成的纯文本快照）
│                              │   ├── novel_chunks（按 embedding profile）
│                              │   ├── revision_derivations（可恢复派生记录）
│                              │   └── media_assets（TTS/后续图片来源）
│                              └── document_revision_proposals
│                                  └── 绑定 base revision + draft version + hash
├── characters ──► character_revisions / character_aliases
│   └── character_relationships（稳定端点、方向、语义 revision）
│       └── relationship_graph_views / positions（独立可选布局，不是关系语义）
├── storylines ──► storyline_events（绑定来源 chapter revision 和文本范围）
├── foreshadows ──► foreshadow_progress_entries（追加式进展与来源 revision）
├── novel_setting_snapshots（不可变建书模板快照）
├── novel_story_settings（当前可编辑设定及 revisions）
├── intelligence_extraction_proposals
│   └── intelligence_proposal_items（角色、关系、线路、事件、伏笔候选）
├── story_facts（正式事实）
│   └── story_fact_candidates（来源 revision、置信度、冲突与审核状态）
├── embedding_profiles（模型、维度、fingerprint、距离与索引策略）
├── model_run_records（任务状态、耗时、输入/结果哈希、失败与幂等重试；不承载商业计费）
├── novel_conversation_bindings（QwenPaw session 与小说/文档/revision 范围）
├── novel_prompt_snapshots（若启用高级建书向导）
├── novel_setup_drafts（正式建书前的可恢复向导草稿）
├── short_setup_drafts（若启用短篇九步向导）
└── outline_generation_drafts（若启用分阶段大纲生成；采用前不进入正式上下文）

作者级可选扩展：
template_schemas ──► template_schema_fields
creative_assets ──► creative_asset_presets
               └── creative_asset_provenance ──► text_study_results
source_texts ──► text_study_jobs ──► text_study_results ──► text_study_evidence_spans
```

正文权威层次：

```text
浏览器内存编辑稿
  -> IndexedDB 未同步备份
  -> PostgreSQL document_working_copy
  -> 不可变 document_revision.content_markdown
       └── 同 revision 的不可变 content_text 纯文本快照
```

PostgreSQL working copy 和 revision 的 Markdown 才是正文权威；`content_text` 是绑定 revision、可验证内容哈希的不可变纯文本快照，用于分块、检索和 TTS 输入，但不能反向覆盖 Markdown。HTML 预览、Diff、chunks、向量、摘要、事实候选和音频均不是正文权威。`media_assets` 元数据是持久业务记录，媒体二进制和缩略图则按缓存/资产策略恢复。

角色、关系、线路事件和伏笔是结构化正式数据，但 AI 从章节抽取的结果在作者采用前只是 `intelligence_proposal_items`。它们必须绑定来源 revision；正文更新不会静默改写已经采用的故事数据，只会标记来源非当前并触发可复核的重新提取建议。章节标题不进入正文 Markdown；编辑器、章节列表和作品总数必须共享同一“可见正文字符”算法，换行和 Markdown 标记的存储长度只能作为诊断口径，不能混进作者字数。

短篇不是第二套正文存储：`novels.work_type=short_form` 只增加 profile 和向导状态，正文、手写保存、AI 候选、历史恢复和审稿采用继续走同一 document/revision 协议。文本拆解只把有权使用的来源文本写入独立 `source_texts`，其报告与证据均是研究数据；只有作者显式采用的报告项才可生成带 provenance 的创作资产。完整约束见[短篇创作与文本拆解产品规格](./10-短篇创作与文本拆解产品规格.md)。

## 9. 自动保存与崩溃恢复流程

```text
用户输入
  -> 编辑器内存立即更新
  -> IndexedDB 写入未同步恢复稿
  -> 防抖触发 PATCH working copy
       请求携带 expected_draft_version + content_hash
       ├── 成功：数据库 version + 1，前端清理对应 IndexedDB 恢复稿
       ├── 网络失败：保留 IndexedDB，显示“离线草稿/重试”
       └── 版本冲突：不覆盖数据库，展示双方内容并进入冲突处理
```

服务端不得采用“最后到达者无条件覆盖”。刷新页面时先读取数据库 working copy，再比较 IndexedDB 的 document ID、base version 和 hash；只有确有未同步内容时才提示恢复。

## 10. AI 规划、生成与提案状态机（后续候选，MVP-0 不实现）

```text
PLANNING
  -> PLAN_READY
  -> 用户确认计划
  -> PLAN_CONFIRMED
  -> CANDIDATE_READY
       ├── 用户接受 -> ACCEPTED
       ├── 用户拒绝 -> REJECTED
       ├── 基线变化 -> CONFLICTED
       └── 新提案替代 -> SUPERSEDED
```

规则：

- `PLAN_READY` 只是一份计划，不是正文。
- 生成候选正文必须携带仍有效的一次性 `plan_confirmation_id`。
- 权威提案内容是基线标识、完整候选 Markdown 和候选内容哈希。
- Diff 由基线正文与候选全文通过固定版本的 diff 引擎生成，可缓存但可重建。
- AI 不能通过提示词绕过状态机；服务端在工具入口强制校验。

## 11. AI 讨论与上下文流程

```text
用户发送消息
  -> flush 当前编辑器自动保存
  -> 若 working copy 与当前 revision 不同，事务性建立 user_checkpoint
       并移动 document.current_revision_id、对齐当时 working copy
  -> 绑定 novel/document/revision/session
  -> QwenPaw Agent 接收消息
  -> 根据意图选择小说 Skill
  -> 按需调用：
       novel_get_context
       novel_get_document
       novel_search
  -> 组合结构化事实 + 明确前文 + 语义检索结果
  -> 返回讨论或计划
```

如果 flush 或检查点失败，聊天仍可继续讨论一般问题，但 UI 必须说明“AI 看到的是上次确认版本”，不能假装已经读取最新编辑稿。

revision 类型至少包含 `user_checkpoint`、`ai_accepted` 和 `imported`。proposal 的 `base_revision_id` 必须等于生成时的 `document.current_revision_id`；历史恢复创建一个新的当前 revision，而不是把当前指针直接指回旧记录。是否为某类检查点建立向量由索引策略决定，但普通检索始终只命中当前有效 revision。

## 12. 接受与拒绝流程（后续候选，MVP-0 不实现）

### 12.1 接受

```text
用户在 UI 点击接受
  -> UI 取得单次接受令牌
  -> 领域服务锁定 proposal 与 document
  -> 校验：
       current_revision_id == base_revision_id
       working_copy.draft_version == base_draft_version
       working_copy.content_hash == base_content_hash
       proposal.state == CANDIDATE_READY
       接受令牌有效且未使用
  -> 单个 PostgreSQL 事务：
       创建不可变 document_revision
       更新 document.current_revision_id
       同步 working copy 到候选全文并递增 draft_version
       proposal -> ACCEPTED
       写入 embedding / fact extraction 等 pending derivations
  -> 提交
  -> 返回新 revision
  -> 后台幂等执行派生任务并向 PawTask 报告进度
```

任何基线校验失败都返回冲突。系统重新读取当前正文并重新生成 Diff，不允许把旧候选强压到新正文上。

### 12.2 拒绝

```text
用户点击拒绝
  -> proposal -> REJECTED
  -> working copy 不变
  -> current revision 不变
  -> story_facts 不变
  -> 不创建正式正文向量
```

拒绝状态用于历史和继续讨论，但不能污染正式小说事实。

## 13. 当前 revision 的向量与事实流程（后续候选，MVP-0 不实现）

```text
AI 接受、用户正式检查点或确认导入事务已经提交
  -> revision_derivations 通过数据库事务原子领取 pending/租约过期记录
  -> 写 locked_by + lease_until；长任务续租
  -> 按 revision 内容哈希幂等分块
  -> 调所选 EmbeddingAdapter
  -> 校验实际维度、fingerprint、距离度量与 profile
  -> 写 novel_chunks
  -> 索引状态 ready

  -> 从已接受 revision 提取 story_fact_candidates
       ├── 无冲突、规则允许 -> 带 provenance 合并正式事实
       ├── 与正式事实冲突 -> 等待用户确认
       └── 提取失败 -> failed，可重试，不回滚正文
```

`revision_derivations` 至少记录 `revision_id`、`kind`、`status`、`attempts`、`next_retry_at`、`locked_by`、`lease_until`、`last_error`、供应商请求 ID 和唯一幂等键。领取使用 `FOR UPDATE SKIP LOCKED` 或经过同等验证的原子方案；进程重启或租约超时后可重新领取，超过重试上限进入可见的 dead-letter 状态。

### 13.1 章节情报提取与采用

章节情报提取与后台事实派生不同：它可能建议新增或修改作者可见的角色、关系、线路、事件和伏笔，因此必须停在人工复核层。

```text
不可变 chapter revision
  -> 幂等启动提取任务
  -> intelligence_extraction_proposal
       └── items：来源文本范围 + 原始分类 + 匹配候选 + 置信度
  -> 作者逐项编辑、重分类、绑定已有实体或拒绝
  -> UI 单事务采用
       ├── 创建或更新正式结构化数据 revisions
       ├── 记录 proposal item 到正式实体的提交映射
       └── proposal -> partially_accepted / accepted / rejected
```

同一 `chapter_revision_id + extractor_profile_fingerprint` 的普通重试只返回同一任务、提案或采用结果。正文发生变化后必须先形成新 revision，旧提取结果保留来源审计并标记“来源已非当前”，不得通过重复追加掩盖版本差异。完整字段、关系图边界和验收见[创作工作台内容模型与关系图产品规格](./09-创作工作台内容模型与关系图产品规格.md)。

## 14. 向量模型与索引策略

模型选择不设允许列表，本地和云端都通过 `EmbeddingAdapter`。数据正确性约束如下：

- 查询和正文必须属于同一 embedding profile、fingerprint、维度、归一化与距离度量。
- 切换模型或配置只创建新 profile 并重建派生索引，不改写历史正文。
- 普通 `search_novel` 必须与 `documents.current_revision_id` 联结，只检索当前有效 revisions；历史向量保留不等于默认可检索。
- 首期使用无固定 typmod 的 pgvector `vector` 和按 profile 过滤的精确扫描。
- pgvector 0.8.6 的 `vector` 近似索引上限为 2000 维，`halfvec` 为 4000 维。
- 4096 维使用精确扫描，或采用模型明确支持并经基准验证的较低输出维度/其他策略；不得静默截断。

## 15. TTS 流程（后续候选，MVP-0 不实现）

```text
用户选择当前段落或整章并点击朗读
  -> 执行保存屏障
  -> 必要时创建不可变检查点 revision
  -> 计算 revision + 选区 + voice + model + content_hash 缓存键
  -> 查询 media_assets
       ├── 命中：直接播放持久化音频
       └── 未命中：调用 TTSAdapter
              -> 将文件及时写入挂载媒体目录
              -> 数据库写 media_assets 元数据
              -> 返回播放地址
```

浏览器不持有 TTS Key，供应商临时 URL 不作为长期媒体。TTS 失败只显示可重试状态，不能改变或回滚正文。

## 16. Agent 工具权限矩阵

需求中的概念能力可以保留为后续研究，但 MVP-0 只把只读能力注册到 QwenPaw 工具表，并使用 `novel_` 前缀。PawApp `@tool` 默认启用，所以不能用“UI 不显示”或提示词代替权限隔离。

| 能力 | 执行面 | Agent 可自主调用 | 权限与一致性 |
| --- | --- | :---: | --- |
| `novel_get_context` | QwenPaw Agent 工具 | 是 | 从服务端会话绑定限定 novel/document/revision |
| `novel_search` | QwenPaw Agent 工具 | 是 | MVP-0 可先用 PostgreSQL 基础文本搜索；向量检索后续再接 |
| `novel_get_document` | QwenPaw Agent 工具 | 是 | 会话范围校验；历史读取需显式模式 |
| `novel_propose_document_patch` | 后续候选 | 否，MVP-0 不注册 | 测试证明需要 AI 写回后再重新设计 |
| `save_chapter_draft` | PawApp UI 应用命令 | 否，不注册为工具 | expected draft version CAS |
| `accept_document_revision` | 后续候选 UI 命令 | 否，MVP-0 不实现 | 与确认/Diff 一起重新立项 |
| `novel_extract_story_fact_candidates` | 后续候选 | 否，MVP-0 不注册 | 事实提取后续评估 |
| `update_story_facts_after_acceptance` | 后续候选 | 否，MVP-0 不注册 | 事实回写后续评估 |
| `novel_synthesize_speech` | 后续候选 | 否，MVP-0 不注册 | TTS 后续评估 |

首期小说 Skill 基线包括：小说方向讨论、故事圣经/总纲、章节大纲、正文写作、连贯性与小说账本检查、文风审查。它们可以版本化优化、拆分、合并、新增或退役，但已使用的 ID 和语义变化必须可迁移、可测试、可回滚。目标是在专用小说 Agent/workspace 中启用；阶段二必须验证 Skill provider 的全 workspace 安装、升级同步和实际启用范围，避免普通 QwenPaw 对话被小说 Skills 污染。

## 17. 失败恢复矩阵

| 故障 | 用户看到什么 | 权威数据结果 | 恢复方式 |
| --- | --- | --- | --- |
| 小说数据库不可用/迁移失败 | QwenPaw 原生页面可用，小说入口显示未就绪 | 不执行小说写入，不修改上游数据 | 修复数据库并显式重跑 one-shot migration；不在启动 hook 自动强推迁移 |
| 插件加载或前端 bundle 失败 | 小说入口不可用或显示加载错误 | QwenPaw 数据与小说数据库不变 | 禁用/移除插件，恢复纯固定版 QwenPaw；检查兼容契约 |
| 自动保存网络失败 | 离线草稿、重试 | 数据库保留上一版，IndexedDB 保留新稿 | 恢复网络后 CAS 重试 |
| 自动保存冲突 | 冲突提示与双方内容 | 不覆盖任何一方 | 用户合并后基于新 version 保存 |
| 章节移动冲突 | 卷章树提示已变化 | 正文 working copy 不变，树结构保持服务端最新版 | 读取新 tree version 后重新选择位置 |
| 大纲重新生成被取消/拒绝 | 保留任务状态和候选历史 | 正式大纲、角色、章节和设定不变 | 可继续编辑候选或创建新候选 |
| 章节情报重复提交 | 打开已有任务、提案或采用结果 | 不重复创建角色、关系、线路、事件或伏笔 | 按 revision + fingerprint 幂等读取 |
| 情报角色无法匹配 | 复核页显示候选匹配和冲突 | 不创建只有“未知”的正式角色 | 用户绑定、补全后新建或拒绝 |
| 关系图布局保存冲突 | 提示另存视图或覆盖前比较 | 关系语义完全不变 | 读取最新 view version，再合并或另存 |
| 聊天模型失败 | 对话失败、可重试 | 正文不变 | 同会话重试或切换 QwenPaw Provider |
| Embedding 失败 | 检索索引待处理/失败 | revision 已保存 | derivation 指数退避重试 |
| 接受时版本冲突 | 候选过期 | 正文和 working copy 不变 | 重新读取基线、生成新 Diff |
| 接受提交后进程崩溃 | 正文已接受，派生处理中 | revision 和 pending derivation 同事务存在 | 重启后通过 pending/过期租约继续领取 |
| 事实候选冲突 | 等待确认 | 正式事实不变 | 用户选择或编辑后合并 |
| TTS 失败 | 朗读失败、可重试 | 正文和草稿不变 | 重试或切换适配器 |
| 媒体 API 返回临时 URL | 下载持久化中 | 不把临时 URL 视为完成 | 下载校验成功后才标 ready |

## 19. 已核实事实、推断、建议和待验证项

### 已核实事实

- QwenPaw 2.1.0 提供 PawApp 路由、工具、命令、Hook、聊天上下文、存储、UI 和 Plugin API Skill provider 注册能力。
- QwenPaw 的首方应用使用 `type: app`、`meta.pawapp`、后端/前端入口和权限声明。
- PawApp 后端路由按 app_id 挂到 `/api/{app_id}`；首方应用页面入口使用 `/apps/{app_id}` 模式。
- PawApp `@tool` 默认 `enabled=True`；UI/系统命令必须通过注册边界隔离，不能只写一张权限表。
- Skill provider 默认把插件 Skills 安装到现有及未来 workspace，并默认启用；需要显式设计小说 Skills 的作用域。
- `PawAppContext.user` 当前仍是待接认证的占位实现，不能作为多用户授权身份。
- PawApp 前端由宿主动态加载，并共享 React、ReactDOM 和 Ant Design。
- QwenPaw 当前通用 Embedding 配置由 ReMeLight 消费，没有供任意 PawApp 复用的通用 Embedding API。
- QwenPaw PawApp TaskManager 的任务状态主要在进程内存中，不适合作为小说派生任务的持久权威。
- QwenPaw 2.1.0 官方 arm64 容器已在本机运行验证：包版本为 2.1.0、Python 为 3.11.2，`127.0.0.1:18088 -> 8088` 可健康访问，三个工作目录可由独立命名卷持久化。
- 当前 Docker 控制台没有登录认证；只绑定本机回环是该个人验证环境的必要安全边界。
- pgvector 允许无固定维度的 `vector` 保存不同维度，但近似索引有存储类型和维度限制。

### 技术推断

- MVP 把小说后端挂入同一 QwenPaw 进程，比增加独立 API 服务更符合 PawApp 边界和最短路径。
- 个人小说数据规模先按 profile 精确检索，通常足以支撑 MVP；真实延迟仍需基准验证。
- 持久化 derivation 记录加进程内执行器可以覆盖单机 MVP 的恢复需求，无需 Celery 或消息队列。

### 项目建议

- 基础小说创建先于完整高级向导；高级向导规格继续保留，但不自动阻塞写作闭环。
- 使用固定本地 owner 和专用小说 Agent/workspace，不为个人 MVP 建设 RBAC。
- 0.6B 本地 Embedding 只是本机默认候选，不限制用户选择其他本地或云模型。
- Portkey 保持可选；出现多供应商路由、集中限流或观测的实际需求后再启用。

### 仍待验证

- 固定 QwenPaw 2.1.0 下的 manifest 字段、应用级模型设置、前端 Blob 加载和插件卸载行为。
- Monaco Worker 资源 URL 在 PawApp 动态 bundle 中是否稳定。
- 插件依赖与 QwenPaw Python 3.11.2 宿主环境的完整解析、安装顺序和冲突行为。
- 专用小说 Agent/workspace 如何通过公开界面或 API 选择，Skills 和工具能否保持所需作用域。
- 用户所选聊天 Provider 的流式 tool-call 兼容性。
- M4/16 GB 本机上不同 Embedding profile 的召回、吞吐和峰值内存。
- 首个 TTS 供应商、模型、声音、限流和真实缓存命中率。

## 20. 非回归验收

阶段二开始后，每次插件变更至少验证：

1. `http://127.0.0.1:18088` 能进入原 QwenPaw。
2. QwenPaw 原生设置、Provider、Skills、MCP、工具和聊天入口仍可打开。
3. AI小说世界2026 只新增自己的入口。
4. 禁用小说 PawApp 后，QwenPaw 原生功能继续运行。
5. 保存密钥后，浏览器持久存储、API 读取响应、服务端日志和遥测中均不出现明文；首次输入/保存请求会短暂携带明文，严格模式使用 secret 挂载。
6. Compose 没有任何绑定 `0.0.0.0` 的主机发布端口。
7. 插件没有注册 `/novels`、`/api/novels` 等全局路由，所有页面/API 都在 app_id 命名空间内。
