## 1. 用户批准与实际范围

用户在获知“先修复已知问题，再进入下一步”的建议后明确回复“同意”。本工作包据此只实现已经由 W2 查询计划证明必要的窄索引：

- Alembic revision：`20260902_0037`
- parent：`20260901_0036`
- 索引名：`ix_story_facts_novel_created_v2`
- 键：`(novel_id, created_at DESC, id DESC)`
- 部分条件：`schema_version = 'story-fact/2'`

对应迁移不增加、删除或改写列，不执行数据回填，不修改旧 revision，也没有夹带兼容收缩。`backend/models.py` 与 Alembic DDL 使用同一索引定义；downgrade 只删除该索引。

## 2. 升级、降级与数据保持

真实迁移测试只允许连接 loopback 上精确命名的 `ai_novel_world_2026_l51_migration_test`，每次再创建随机 schema；若数据库名、主机或与 `AI_NOVEL_DATABASE_URL` 相同则拒绝运行。

实际执行链：

1. 新隔离 schema 升级到 `20260901_0036`；
2. 写入 2,000 条 `story-fact/2` 合成事实，确认正式索引不存在；
3. 升级到 `20260902_0037`，确认索引定义与 2,000 行数据；
4. 再写入 2,000 条事实并复验查询计划；
5. downgrade 到 `20260901_0036`，确认索引消失而 4,000 行仍在；
6. re-upgrade 到 `20260902_0037`，确认索引恢复且 4,000 行仍在；
7. 删除随机 schema，停止一次性 PostgreSQL。

结果：**PASS；4,000／4,000 行保持，迁移可逆。** 一次实测的 2,000 行写入为无索引 78.513 ms、有索引 51.410 ms；该顺序样本受到缓存和环境噪声影响，只能说明本次未观察到写入退化，不能作为普适性能承诺。

## 3. 查询计划门禁

W2 修复前的同一默认页 SQL 与正式迁移后的结果：

| 事实数 | 修复前扫描 / 返回 | 修复后计划 | 正式索引扫描 / 返回 | 修复后执行时间 |
| ---: | ---: | --- | ---: | ---: |
| 500 | 500 / 20 | Index Only Scan | 21 / 20 | 0.021 ms |
| 2,000 | 2,000 / 20 | Index Only Scan | 21 / 20 | 0.018 ms |
| 10,000 | 10,000 / 20 | Index Only Scan | 21 / 20 | 0.018 ms |

三档都命中 `ix_story_facts_novel_created_v2`，没有再创建或删除测试探针索引。2,000 条发布硬门禁要求扫描不超过 64 行，实际为 21 行，因此 **PASS**。benchmark 已把“正式索引存在、命中正式索引、访问不超过 64 行”改为可执行断言，缺索引或计划漂移会直接失败。

正式索引下的结构门禁继续成立：list 为 7 条 SQL、加载 20 个 StoryFact ORM；summary 为 3 条 SQL、不加载 StoryFact ORM；detail 为 6 条 SQL、加载 1 个 StoryFact ORM。峰值内存约 0.487–0.605 MiB，没有随 500／2,000／10,000 的全书规模线性增长。端到端毫秒数受容器、缓存和测试并发影响较大，只保存观测值，不设置虚假绝对时延承诺。
