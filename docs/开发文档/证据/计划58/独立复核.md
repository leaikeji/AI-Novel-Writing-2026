## 结论

**总体：BLOCKED。** 不能放行完整 `G-BUTTON`、`G-NATIVE`、`G-SEMANTIC-BUTTON`、`G-SEMANTIC-NATIVE` 或 `G-FULL`。

与早期“尚未接线”结论不同，当前工作树已将章节正文、建书模板／命名、四类全书大纲、章前线路推荐、章纲、审稿、`chapter.body` 选区和人物卡补全接入了受管确定性链。但是仍有四个不能被“按钮曾经成功返回”覆盖的严重差距：

1. **BLOCKED：真实入口没有生产任何可信 `mechanism` 来源。** 确定性 resolver 只会用 `SourceItem.kind == "mechanism"` 匹配机制模块（`backend/writing_skills/resolver.py:70-110`），但章节正文投影只产出 `genre/subgenre/content`（`backend/writing_skills/projection.py:24-53`），通用创作投影也只产出分类和整个 Prompt `content`（同文件 `125-172`），大纲投影除 `genre/subgenre` 外的字段统一标为 `content`（同文件 `321-345`）。因此当前产品自动分类可按明确题材选中 `suspense-writing`，却不能在确定性分支中根据已确立的金手指／时间回溯／特殊信息优势选中 `golden-finger-writing`。`tests/writing_skills/test_evaluation_contract.py:82-99` 直接把夹具的 `mechanism` 标签构造成 `SourceItem`，绕过了产品 projection；它即使运行通过也不能证明入口合同通过。
2. **BLOCKED：章前推荐／章纲的模型输入仍可由浏览器伪造或跨范围混入。** DTO 只限制顶层字段集、`novel` 三个字符串和 `storylines` 为 list，没有对线路、人物、伏笔、前章的嵌套结构或 ID 作范围授权（`backend/creative_schemas.py:581-635`）。服务端范围校验仅核对草稿状态／版本及小说的 `title/genre/subgenre`（`backend/writing_skills/creative.py:282-305`）；`prepare_creative_generation()` 对这两类任务不重建权威快照（`backend/creative_services.py:4814-4907`）。实际页面会回传完整线路／人物／伏笔对象及前章摘要（`frontend/src/workbench-studio.ts:2081-2093, 2127-2168`）。这些值在 action 认领后可直接进入最终 Prompt 和路由 `content`，未满足“范围校验先于取数、只使用已授权且对当前位置可见的资料”。现有反例只覆盖过期草稿和伪造题材（`tests/writing_skills/test_creative_button_http.py:698-727`），没有覆盖跨小说 ID／未来章／伪造嵌套资料。
3. **BLOCKED：旧无 `writing_action` 链没有服务端强制的“受管门禁已明确关闭”前置。** 章节正文仅根据 `writing_action is not None` 分流，否则直接进入旧检索和 `ctx.chat(..., skill="prose-writing")`（`backend/app.py:889-945`）；通用创作也在无 action 时直接读模型／检索并以 `creative_generation_skill(job)` 发送（`backend/creative_api.py:1395-1468`）；人物卡专用旧端点始终可用（同文件 `705-774`）。新前端的正常路径会根据服务端目录门禁决定受管／兼容分支，但旧页面或直接 HTTP 调用可在门禁打开时省略 action 绕过受管目录、唯一清单和稳定动作。计划58既存证据也曾观察到未重载旧页面发出旧请求并暴露完整宿主工具清单（`docs/开发文档/证据/计划58/施工记录.md:249-253`）。当前没有后端反例测试证明受管门禁开启时无 action 请求会被拒绝。
4. **BLOCKED：人物卡页面没有把恢复票据写入 `sessionStorage`。** 共用 client 只在收到 storage 时保存 action（`frontend/src/writing-skills/creative-client.ts:81-112, 172-199`），人物卡适配器又将 storage 定义为可选（`frontend/src/writing-skills/profile.ts:84-116`）；产品面板两次 `new CharacterProfileMethodClient(catalog)` 都没有传 storage（`frontend/src/character-profile-completion-panel.ts:105-123, 164-188`）。因此当前请求内的 action 和立即 GET 恢复可用，但页面刷新／返回后新 client 无票据，无法自动查回原 action 和冻结方法回执。`frontend/src/writing-skills/profile.test.ts:113-139` 通过手工注入预置 storage 测 GET，没有测产品构造路径确实先保存后恢复。

## 已证实的按钮子链（不等于 G-BUTTON）

1. **PASS：章节正文。** 当前入口确实调用 `generate_managed_chapter()`（`backend/app.py:876-894`）；既存隔离产品证据记录唯一 action／job、一次回环、冻结块各一次、空工具及未自动采用（`docs/开发文档/证据/计划58/正文产品按钮确定性装载-20260907.json`）。
2. **PASS：建书模板／命名及四类全书大纲的确定性题材子链。** 前端均通过共用 `ManagedCreativeMethodClient`（`frontend/src/creative-center.ts:717-733`；`frontend/src/workbench-studio.ts:869-909`）。既存结构化证据为 `建书产品按钮确定性装载-20260907.json`、`大纲背景产品按钮确定性装载-20260907.json` 和 `大纲人物情节亮点产品按钮-20260907.json`。
3. **PARTIAL：章前线路推荐／章纲。** 确定性题材装载、稳定 action、冻结回执和草稿回填有隔离产品证据（`章前推荐与章纲产品按钮-20260907.json`），但服务端嵌套资料授权缺口使入口整体不 PASS。
4. **PASS：审稿确定性题材子链。** 服务端精确比对正文、版本、hash、字数、题材和章纲（`backend/writing_skills/creative.py:246-281`）；证据见 `审稿产品按钮确定性装载-20260907.json`。
5. **PASS：`chapter.body` 选区的已验证 `polish` 子链；PARTIAL：全 operation 矩阵。** 服务端校验 working copy 版本／全文 hash／UTF-16 切片／前后 1500 字符（`backend/writing_skills/creative.py:143-181`）。既存产品证据只实点 `polish`，其余六种 operation 仅有自动化合同（`选区产品按钮确定性装载-20260907.json`）；非正文选区按计划明确留在兼容链，不计受管 PASS。
6. **PARTIAL：人物卡补全。** 服务端只收当前快照 hash，会在模型／目录前重建全快照核对（`backend/writing_skills/creative.py:433-472`），且候选不自动采用；证据见 `人物卡补全产品按钮确定性装载-20260907.json`。但产品 storage 接线缺失，不能继续宣称刷新恢复合同已通过。

### 仍未覆盖的反例与接口偏差

1. **创建草稿原生范围完全缺失。** 计划明确要求 novel／creation_draft 分开验收（计划 `200, 215-218`），但Context创建请求仍强制 `novelId` 并先验证小说范围（`backend/assistant_api.py:125-158`），注册表binding要求非空 `novel_id`（`backend/assistant_context_registry.py:308-320`），原生范围固定构造 `kind="novel"`（`backend/writing_skills/native.py:72-97`），投影也明确拒绝非novel（`backend/writing_skills/projection.py:78-106`）。前端创作中心还明确显示“未进入具体作品”且不启动workbench ref链（`frontend/src/assistant-route-wrap.ts:329-345, 419-422`）。不存在 creation_draft 原生状态端点或对应测试。
2. **写作意图可能逃逸受管链。** 生产判断依赖硬编码中文前缀（`backend/writing_skills/middleware.py:40-107`）；明显写作表达如“帮我续写这一章”“接着写一段”不以现有 `_WRITE_PREFIXES` 开头，会返回 `None` 并直接走普通宿主链（同文件 `292-302`），从而没有动作认领、冻结清单或方法回执。原生选区也没有计划列出的 `custom` operation映射。现有测试只证明标题／剧情词和“帮我看看”不误认（`tests/writing_skills/test_native_entrypoints.py:110-159`），没有“自然写作表达不得绕过”及custom正例。生产无条件开放前必须冻结明确的受管意图边界；不能让漏匹配自动降级为有工具的旧写作链。
3. **首次状态成功前不可刷新恢复。** `bind()`只更新内存并删除旧storage（`frontend/src/writing-skills/native.ts:203-212`）；动作binding要等第一次成功GET后才写入sessionStorage（同文件 `156-191`）。发送后、首次状态响应前刷新或状态网络失败会丢失唯一恢复凭证。现有前端测试覆盖成功后状态、切换action和显式clear（`frontend/src/writing-skills/native.test.ts:36-121`），未覆盖“bind后立即重建runtime只能GET、不得再发”。
4. **切Agent／切session不会清理旧回执。** 路由包装在 `selectedAgentId/currentSessionId` 改变时只更新context；只有离开workbench才清理native回执，另一个清理effect只依赖novel/document（`frontend/src/assistant-route-wrap.ts:405-417`）。因此同一页面切换Agent或原生session时，旧action状态仍可能显示。当前测试仅覆盖document变化（`frontend/src/assistant-route-wrap.test.ts:362-397`），缺切Agent、切session、多标签页恢复与连续两次共享context_ref的UI反例。
5. **当前实现没有产品级原生非回归证据。** `tests/test_qwenpaw_integration_contract.py:127-140`只静态断言注册字符串；原生后端测试使用本地FastAPI假 `/api/skills` 和fake model probe（`tests/writing_skills/test_native_entrypoints.py:335-402`），前端测试使用fake transport。既存 `原生公开合同探针.md` 与两个JSON明确只证明公开SDK技术可行和动作票据，施工记录第二十五、二十六轮仍把生产认领、状态UI和真实页面列为缺失（`施工记录.md:405-421`）。当前代码补上了其中多项，但没有新的当前包hash、安装、真实原生发送、压缩／切换、UI三视口及卸载非回归证据，故“文件已存在”不能反推实测通过。
6. **生产释放方式与门禁合同不一致。** `PublicLoadCapabilities.require("native")`仍声明必须具备历史与压缩能力（`backend/writing_skills/load_policy.py:64-92`），但生产native工厂没有使用该能力对象，而是经插件注册直接固定 `released=True`。若本轮尚未正式裁决 `G-NATIVE`，应先关闭／撤回该注册或引入单一服务端发布常量；若主代理认为已裁决，则必须先补齐上述范围、反例和运行证据并同步计划／入口清单，不能同时保留“关闭”注释与实际开放行为。
