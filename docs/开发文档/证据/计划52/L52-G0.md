# L52-G0：百万至五百万字当前路径规模事实基线

日期：2026-09-02（Asia/Shanghai）
状态：已完成（隔离合成数据；生产源码只读；云端 Provider 调用 0）

## 1. 结论

当前数据库底座和 2048 维 pgvector 精确扫描不需要更换，也没有证据支持现在增加 ANN 或新的全文搜索索引。需要立即优化的是四类应用层结构问题：

1. `list_novels` 为每章读取 working copy 并在 Python 计算字数，500 万字样本产生 2,502 条 SQL。
2. `get_novel`／`/tree` 把整部作品正文装入一个响应，500 万字响应达到 15.62 MiB，并在前后端形成多份副本。
3. Context V4 先遍历全书和全部事实，再做预算；500 万字产生 5,011 条 SQL、10.34 MiB snapshot 和 142.99 MiB tracemalloc 峰值。
4. hybrid 检索先把 Dense／lexical 全候选返回 Python，再逐候选检查 current source；500 万字产生 7,508 条 SQL。authority local fallback 也先读取并切分整书。

这些结果说明长篇写作不会因为“有 500 万字”必然崩溃，但现状存在明显线性放大，不能宣称 500 万字稳定可用。优化后必须让导航、Context、Prompt 和检索的应用层返回规模由页大小／策略上限决定，而不是由全书长度决定。

## 4. EXPLAIN 与索引裁决

### 4.1 lexical

- 500 万字当前无界查询返回 7,500 行，执行 138.826 ms，并扫描全部 7,500 chunk 和 2,500 source。
- 同数据的有界候选查询返回 1 行，执行 0.129 ms，使用已有 `ix_semantic_chunks_content_trgm` Bitmap Index Scan。
- 100 万字数据量较小时优化器选择顺序扫描；返回 1 行，执行 25.143 ms。该选择仍在可接受范围。

裁决：保留现有 pg_trgm 索引，先改 SQL 形状、scope/current 过滤和 `LIMIT`；本阶段不批准新的搜索索引 migration。

### 4.2 Dense 2048 cosine

使用隔离库临时 unlogged probe 表，结束后已删除；没有 ANN：

| 向量行数 | 当前无界 P95 | 有界 80 P95 | DB 返回行 |
| ---: | ---: | ---: | ---: |
| 1,500 | 8.247 ms | 7.074 ms | 1,500 → 80 |
| 7,500 | 67.280 ms | 46.637 ms | 7,500 → 80 |

`LIMIT 80` 仍做精确向量扫描，但把应用返回行固定为 80。目标规模下数据库计算不是主要瓶颈；当前不批准 HNSW／IVFFlat。若未来 active chunk、并发或冷数据 P95 超过冻结阈值，再以 Recall 和写放大证据单独立项。

### 4.3 retired／invalid churn

500 万字 active generation 基线为 2,500 source／7,500 chunk：

| churn | 总 source | 总 chunk | current query 扫描 chunk | 执行 ms |
| --- | ---: | ---: | ---: | ---: |
| 1× retired | 5,000 | 15,000 | 15,000 | 131.662 |
| 10× retired | 27,500 | 82,500 | 82,500 | 136.604 |

热缓存时间暂未失控，但扫描块和存储随历史派生数据持续增长。必须实现 active generation 内 retired／invalid source 及其 chunk/vector 的安全 GC；它只删除可重建派生数据，不删除 working copy、revision、StoryFact、binding 或 generation 审计记录。

当前 `EMBEDDING_BATCH_MAX_ITEMS=1`；一次 7,500 chunk 全量构建会形成约 7,500 次 batch/job 请求。普通单 source 保存必须改成 source 级增量 refresh；全量 rebuild 保留为显式动作，并分别验收 superseded pending、retry、cancel 和整书清理。

## 5. 调用图与契约分类

```text
GET /novels
  -> list_novels -> 全部章节 -> 每章 session.get(working) -> Python 计字

GET /novels/{id} / GET /novels/{id}/tree
  -> get_novel -> get_novel_tree -> 全部 working/base revision 正文
  -> frontend workbench-v2 打开作品时重复取得
  -> creative_services 多个创建/完成响应也复用 get_novel
  -> assistant_api 用 get_novel 只为存在性检查

Context V4
  -> 全部 StoryFact
  -> 全部章节 -> 每章 working + revision
  -> 构造大 snapshot -> Prompt 再预算

semantic_search
  -> Dense .all() + lexical .all()
  -> 每个候选 _source_is_current
  -> 融合/邻块/裁剪
  -> 失败时 authority local 读取并切分整书
```

分类：

- `/novels/{id}` 与 `/tree` 是本项目第一方 PawApp 契约，不是 QwenPaw 上游公共契约；当前前后端和测试有多个调用者，不能原地突然改形状。
- 单文档读取是长篇正确边界，应复用并把 revision 摘要改为有界分页。
- `get_novel` 同时承担元数据、树和响应拼装，是结构性冗余源；先新增轻量 workspace 服务并迁移调用者，全部调用者归零后删除 full-tree helper，不保留永久兼容层。
- 生成/任务数据库内部 snapshot 是审计证据；HTTP projection 只能公开脱敏 `retrieval_summary`，不能将 query、snippet、Prompt 或 Context snapshot 暴露给前端。

## 6. 迁移裁决

| 候选 | G0 裁决 | 原因 |
| --- | --- | --- |
| 未来新书向量默认偏好表 | 不需要 | 用户已裁决产品直接默认开启；现有逐书 `NovelEmbeddingConsent` 已能保存每本书的 Provider/model/scope/授权与撤销证据 |
| working copy 可见字数列 | 需要，待用户单独批准 migration | 作品列表必须聚合数字，不能加载正文；所有写路径与回填需等值 |
| 作品搜索新索引 | 暂不需要 | 500 万字当前 P95 171.135 ms，且返回有界 |
| lexical 新索引 | 不需要 | 现有 trigram 在 500 万档有界查询执行 0.129 ms |
| ANN | 不需要 | 7,500×2048 exact P95 67.280 ms；主要问题是应用返回无界 |
| tree version 列 | 暂不需要 | manifest ETag 可先由轻量聚合版本材料构造；实现若证伪再回到契约门禁 |
| GC 辅助 DDL | 暂不需要 | 先用既有 source state/generation 外键实现有界批次清理并测锁；不足再立项 |

本报告只作 migration 必要性裁决，没有创建或修改任何 migration。用户后续裁决取消了授权偏好表，因此现在只有 working copy 可见字数列需要取得 migration 明确批准。

## 7. 优化后绝对门槛建议

以下是在本机、同类隔离数据上的 W4 门槛；功能正确性和结构性硬门禁优先于毫秒数：

| 路径 | 500 万字目标 |
| --- | --- |
| 作品列表 | P95 ≤ 250 ms；SQL ≤ 5 |
| manifest 每页 200 | P95 ≤ 250 ms；SQL ≤ 8；响应 ≤ 512 KiB；无正文 |
| 代表性 2,000 字单文档 | P95 ≤ 100 ms；SQL ≤ 6；只随目标正文增长 |
| Context V4 | P95 ≤ 1,500 ms；SQL ≤ 60；峰值 ≤ 64 MiB；snapshot ≤ 2 MiB |
| authority local fallback | P95 ≤ 750 ms；SQL ≤ 12；峰值 ≤ 32 MiB |
| hybrid 应用链（不含云 Provider） | P95 ≤ 500 ms；SQL ≤ 20；两路候选合计 ≤ 160 |
| Dense exact DB | P95 ≤ 250 ms；应用返回 ≤ 80 |
| indexed lexical | P95 ≤ 250 ms；应用返回 ≤ 80 |
| 作品搜索 | P95 ≤ 500 ms |

从 100 万到 500 万，manifest、选中文档和应用侧候选行不得近似 5 倍增长。Dense exact 的数据库 CPU 可以随 active chunk 增长，但不得把全候选交给 Python。

## 8. G0 限制与 W1 输入

- 本轮没有做真实浏览器 UI 基线。当前 full-tree 的 15.62 MiB 响应和服务端峰值已经证明契约必须先改；真实 QwenPaw 的 1920×1080／2560×1440、网络解析、DOM、heap、dirty 恢复和助手组合统一放在 W4 对完整候选验收，不能用当前已知错误形态冒充优化后 UI 通过。
- 没有做云 Provider 延迟、费用或限流压力；W4 如需少量真实调用必须另行获批。
- 固定查询命中不等于质量套件；W1 必须冻结 Recall@5、MRR、无答案拒答和隔离泄漏门禁，W4 用多查询 oracle 复测。
- `L52-CONTRACT` 可据此冻结 manifest、Context/Prompt、candidate、consent、公开 summary 和兼容删除策略；生产代码仍未获准越过必要 migration 的单独批准门禁。
