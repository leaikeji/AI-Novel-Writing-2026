## 1. 用户决策与唯一目标

用户已明确要求：找出故事账本领域全部兼容内容；允许清理所有已经证明确为测试用途的小说；不再保留故事账本兼容层；最终只保留一套最清晰、完整、可恢复、可审计的故事账本。

本计划的唯一目标是把当前已经统一到 `story_facts` 权威表、`novels.story_ledger_version` 快照根和共享领域服务的实现进一步收缩为**单一数据库结构、单一 HTTP 契约、单一人物写作视图和单一前端调用路径**，并在完整备份后删除精确识别的 7 本测试小说。

本计划不做：

- 不删除、修改或摘要任何未被证据明确证明为测试用途的小说；
- 不删除 PostgreSQL、QwenPaw 或媒体数据卷，不执行广义数据库清理；
- 不修改 QwenPaw 上游核心、私有路由、私有数据库或基础镜像；
- 不引入第二数据库、第二账本、队列、缓存、Agent Runtime 或模型选择器；
- 不启动计划 52 的百万／五百万字压力矩阵；
- 不切换长期 API／worker 数据库角色，计划 53 的 `HOLD` 保持不变；
- 不暂存、提交或推送。

## 2. 当前实现事实

### 2.1 只有一套权威账本

当前实现已经只有一个权威故事事实写入面：

- `novels.story_ledger_version`：作品级账本快照与 CAS 根；
- `story_facts`：唯一正式事实表；
- `derived_source_bindings`：事实到不可变章节 revision 的来源有效性与溯源；
- `story_event_links`：事实与事件的关系证据；
- `intelligence_commit_batches`：提交、幂等、撤销和恢复证据；
- `intelligence_proposals`／`intelligence_proposal_items`：尚未进入正式账本的候选层；
- `backend/story_state/fact_authority.py` 与 `effective_state.py`：Context、Embedding、人物卡和全书账本共同使用的权威纳入与状态判断。

长期数据库没有第二张名为 ledger 的关系表。计划 51/53 验收时，正式事实、来源绑定、事件链接和提交批次均由上述同一链路读取。人物工作台、Context V4、Embedding 和全书账本是同一权威数据的不同只读投影，不是第二套账本。

### 2.2 已确认仍存在的故事账本兼容内容

以下内容不构成第二套权威数据，但会继续制造双契约、双字段或双路径，本计划全部移除：

## 3. 唯一冻结契约

### 3.1 数据库

- 正式事实只写 `story_facts`；候选只写 proposal 表，作者接受后通过同一领域服务进入正式事实。
- `derived_source_bindings` 唯一键收缩为 `(derived_entity_id, source_chapter_revision_id)`；删除 `derived_entity_type`。
- `character_relationships` 只保留 `label`；删除 `relation_type`。
- 新迁移固定为 `20260902_0038`，唯一父 revision 为 `20260902_0037`；不得修改历史迁移。
- 升级前必须 guard：来源类型只能为 `story_fact`，关系别名必须与 `label` 相等，否则 fail closed。

### 3.2 HTTP API

全书账本唯一读取／命令路径：

- `GET /novels/{novel_id}/story-ledger/summary`
- `GET /novels/{novel_id}/story-ledger/facts`
- `GET /novels/{novel_id}/story-ledger/facts/{fact_id}`
- `GET /novels/{novel_id}/story-ledger/facts/{fact_id}/source`
- `GET /novels/{novel_id}/story-ledger/facts/{fact_id}/impact-preview`
- `POST /novels/{novel_id}/story-ledger/facts/{fact_id}/corrections`
- `GET /novels/{novel_id}/story-ledger/batches/{batch_id}/impact-preview`
- `POST /novels/{novel_id}/story-ledger/batches/{batch_id}/revert`

人物工作台只返回 `character-workspace/2`；删除 `view_version` 查询参数和 V1 分支。人物 facts 分页继续作为同一账本的按人物投影保留，不另建表或规则。

章节情报提交继续使用现有 proposal commit endpoint，但请求只接受：`accepted_item_ids`、`expected_story_ledger_version` 和 `operation_key`。删除客户端覆盖字段；要修改 AI 提案内容必须回到提案审阅／作者命令，不在正式提交时静默覆写。

关系创建、更新、批处理和响应只使用 `label`；带 `relation_type` 的请求因严格请求模型／未知字段规则失败，不再 fallback。

### 3.3 幂等收缩

情报提交 canonical payload 固定为：

```json
{"accepted_item_ids":["<sorted UUID>"],"proposal_id":"<UUID>"}
```

迁移对现有 `intelligence_commit_batches` 逐行重算 `inverse_operations.payload_hash`；没有显式 `operation_key` 的批次同时把 `commit_key` 改为新 hash，有显式 key 的批次保留 key。迁移不得保留运行时“新旧 hash 都接受”分支。降级只用于从备份／迁移失败恢复，并按已冻结的空 override 旧形状重算；正式升级后的运行时只有新形状。
