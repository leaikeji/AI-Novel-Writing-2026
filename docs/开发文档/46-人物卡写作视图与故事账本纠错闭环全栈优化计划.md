# 人物卡写作视图与故事账本纠错闭环全栈优化计划

状态：**V1.2 源码候选已完成，自动化、打包、隔离 PostgreSQL 合成数据和桌面浏览器验收通过；500 条人物事实性能门禁通过。本专项已按用户后续授权单独提交并推送。尚未安装到长期 18088，未写入《潮汐盲区》，未执行长期发布／回退门禁。** 当前工作区仍包含人物声音页等其他未提交改动；本专项交付与这些改动继续按文件和 diff 范围区分，不能混合认定为计划 46 成果。

日期：2026-09-01（Asia/Shanghai）

## 0. 最终裁决

### 0.1 一句话方案

保留“人物根档案 → 当前线人物实例 → StoryFact v2 故事事实”的三层权威模型，把人物卡改造成“基础资料轻编辑、当前线设定渐进披露、当前状态先摘要后历史”的桌面写作界面，并补齐事实来源跳转、受控修正、同步批次撤销和人物卡原子保存。

### 0.2 不合并三层权威数据

三层的生命周期和并发版本不同，不能为了减少页签而合并表或 JSON：

| 作者看到的内容 | 唯一权威 | 允许修改方式 |
| --- | --- | --- |
| 基础资料 | `NovelCharacter` + 不可变人物根 revision | 作者显式保存人物卡 |
| 当前线设定 | `CharacterInstance` + 不可变实例 revision | 作者显式保存人物卡 |
| 当前状态与经历 | `StoryFact v2`、来源绑定和事件链接的投影 | 章节同步确认、受控事实修正或同步批次撤销 |

前端可以把这三层组织得更轻，但不得把章节变化复制回人物根 `details` 或实例 `profile_json`，不得让状态摘要成为第二份故事真相。

### 0.3 当前实现事实与旧计划冲突裁决

1. 计划 27／29 的顶部仍保留“待批准、未施工”的历史阶段状态，但后续计划 31、32、42 已经完成正式人物 revision、人物实例、StoryFact v2、来源有效性和章节同步关系投影。本文以当前源码及这些后续完成记录为基线，不重新执行旧计划的全量范围。
2. `CharacterWorkspaceV1` 已正确聚合人物根、所选时间线实例、别名、关系、章纲引用、声音绑定和投影事实。
3. 当前“成长与状态”直接渲染 `projected_state.current_facts`。投影键包含 `fact_type + stable_entity + dimension + predicate`，不同动作谓词可以长期并存，因此事件流水会被呈现成“当前状态”。投影算法本身不因此错误，错误在于把底层投影直接当作者界面。
4. 章节“同步进展”确认会原子创建 StoryFact、来源绑定及必要关系实体，并推进 `story_ledger_version`；该主链保留。
5. 页面提示“回到事实账本修正来源”，但当前正式工作台没有完整可达的事实纠错界面。现有 `GET /story-facts` 只返回最多 500 条全书记录；故事事件链接 API 能建立 supersedes／contradicts，但没有面向作者的替代事实命令。
6. 当前“保存人物卡”先调用人物根 PUT，再调用实例 profile PUT；两次请求属于两个事务，后一个失败时可能产生部分保存。
7. `frontend/src/workbench-v2.ts` 在返回 `StudioProjectView` 后还保留一整段不可达旧角色／线索渲染，同时页面仍会为角色／线索加载全书 `story-facts`。这是可证明的冗余读取和死代码，必须在不影响现行工作台后安全移除。

### 0.4 V1.1 第二轮复核修正

1. 原 V1.0 用 `operation_key + replacement_hash` 生成修正事实指纹，无法在数据库唯一约束上识别“同一 operation key、不同 payload”；V1.1 改为只用 scope + operation key 生成唯一指纹，并把完整 operation hash 写入事件链接供重放比较。
2. 替代事实如果继续引用来源 revision，就必须创建自己的 `DerivedSourceBinding`；否则现有来源有效性投影会把它判为不确定。V1.1 已补齐绑定规则。
3. 来源有效性目前按 revision 聚合；单独把某个 binding 改成失效会使同一 revision 的其他事实一起失效。批次撤销因此只能改变 batch 和 batch-owned fact 状态，不能把单条 binding 改成 `source_superseded`。
4. 正文 revision 恢复会重新协调 fact status。V1.1 要求协调器识别已撤销 batch，禁止把其中事实重新激活。
5. 新原子保存不能直接绕过 `update_novel_character()` 现有的角色类型、姓名清洗、同名、生命周期和 details 合并校验；这些规则必须先抽成共享校验器。
6. `source_start/source_end` 来自 Python Unicode code-point 坐标，不能直接作为浏览器 UTF-16 selection。V1.1 增加坐标版本、content hash 校验和转换测试。
7. 当前已有 revision 内容 GET，但没有可直接定位证据的正式历史查看器；V1.1 将其作为本计划新增的只读来源证据组件，不再假定页面已经存在。
8. V1.0 验收命令引用了不存在的 `workbench-studio.test.ts`／`workbench-v2.test.ts`；V1.1 已改为现有测试文件和本计划明确新增的测试文件。
9. `CharacterInstanceProfileV1/V2` 是 `extra="forbid"` 的严格版本化协议，不是任意扩展 JSON。V1.1 不再承诺保存未知 profile 字段；前端提交完整、合法的版本化 profile，服务端只对人物根的可扩展 `details` 做 patch 合并。
10. 人物根保存不写故事账本，实例 profile 保存才会推进 `story_ledger_version`。V1.1 要求只对实际发生变化的聚合执行相应 CAS，避免仅修改人物姓名时被无关章节同步阻塞。
11. 原子保存子操作键不能简单追加后缀，否则 160 字符的合法外部 key 会溢出底层限制；V1.1 改用固定前缀加 SHA-256 派生键，底层 revision 自身的 operation hash 继续负责 payload 冲突检测。
12. 投影中的“当前”“历史可见”“冲突／不确定”和事实生命周期不是同一轴。V1.1 将事实有效状态与健康状态拆分，补上此前遗漏的“历史变化”，避免把冲突当成 superseded 一类生命周期。

## 1. 目标、非目标与硬不变量

### 1.1 目标

- 让作者在 5 秒内回答“这个人物是谁、现在处于什么状态、最近发生了什么、依据来自哪一章”。
- 基础资料保持低负担；当前线设定按使用频率分组和折叠，不删数据。
- 从 StoryFact 投影生成确定性的写作状态摘要，摘要缺失、冲突和不确定时明确披露，不由前端猜测。
- 全部事实按人物、时间线和叙事截止点分页读取，支持维度、状态和来源筛选。
- 每条事实能跳转到来源章节／revision／证据区间；来源不是当前 revision 时明确进入只读历史证据。
- 作者可以创建替代事实并 supersede 错误事实；错误的整次章节同步可以在影响预览后撤销。
- 人物根与实例设定在一次“保存人物卡”操作中同事务成功或失败。
- 保留声音页独立保存和计划 44 已收敛的交互，不把声音保存并入人物资料事务。

### 1.2 非目标

- 不合并人物根、人物实例和 StoryFact 表。
- 不把状态摘要持久化为第二份权威数据，不新增人物轨迹表、状态快照表或任务账本表。
- 不改变 `project_story_facts()` 的通用权威投影键；作者摘要由单独的只读适配层生成。
- 不允许任意原地编辑或删除 StoryFact，不静默改写来源正文或历史 revision。
- 不重新引入按人物姓名、中文关键词或样书内容猜测状态的规则。
- 不新增模型调用、Agent、Skill、向量模型、队列、运行时依赖或 QwenPaw 上游改动。
- 本轮不设计新的移动端界面；现有窄屏规则只做非回归，不作为视觉验收目标。
- 不自动修改《潮汐盲区》或其他长期小说数据；真实小说只允许只读核验，写入验收使用隔离数据库和合成小说。

### 1.3 硬不变量

- 作者确认前，AI 候选不得写入故事账本。
- StoryFact 的 stable entity、timeline、来源 revision 和知识可见性必须由服务端校验。
- 修正以“新事实 + `supersedes` 链”实现，原事实继续保留用于审计。
- 同步批次撤销不得删除事实、revision、来源绑定或关系历史；只改变有效性／投影可见性，并记录批次状态。
- 单线作品继续零配置；多线作品仍要求显式 timeline／instance，不允许最近值猜测。
- CAS、幂等、content hash、来源有效性和不可变 revision 不能被 UI 便利性绕过。
- 生成上下文继续以权威投影和来源证据为准；人物卡摘要首期只服务作者 UI。

## 2. 人物卡信息架构

正式页签固定为：

1. **基础资料**：跨故事线稳定的人物身份。
2. **当前线设定**：替代“本线档案”，表达这是当前时间线／连续个体的初始与长期设定。
3. **状态与经历**：替代“成长与状态”，内部再分“当前状态、最近变化、全部事实”。
4. **声音**：继续复用唯一声音组件和独立保存链。

页签计数规则：

- 不再把全部事实数作为“状态与经历”的醒目徽标，避免把资料数量误当待办。
- 只有冲突、不确定或来源失效等需要作者处理的数量才显示徽标，例如“2 项待核对”。
- 全部事实数量放在“全部事实”折叠区标题中，例如“全部事实（38）”。

## 3. 桌面 UI 布局冻结

### 3.1 对话框与公共骨架

- 宽度从当前 `1120px` 提升为 `min(1240px, calc(100vw - 64px))`。
- 最大高度为 `calc(100dvh - 48px)`；顶部摘要、页签和底部动作固定，中间内容区唯一滚动。
- 外边距 24px；内容区使用 12 列网格，列间距 16px，区块间距 20px。
- 顶部保留人物头像、姓名、角色定位、正式人物卡版本；多时间线时才展示时间线与人物实例选择器。
- 静态资料卡不增加 `tabindex`，鼠标点击不出现装饰性蓝框；键盘交互控件继续使用 `:focus-visible`，不能为了视觉美观删除可访问焦点。
- 底部只在人物资料 dirty 时出现“撤销修改／保存人物卡”；干净状态保留“关闭”。声音页继续显示自己的独立保存语义。

### 3.2 基础资料

首屏不需要折叠：

- 第一行：人物姓名 6 列、角色定位 3 列、性别 3 列。
- 第二行：核心主题 12 列。
- 第三行：公开小传 12 列，最小高度 112px。
- 底部：称谓与别名 6 列、引用概览 6 列。

基础资料不增加低频字段，不把声音、当前状态或出生信息塞入此页。

### 3.3 当前线设定

正文区域采用“主区 7 列 + 辅区 5 列”，不再用 13 个字段等权三列平铺：

- 主区“常用写作信息”：职业、初始性格、目标、缺陷、秘密、成长方向。目标／缺陷／秘密继续每行一项，显示项数和空态提示。
- 辅区“身份层”：现实身份、真实身份、掩护身份。已填写值直接显示；全部为空时只显示一行摘要和“展开填写”。
- 辅区“出生与年龄”：出生年、历法、出生信息、开篇年龄说明，默认折叠；存在任一值、字段错误或服务端冲突时自动展开。
- 每个分组标题显示“已填写 n/m”，但不把未填字段渲染成错误或强迫完成。
- 折叠只改变显示，不卸载或丢弃 draft；前端必须回传当前 schema 中未编辑的合法 profile 字段。人物实例 profile 继续按 V1/V2 严格校验，不接纳未知字段。

### 3.4 状态与经历

从上到下固定为三层：

#### A. 当前状态摘要

采用“主区 8 列 + 风险区 4 列”：

- 主区使用紧凑定义列表，不用十几张等高卡片；默认维度为位置、目标、健康、情绪、身份、已知信息、持有物、关键关系。
- 单值维度显示当前值、故事时间／序位和来源章节；多值维度显示前 3 项及“查看全部”。
- 未记录显示“尚无已确认事实”，不能从人物小传、正文关键词或服务器日期补值。
- 风险区显示冲突、不确定事实、来源失效和缺失维度；已撤销同步属于审计历史，不计入待处理风险。没有风险时显示“当前状态依据完整”，不保留空白大卡。

#### B. 最近变化

- 默认显示最近 5 条有效事实，按可比较的故事序位、创建时间和稳定 ID 排序。
- 每行包含维度、事实描述、来源章节、故事序位／故事时间和“查看来源”。
- `action`、`presence` 等事件型事实只进入最近变化和历史，不占据当前状态摘要。

#### C. 全部事实

- 默认折叠；首次展开时才请求分页接口，每页 20 条。
- 有效状态筛选：全部／当前值／历史变化／已被替代／来源失效／已撤销同步；健康筛选：全部／正常／冲突／不确定；另提供维度和来源章节筛选。
- 表格列：状态、维度、事实、故事位置、来源、操作。长文本两行截断，展开行查看完整 details 和来源证据。
- 操作固定为“查看来源”“修正”；有 commit batch 且满足安全条件时额外显示“撤销本次同步”。

### 3.5 来源与修正交互

- “查看来源”以 `document_id + revision_id + source_content_hash + source_coordinate + source_start/source_end + source_range_hash` 定位证据。人物资料无未保存改动时可关闭人物卡并切到章节；存在 dirty draft 时必须提供“保存并跳转／放弃并跳转／取消”，不得虚构未实现的暂存能力或静默丢稿。
- 若来源 revision 仍为当前版本，先核对 content hash，再把 `unicode-codepoint-v1` 坐标转换为浏览器 UTF-16 坐标，并核对证据区间 hash 后只读高亮；任一校验不匹配时只显示有界证据摘录，不猜测位置。
- 若来源 revision 已失效，调用现有 `GET /documents/{document_id}/revisions/{revision_id}`，在本计划新增的只读来源证据查看器中展示 revision、摘录和位置，并显示“该来源不是当前正文”；查看器不得提供恢复、覆盖或编辑快捷操作。
- 修正使用人物卡内右侧 480px 抽屉，不叠加第二个居中 Modal。抽屉显示原事实、来源证据、替代值、修正理由和影响预览。
- stable entity、timeline、人物实例和来源 revision 只读；作者只能修改允许的语义字段。
- 提交前提示“将创建新事实并替代旧事实，旧记录仍保留”；成功后刷新摘要和历史并聚焦结果提示。
- “撤销本次同步”必须先显示该批次涉及的事实和关系影响，不能从单条事实直接静默撤销整批。

## 4. 后端读模型与写作摘要

### 4.1 `CharacterWorkspaceV2`

保留当前 GET 路径，并增加 `view_version=2` 显式协商；默认 V1 在兼容期不变。V2 保留 V1 全部字段，新增：

```text
schema_version = character-workspace/2
writing_state:
  as_of: timeline_id / narrative_cutoff / story_time
  slots[]: key / label / mode / values[] / health
  recent_changes[]
  risk_summary: conflict_count / ambiguous_count / invalid_source_count
  history_summary: total / current / historical / superseded / source_invalid / batch_reverted
```

V2 使用新的 `ProjectedFactViewV2` 增补只读来源摘要，V1 的冻结字段保持不变：

```text
source:
  document_id / document_title / document_position
  revision_id / revision_is_current
  source_content_hash / source_coordinate=unicode-codepoint-v1
  source_start / source_end
  source_range_hash
  source_excerpt / source_excerpt_truncated
  binding_state / proposal_item_id / commit_batch_id
```

`source_excerpt` 只返回证据区间附近至多 500 个 Unicode code points；超长证据标记 `source_excerpt_truncated=true`。`source_range_hash` 固定为原始 `content_text[source_start:source_end]` 的 UTF-8 字节 SHA-256，始终覆盖完整证据区间，使前端即使只收到有界摘录，也能在已授权读取的完整 revision 中验证定位而不靠模糊文本搜索。

V2 仍返回 `projected_state`，保证声音匹配等现有消费者不被写作 UI 摘要替代。

### 4.2 确定性摘要适配器

新增纯模块 `backend/character_workspace/writing_state.py`，输入只能是经过时间线／截止点／可见性过滤的投影和来源元数据。

- 单值状态：`location / health / emotion / identity`。
- 多值状态：`goal / knowledge / possession / relationship`。
- 事件历史：`action / presence` 及未注册维度；只进入最近变化／全部事实。
- 未知维度不得被丢弃，统一进入历史并标记“其他事实”。
- 同一槽存在投影冲突时不选赢家，槽状态为 `conflicted`。
- 无故事序位、来源无效或可见性不确定的事实不进入“已确认当前值”，转入风险区。
- 规则只依赖协议枚举和稳定字段，不读取中文文案或小说专名。

首期不改变 Context V4；摘要通过浏览器验收和合成小说一致性门禁后，若未来要复用于模型上下文，必须另行批准并继续携带原始事实证据。

### 4.3 人物事实分页接口

新增：

```text
GET /novels/{novel_id}/characters/{character_id}/facts
  ?timeline_id=
  &character_instance_id=
  &narrative_cutoff=
  &effective_state=all|current|historical|superseded|source_invalid|batch_reverted
  &health=all|ok|conflict|ambiguous
  &dimension=
  &source_document_id=
  &cursor=
  &limit=20
```

- `limit` 为 1–100，默认 20；游标由服务端编码稳定排序键，不接受任意 SQL 字段。
- 查询必须先验证 novel、character、timeline 和 instance 范围。
- 关系事实只返回当前人物参与且符合实例／时间线范围的记录。
- `effective_state` 与 `health` 是两个正交字段：状态型事实进入权威投影当前值时为 `current`；事件型事实及仍可见但不是当前值的事实为 `historical`；`source_invalid`、`batch_reverted` 和 `superseded` 来自事实、来源绑定、事件链接和 commit batch 的组合状态，不能只看一列字符串。冲突与不确定只进入 `health`，不得伪装成事实生命周期。
- 单行主状态优先级冻结为 `batch_reverted > superseded > source_invalid > current/historical`，避免已被替代的旧事实继续制造来源待办；有效状态计数互斥，健康状态作为独立分面可与有效状态交叉，但 `total` 始终只按事实去重。
- 返回 `items / next_cursor / total_summary`；全量统计和页面数据来自同一过滤规则。
- 正式人物卡不再调用全书最多 500 条的旧 `GET /story-facts`。

## 5. 人物卡原子保存

新增：

```text
PUT /novels/{novel_id}/characters/{character_id}/workspace
Content-Type: application/json
schema_version = character-workspace-save/2
```

请求包含：

- `operation_key`；
- `expected_character_catalog_version`、`expected_story_ledger_version`；
- `expected_character_version`、`expected_instance_version`；
- 所选 timeline／instance；
- 可空的 `root_patch` 和完整版本化 `profile`。

事务规则：

1. 固定锁顺序为 Novel → NovelCharacter → CharacterInstance → 对应 revision 集合。
2. 服务端验证人物实例属于人物且在所选时间线有效。
3. 先把 `update_novel_character()` 中角色类型、姓名清洗、同名、active lifecycle、可见 `details_patch` 合并与字段错误映射抽成共享纯校验器；旧人物 PUT 和新 workspace PUT 必须调用同一个校验器。
4. 根变更经共享校验后复用 `save_character_root()`，实例变更复用 `save_character_instance_profile()`；子操作键分别使用 `cw2:root:<sha256(operation_key)>` 和 `cw2:profile:<sha256(operation_key)>`，避免外部 key 追加后缀后越界。禁止把可见 root patch 当成完整 `details` 覆盖未知扩展字段；`profile` 则必须是完整且通过 V1/V2 严格校验的文档。
5. 任一 CAS、字段、同名或唯一性校验失败时整个事务回滚，不允许部分保存。
6. 成功只提交一次并返回刷新后的 `CharacterWorkspaceV2`。
7. `root_patch` 与 `profile` 都为空时返回稳定 `no_changes`，不推进任何版本。
8. 现有人物根 PUT 和实例 profile PUT 继续保留给其他明确消费者；人物卡前端切换后不得再串行调用两者。

CAS 只作用于实际写入的聚合：只有 `root_patch` 非空时校验 character catalog／character version，只有 `profile` 非空时校验 story ledger／instance version。请求仍携带完整 workspace 基线便于统一错误 envelope，但未修改聚合的版本变化不能制造保存冲突。

错误 envelope 必须提供 `code / message / field_errors / current_workspace`。写事务失败后先 rollback，再以新只读事务读取 `current_workspace`；前端保留 draft，自动切到首个错误字段所在页签和分组，CAS 冲突不自动覆盖作者输入。

## 6. 事实修正与同步批次撤销

### 6.1 单条事实修正

新增：

```text
POST /novels/{novel_id}/story-facts/{fact_id}/corrections
schema_version = story-fact-correction/1
```

请求包含 `operation_key`、`expected_story_ledger_version`、`reason` 和 `replacement`。只允许修正有效状态为 `current` 或 `historical`、未被其他事实替代的事实；有来源时必须验证完整 revision、content hash 和证据区间，无来源的既有人工事实可修正但必须继续明确标记为“无来源”，不得补造章节证据。服务端固定复制原事实的 novel、timeline、stable entity、来源 revision／document 和证据区间，只允许替换协议允许的 predicate、object、details、dimension、event kind、故事位置与可见性。

提交事务：

1. 锁 Novel 和目标事实，验证目标仍在当前小说、仍可修正且来源范围一致。
2. 按 StoryFact v2 判别联合重新校验 details，拒绝跨类型或跨人物篡改。
3. `event_fingerprint = sha256("manual-correction-v1|novel_id|target_fact_id|operation_key")`，不把 replacement hash 放进唯一指纹；另计算覆盖 target、replacement 和 reason 的 `operation_hash`。
4. 重放时按唯一指纹读取 replacement fact，再读取其 supersedes link details：operation hash 相同返回既有结果，不同返回幂等冲突；并发首写由现有 `(novel_id, event_fingerprint)` 唯一索引裁决。
5. 创建新 StoryFact；若原事实有有效来源，则为新事实创建指向同一 chapter／revision／content hash 的独立 `DerivedSourceBinding`，复制其有效的 `current`／`source_restored` 来源语义，但 `proposal_item_id` 和 `commit_batch_id` 为空。没有来源的人工事实不得伪造 binding。
6. 创建 `source=new / target=old / link_type=supersedes` 的事件链接；修正理由、operation key 和 operation hash 写入 link details。新服务直接完成事实、binding 和 link 写入，不调用会自行推进 ledger 的公共 link API。
7. `story_ledger_version` 只推进一次；任何一步失败全部回滚。
8. 原事实、原来源绑定和原证据永不删除。

本轮不开放任意事实 CRUD。若作者只是要否定整次错误同步，使用批次撤销，不用伪造“空值替代事实”。

### 6.2 同步批次撤销

复用现有 `IntelligenceCommitBatch.inverse_operations`、`reverted_at`、StoryFact 状态和来源有效性，不新增第二套撤销账本：

```text
GET  /novels/{novel_id}/intelligence-commit-batches/{batch_id}/revert-impact
POST /novels/{novel_id}/intelligence-commit-batches/{batch_id}/revert
```

- POST 请求必须包含 `expected_story_ledger_version`；batch 自身是唯一撤销作用域，状态已为 `reverted` 时返回 replayed。
- 影响预览列出本批次事实、AI 创建／更新关系、后续 supersedes 链和当前来源 revision 状态。
- 只处理本批次实际创建并有该批次来源绑定的事实；指纹重放而复用的既有事实和其他批次来源不得被撤销。
- 撤销把 batch 设为 `reverted`、写 `reverted_at`，并把 batch-owned fact 的 status 设为 `superseded`；`DerivedSourceBinding.validity_state` 保持原来源状态，禁止用单条 binding 失效表达批次撤销，否则会连带污染同一 revision 的其他事实。
- `_reconcile_story_facts_for_revision()` 必须先读取 binding 对应 batch 状态：来源恢复时，已撤销 batch 的事实继续保持 `superseded`，不能被重新激活。
- 关系根和关系 revision 不删除、不倒拨。现有关系列表按有效 `relationship_state` fact 决定增量 AI 关系是否显示；批次事实撤销后重新投影即可隐藏仅由该批次支撑的 AI 关系，人工关系始终保留。
- 存在后续人工修正、其他有效来源或无法安全逆转的关系时，预览标记“保留”，服务端不得猜测回滚。
- 已撤销批次重复提交返回 replayed；恢复不自动执行，作者需要从当前章节重新发起同步和确认。
- 撤销与 ledger CAS、fact status、关系投影结果和 batch 状态属于同一事务；来源 binding 只保留审计，不在此事务中改为失效。

## 9. 性能、安全与兼容

- workspace V2 首屏只带当前摘要和最近 5 条变化，不内嵌全部历史。
- 全部事实使用服务端分页；同一人物、时间线和 cutoff 的摘要查询不得产生逐事实 N+1 文档／binding 查询。
- 目标为合成 500 条人物相关事实时，workspace V2 数据库查询数固定、响应 P95 小于 300ms；事实页每页 20 条响应 P95 小于 250ms。阈值在隔离本机环境记录，不伪装成跨机器 SLA。
- workspace／事实分页只返回至多 500 code points 的有界证据摘录，不返回整章内容；只有作者主动查看来源时才通过现有、同样执行小说范围校验的 revision GET 读取完整历史 revision。
- 修正理由最大 1000 字，事实文本和 details 沿用 StoryFact v2 上限；所有 JSON 由 Pydantic 严格校验。
- 来源定位必须同时验证 immutable revision ID、content hash、坐标版本和完整证据区间 hash；有界 excerpt 只用于预览和失败降级。加入 emoji／非 BMP 字符用例，禁止直接把 Python offset 传给 JS selection。
- 不增加依赖，不增加 Alembic 迁移。若 G0 证明仅靠 event fingerprint、现有 batch 字段和事件链接不能保证幂等审计，必须暂停并提交独立 schema 裁决，不能临时塞入无约束 JSON。
- V1 GET 和旧保存接口在兼容期保留；人物卡切换完成并通过调用者搜索前不得删除。

## 10. 恢复与发布策略

- 本计划无 schema 迁移，源码回退不需要数据库降级。
- 新写入的替代事实和 supersedes 链属于合法 StoryFact v2 历史；旧版本不认识写作摘要，但仍会按现有投影读取事实。
- 若 V2 UI 发布后出现问题，前端可以回退到 V1 读取和旧 UI；不得删除已产生的修正链。
- 人物卡原子保存失败时事务回滚；前端 draft 保留在内存，现有关闭确认继续生效。
- 长期环境安装前备份数据库和当前 PawApp 包；失败时恢复旧包，保留数据卷。
- 禁用／卸载 PawApp 后 QwenPaw 原生聊天、设置和 Agent 功能必须恢复，不残留路由包装。
