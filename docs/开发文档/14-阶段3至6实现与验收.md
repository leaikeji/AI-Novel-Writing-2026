# 阶段 3–6 实现与验收记录

执行日期：2026-08-23（Asia/Shanghai）。

状态：**阶段 3–6 已完成。QwenPaw 已激活 MiniMax M3，并完成真实小说讨论、只读工具调用、方向选择和章节规划闭环；AI 未修改正文。**

## 1. 本轮交付边界

本轮实现的是最小 MVP-0：

- PostgreSQL 18.6 + pgvector 0.8.6 权威账本。
- 小说、分卷、文档、working copy、不可变 revision、故事事实、向量分块占位和媒体元数据表。
- 创建小说、创建卷章、Markdown 源文本编辑、600ms 自动保存、手动检查点和历史恢复。
- IndexedDB 只保存尚未同步的崩溃恢复稿；恢复后自动重新走 CAS 保存。
- QwenPaw 原生聊天继续原样呈现；专用 `ai-novel-writer` Agent 启用六个项目 Skills。
- 三个只读类型化工具：`novel_get_context`、`novel_get_document`、`novel_search`。
- HTTP UI 与 Agent 工具共用 `backend/services.py`，没有第二套小说业务逻辑。

本轮明确没有实现 AI 正文写入、确认、Diff、候选版本、接受/拒绝、向量检索、TTS、图片、富文本或 Monaco 编辑器。

## 3. 数据与并发契约

```text
documents
  ├── document_working_copies
  │     当前可变正文 + draft_version + base_revision_id + content_hash
  └── document_revisions
        不可变检查点；恢复旧版时创建新的 revision，不回拨旧记录
```

自动保存请求必须携带 `expected_draft_version`。服务端对 working copy 加行锁并比较版本：

- 相等：写入、计算服务端 hash、`draft_version + 1`。
- 内容未变化：幂等返回，不制造空版本。
- 不相等：HTTP 409，响应包含服务器当前稿；绝不执行最后写入者覆盖。

正式正文的长期权威源是 PostgreSQL。IndexedDB 只保存尚未同步的浏览器恢复稿；同步成功后清除对应记录。`novel_chunks` 是后续可重建派生表，本轮没有生成或检索向量。

## 4. PawApp 与原生助手边界

```text
/apps/ai-novel-world-2026
  -> 作品库
  -> 创建小说
  -> /chat?novel_workbench=1&novel_id=...&document_id=...
       ├── 左：作品、分卷、章节
       ├── 中：Markdown 源文本、保存状态、历史
       └── 右：QwenPaw 原生 core.chat Inner
```

原生模型选择、消息、历史、输入框、Agent 选择和工具安全控制没有被复制或修改。当前 QwenPaw 公开前端契约没有提供“当前小说 ID 自动注入 Agent 会话”的接口，因此 MVP-0 使用“复制 AI 上下文”把明确的 `novel_id` 与 `document_id` 交给原生助手。三个工具只读且要求显式 UUID；后续若要自动绑定会话，必须先验证公开会话上下文能力，不能读取私有状态。

真实使用时发现 QwenPaw 会把新会话的 `/chat?...` 地址规范化为 `/chat/{session_id}` 并移除查询参数。插件现用 `sessionStorage` 保存当前工作台的小说、文档与原生会话路径；规范化后仍保持三栏布局，切换到其他原生会话时不会错误套用。该修复完全位于 PawApp 前端，没有覆盖上游路由。

切换 QwenPaw 当前 Agent 会回到普通 `/chat`，这是上游原生导航行为；重新从作品库打开工作台即可在所选 Agent 下继续。当前没有为了隐藏这一行为而覆写上游路由。

## 6. 失败恢复

- migration 失败：QwenPaw 仍可启动；迁移只由 `scripts/migrate.py` 显式执行，不放进插件 import/startup。
- 数据库不可用：编辑器内存和 IndexedDB 保留输入，PawApp API 健康状态降级，QwenPaw 原生控制台不受影响。
- 自动保存冲突：保留本地恢复稿并显示 409 冲突，不覆盖服务器正文。
- 插件构建或验证失败：安装脚本中止；三个 QwenPaw 命名卷和 PostgreSQL 数据卷不删除。
- 插件回退：使用固定上游基底重建容器；完整卸载必须走运行中官方插件 API，以执行 Skill/路由清理。
- 模型或工具失败：本轮 Agent 没有写正文工具，失败不会改变 working copy 或 revision。

## 7. 已核实事实、推断、建议和待验证

### 已核实事实

- 当前两个容器均为 `healthy`，主机端口只绑定 `127.0.0.1:18088` 和 `127.0.0.1:15432`。
- QwenPaw 2.1.0 在插件启动时把动态工具配置写入当时的 active Agent 模板；插件加载后新建的 Agent 会获得这些工具配置。阶段二提前创建且无聊天记录的小说 Agent 已通过公开 API 重建一次，随后重复安装保持幂等。
- 原生助手和小说工作台可以通过公开 `route.wrap("core.chat")` 同屏。
- MiniMax M3 能在原生助手中调用 PawApp 只读小说工具与 Skill，并保持“先讨论、后规划、不写回正文”的边界。
- 首轮真实创作暴露出三个可优化点：模型可能扩张作者指定的方案数量、对无法可靠核算的字数给出精确标签、把新构思的世界规则写得像既有事实。`novel-direction`、`chapter-outline` 和 `prose-writing` 已升级到 Skill 0.2.1，分别收紧数量/格式、候选设定标识、字数余量和重复工具调用。
- 更新后的同一创作会话继续请求“只给两个开场、每个不超过 80 字、不解释、不增加规则”时，MiniMax M3 返回恰好两个短开场，没有追加解释、没有新增世界规则，也没有重复读取小说上下文。该结果说明本轮行为方向正确；仍需在更多自然对话中区分明确提示和 Skill 本身各自的影响。
- 长正文继续暴露出模型行为波动：MiniMax M3 曾明显超过 600–800 字、加入未确认的档案规则和关键物件，并让时钟状态自相矛盾；重写时还错误声称已经删除实际仍存在的内容。所有这些草稿都只在聊天中，未写入正文。
- 根因核查发现“AI小说作家”仍使用 QwenPaw 默认工作区人设，且 `BOOTSTRAP.md` 持续注入首次设置说明。项目现通过官方 `/api/workspace/files` 与 `/api/workspace/system-prompt-files` 接口启用独立的 `AI_NOVEL_WORLD.md`，只负责把创作任务路由到六个 Skills；原生 `AGENTS.md`、`SOUL.md`、`PROFILE.md` 保持不变，`BOOTSTRAP.md` 改名归档而非删除。
- 新 Agent 路由启用后的全新会话中，一次正确执行 `novel_get_document -> prose-writing`，另一次只执行 `novel_get_document` 而跳过 Skill；说明 MiniMax M3 当前对 Skill 选择和“只输出正文”等约束的遵循仍有随机波动。工程配置已正确，模型质量尚不能靠提示词保证。

### 技术推断

- 在未验证公开会话绑定能力前，显式 ID + 只读工具是最小且可审计的上下文交接方式。
- 目前正文量很小时，基础关键词搜索足以验证 Agent 读上下文链路；它不能替代后续向量召回质量测试。

### 项目建议

- 下一轮以《封存区没有明天》的连续创作对话迭代六个 Skills，优先观察上下文准确性、重复建议和长会话稳定性。
- 在真实讨论暴露明确痛点前，不加入 Diff、确认、AI 写回、向量服务或 TTS。
- 保留当前验收样书，作为后续模型与 Skill 回归样本。
