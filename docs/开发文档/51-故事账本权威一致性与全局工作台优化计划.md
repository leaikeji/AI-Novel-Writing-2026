## 0. 复查结论

原账本优化思路必须按当前实现重新裁剪，不能直接开工。计划 46 和计划 48 已经交付了人物卡四栏目、人物范围当前状态、事实历史分页、来源证据、“新事实 + supersedes”修正、批次撤销、原子保存、CAS、宿主主题隔离和嵌套抽屉焦点闭环。这些能力是现行基线，不重建。

本计划只解决十二类仍然由当前代码、文档和页面证明存在的问题：

1. 不同后端读模型对“当前有效事实”使用不同的聚合规则，且章节 revision 对账同时改两套状态；人物卡虽已区分“有效生命周期”和“冲突健康度”两条轴，但计划不能把它们再合并成一个枚举。
2. `story_ledger_version` 现已被事实、时间线、连接、映射、人物实例等多类权威故事状态共同使用；部分路径的加一、无变化和客户端预期版本语义仍未统一，不能再把它窄化为“有效事实集版本”。
3. 模型明确返回无变化或归一化结果为空时，服务端仍可以伪造“人物在本章出现”事实。
4. 现有 UI 只能从人物卡看人物范围的账本；世界、关系、故事线、伏笔、时间和通用事实没有一个统一、可解释、可纠错的全书入口。
5. 当前人物卡已经可用，但多值状态、来源长文、行内动作、筛选和底部操作区仍显得沉重，时间线页面也没有接入后端已有的合并、连接和 revision 映射能力。
6. QwenPaw 左侧导航和右侧原生助手同时展开时，PawApp 中间工作区可以被压缩到约 380px；当前人物页响应式主要依赖外层 viewport media query，外层仍宽于断点时，中栏已经出现纵向碎字和信息不可读，属于工作台容器级系统问题。
7. 全书账本若直接沿用现有人物事实列表，会继承伪语义表格、弱游标一致性、来源证据首屏不聚焦和读写版本漂移；这些必须在 API／UI 契约冻结时一并解决，不能等页面完成后补洞。
8. 根 `README.md` 仍写“当前已应用”的迁移链到 `20260830_0035`，而当前候选源码 head 已推进到 `20260902_0037`；两者分别是长期已应用状态与候选源码 head，不能直接互相覆盖。
9. 计划 50 当前处于前端播放器 W1，实际改动集中在 narration 与 `workbench-v2.ts`；把它扩张成“计划 50 未全部完成前，计划 51 的 G0／后端 W1 一律不能开始”缺少文件和资源冲突证据，会造成不必要的全局串行。
10. 现有人物事实 endpoint 的“分页”会先加载全书 StoryFact 投影、事件链接、来源绑定和人物相关事实，在 Python 内存中分类、筛选、排序后才切 `limit`；这不是数据库有界分页，不能直接扩成全书账本。
11. 关系、故事线、伏笔和人物名称等会改变账本列表、详情或 assistant context 的权威根数据存在独立版本／写入口，其中多条写路径既不读取也不推进 `story_ledger_version`。如果读取时继续实时 join 这些根数据，仅凭当前账本版本无法保证稳定快照。
12. 前端人物修正／批次撤销每次提交尝试都会生成新 `operation_key`，超时后的精确重试无法命中后端幂等回放；“加载更多”和批次影响预览也缺少完整的 generation／取消隔离，时间线组件的本地账本版本不会随新 props 或普通 refresh 重新同步。

核心裁决：**先修正现有 StoryFact + DerivedSourceBinding + StoryEventLink 模型的共享解析、版本和写入语义，冻结能覆盖实时根数据的完整快照边界；再实现数据库有界的全书账本读取，提取一套前端账本共享能力并解决宿主挤压下的容器响应；不预先增加第二套 Adoption 表、通用 Operation 表、新队列或新缓存基础设施。** 只有 `L51-G0` 的隔离 PostgreSQL 只读体检和真实查询计划证明现有结构无法表达语义或达到有界查询门禁时，才允许提出窄迁移／索引和 ADR 复裁。跨计划排程按“当前工作包 + 精确文件 + 实际运行资源”加锁，不把整份计划的进行中状态当作全生命周期互斥锁。

## 2. 后端冲突、缺口与决策

### 2.1 `no_changes` 与服务端伪造事实冲突（P0）

提取协议允许 `{"no_changes": true, "items": []}`，提示词也明确要求“不要为了满足数量制造情报”。但 `_fallback_character_presence_candidates` 会在归一化结果为空时，按人名字面出现自动生成“在本章正文中出现”的 `character_state` 候选。这会把“没有可记录变化”替换成虚假状态事实。

决策：删除 fallback 函数、调用和仅为它存在的测试；保留 proposal `ready + empty/no_changes` 的已有 UI 语义。不用新的空结果数据库状态增加重量。

### 2.2 事实解析规则分裂，但现有两条展示轴必须保留（P0）

`_reconcile_story_facts_for_revision` 同时改 `DerivedSourceBinding.validity_state` 和 `StoryFact.status`。当前消费者又使用不同规则：

- Context V3 按 revision 记录最后一个 binding 结果；
- Context V4 和 story-state persistence 按 revision 对多个 binding 做 AND；
- story-state engine 先看 `StoryFact.status`，再看 source revision validity；
- 人物卡 service 已经是更安全的“按 fact 聚合 binding”。

同一 revision 上一条失效 binding 不应把其他事实整批污染，不同上下文加载器也不应对同一事实得出不同结论。

人物卡当前并不是一个简单枚举：`effective_state` 已输出 `current / historical / superseded / source_invalid / batch_reverted`，`health` 另行输出 `ok / conflict / ambiguous`。两者是正交维度；例如一个来源仍有效的当前事实仍可能冲突，不能为了“统一”而压成单轴。

决策：从人物卡现有实现抽出 fact-specific 的共享解析契约，但分层输出：

1. 权威／纳入轴：根据事实自身生命周期、supersedes、按 fact 聚合的 binding validity 和批次状态，输出 `included_in_current_projection`、`effective_state` 与稳定 `reason_codes`；
2. 健康轴：根据冻结的冲突／歧义输入独立输出 `health`，不得让 `source_invalid` 取代 `conflict/ambiguous`，也不得让健康度决定事实生命周期；
3. Context V3/V4、story-state projection、embedding、人物卡和全书账本统一消费同一“是否纳入当前投影”结果；需要面向作者展示时同时返回两条轴。

`StoryFact.status` 只描述事实自身生命周期，source revision 有效性由 binding 表达；batch revert 与 supersedes 的优先级、混合 binding 的规则、健康分类输入和 reason code 在 `L51-G0` 用矩阵冻结。

### 2.3 账本版本的实际作用域比“有效事实集”更宽（P0）

当前源码在 `backend/services.py`、`story_state/persistence.py`、`revisions.py` 和 `corrections.py` 多处推进 `Novel.story_ledger_version`；它已保护事实、时间线 patch／link／merge、revision mapping、人物实例及纠错／撤销等权威故事状态。章节候选接纳、checkpoint 和 restore 仍存在 changed flag、加一次或不加、客户端预期版本不完整的问题；章节情报提交请求只有 `accepted_item_ids` 和前端一直传空的 `item_overrides`，没有客户端期望账本版本。

第五次复查还确认，不能只搜索当前已经读写 `story_ledger_version` 的函数：关系 create/update/archive/restore/batch、故事线 create/update/delete、伏笔 create/update/delete 以及人物名称等根数据会改变账本行标签、详情、投影或 assistant context，但这些入口目前使用各自版本或直接提交。如果账本读取实时 join 这些根，账本版本不变时页面内容仍可能变化。

决策：

1. G0 既列出所有读、校验和加一位置，也从 API／领域命令反向列出**所有会改变账本呈现或上下文的权威写入口**；关系、故事线、伏笔、人物目录和 document revision 写链即使当前没有版本引用也必须入表，不得只搜索 `backend/services.py` 或 `story_ledger_version` 后宣称覆盖全链；
2. G0 冻结一种且仅一种完整快照方案：要么把所有会改变账本读取结果的权威根变化纳入聚合账本版本，要么让账本行只读不可变 fact/source 快照并使用包含账本、人物目录及其他必要根版本的 opaque 复合 `ledger_snapshot_token`。禁止一边实时 join 根数据，一边继续把单一旧版本声称为稳定快照；
3. 所有属于冻结矩阵的命令在一个事务中锁定正确的聚合根，实际权威状态变化每个业务事务精确推进一次对应快照；同值 patch、精确重复和其他 no-op 不推进；纯 UI 偏好必须明确排除；
4. reconcile 返回结构化 changed result，而不是让不同调用者猜测；章节提交、采用、checkpoint、restore、时间线／映射、人物实例、修正和批次撤销统一校验冻结的预期快照，返回当前 token／版本和可理解的 409 冲突；
5. 命令幂等优先级统一为：同 `operation_key` + 同 canonical payload 先回放成功结果，再做版本冲突判断；同 key + 不同 payload 返回 `idempotency_conflict`；新 key + 过期快照返回版本冲突。当前修正命令已基本符合该顺序，批次撤销的已撤销分支还没有核对 key／payload，必须补齐；
6. 暂不增加通用 operation 表，继续使用已有 commit key、batch 和命令幂等证据；现有对外契约不得因内部收敛丢失恢复能力。

### 2.4 精确重复提交语义模糊（P1）

现有 `event_fingerprint` 包含 source revision 和原文坐标，是“证据发生”指纹，不是跨 revision 语义去重指纹。当指纹已存在时，当前提交会把 item 记为 accepted 并指向旧 fact，却不一定新建 provenance，batch inverse 也可能是空的。关系候选还会在查重 fact 之前先物化关系；一个没有 created fact 的空 inverse batch 仍可进入 committed，随后批次撤销会把它改为 reverted 并无条件推进账本版本。

决策：保持当前 fingerprint 定义，不做自动跨 revision 语义合并。关系物化和 fact 查重必须按冻结事务语义排序，不能让“fact 无变化”掩盖关系变化；任何实际关系 create/update 都必须进入 inverse evidence 并精确推进一次快照。对精确重复明确返回 `already_committed/no_change`，不记成新写入、不推进账本版本；可以不创建 batch，或只保留明确不可撤销的 no-op receipt，但禁止生成可被“空撤销”推进版本的 committed 空批次。若产品要求保留第二个证据发生，则必须同时新建 binding 并给 batch 可逆证据，不得静默接纳。

### 2.5 当前可确认的凑余与历史数据边界（P1）

以下项目进入删除候选，但必须在替代路径落地、全库调用者搜索、公共契约分类和数据等值体检后分流到 `L51-CLEAN-INTERNAL`、`L51-MIG-COMPAT` 或 `L51-CLEAN-COMPAT` 安全清理：

- `_fallback_character_presence_candidates` 及专用测试；
- 章节情报提交 DTO 中前端始终传 `{}` 的 `item_overrides`；
- `CharacterRelationship.relation_type` 对 `label` 的兼容别名及前后端 fallback；
- 只支持 `story_fact` 的 `DerivedSourceBinding.derived_entity_type`；
- 只有旧测试使用的弃用关系同步包装器 `sync_relationships_from_intelligence_proposal`；
- 无当前仓库前端调用者的旧 `GET /novels/{novel_id}/story-facts`；`rg` 不能证明不存在外部插件客户端，G0 必须先判断它是否属于已公开／已文档化契约。若为内部未发布端点则同版本删除；若为公开端点则只保留一个带移除版本／日期、调用证据和契约测试的兼容窗口，并在窗口结束删除，不得无限双轨；
- 旧事实端点移除后，`presenters.ts` 中仅为原事实墙服务的 fact helper／测试和孤立 `StoryFactRecord` 类型。

公共契约分类必须应用到上面**每一项**，不能只审旧 endpoint：请求字段 `item_overrides`、响应／请求兼容字段 `relation_type`、固定值列 `derived_entity_type` 和旧包装器都要分别核对文档、已发布包、外部调用、数据库数据和恢复路径。内部私有凑余在替代完成并通过回归后同版本删除；公开契约只能按已冻结的有限窗口删除。

删除未来 fallback 不等于可以直接删除历史数据。现有记录没有专门的“由 fallback 生成”来源标志；G0 只能用精确 payload 形状、proposal／model 证据、source binding 和批次信息生成“高可信候选／歧义候选”只读报告，不能仅凭文案模式自动删事实。高可信错误也先进入作者可审阅修复提案；真实数据清理仍需精确目标、备份、恢复方案和单独授权。

以下不是凑余，不得在本计划删除：`committed_story_fact_id`、`accepted_item_ids`、`inverse_operations`、`no_changes`、StoryFact 来源快照字段、规划状态／进度字段、Provider 历史兼容字段、负向／恢复／兼容测试和已执行迁移。

### 2.6 现有人物事实“分页”不是数据库有界读取（P0）

`CharacterWorkspaceService.list_facts` 当前先调用全书 `projection()`，再读取人物及关系范围的全部事实与关联证据，在 Python 中完成分类、筛选、排序，最后才执行 `facts[:limit]`。其依赖的 `get_story_projection_payload` 又会加载当前小说全部 StoryFact v2、全部 StoryEventLink 和相关全部 DerivedSourceBinding。现有 page DTO 也没有快照 token／版本或筛选指纹。即使 UI 每次只显示 20 条，请求的数据库读取、内存占用和一致性都没有被页大小约束。

决策：全书账本 API 不复用这条全量投影路径作为分页实现；人物历史也在共享读取落地后迁到同一有界服务。冻结的查询流程至少满足：

1. 数据库先按作品范围、冻结筛选和稳定排序／cursor 选出本页 fact IDs，不扫描后在 Python 切页；
2. 只对本页 IDs 批量加载 binding、event link、实体显示快照和批次证据，不做逐行 N+1；summary 使用独立、可解释且有界的聚合查询，不以“把所有行拉进内存”换准确；
3. token 捕获、筛选查询和本页 enrichment 必须处于同一可证明的数据库读取快照中，可使用只读 repeatable-read、单语句／CTE 或查询后原子复核 token 等 G0 冻结方案；禁止“先读版本、并发写入、再读页面”却仍返回旧 token 的 check-then-read 竞态，也不得让外部模型／网络调用占用事务；
4. page response 返回 opaque 快照 token、筛选指纹和稳定 next cursor；跨 token／筛选的 late page 不能被追加；
5. G0 用 500／2,000／10,000 分布样本记录 SQL 数、返回行数、内存和 `EXPLAIN (ANALYZE, BUFFERS)`。当前 StoryFact 索引只覆盖少数 timeline／type／status／character-instance 组合；只有真实查询计划证明必要时才提出窄索引迁移，不凭字段列表预建一串索引。

## 3. 前端系统与 UI 复查

### 3.1 保留现有人物卡的职责

人物卡继续作为人物范围的写作前快照，不变成全书账本页：

- “当前写作状态”用于 5 秒内完成续写前校准；
- “最近变化”保留最近 5 条；
- “全部事实”继续惰性分页；
- 来源、修正和批次撤销复用全局账本的共享组件和命令契约；
- 人物卡的四栏目、浅色局部表面和焦点闭环不重做。

### 3.2 现有人物卡需要的轻量收口

1. **多值状态减重**：当前 `slot.values` 全部用分号拼接，“已知信息”可以无上限拉高页面。默认显示前 3 条和“共 N 条／查看全部”，单值设置有界截断，完整内容仍可展开。
2. **缺失维度如实呈现**：当前核对摘要只统计冲突、不确定和来源失效，即使大部分维度缺失也会显示“没有待核对项”。加入中性的“已记录 X/8，Y 项尚无事实”，不把缺失强行标红或计入待办 badge。
3. **来源证据先聚焦**：当前完整 chapter revision 全量渲染，高亮可能在屏幕下方。打开后先显示安全有界摘录并自动将焦点／滚动定位到 `<mark>`，作者点击“查看全文上下文”后再展开不可变 revision。
4. **筛选补齐**：在生命周期和健康度之外，补维度和来源文档筛选；文本检索只在服务端有明确分页／索引策略后接入，不在前端对已加载小部分数据做伪全局搜索。
5. **行内动作降噪**：每行保留一个主“查看”动作，修正和批次撤销收入明确标签的“更多”菜单；键盘路径和 `aria` 名称必须完整。
6. **批次撤销不再伪装成单行动作**：按 commit batch／来源章节分组，预览统一显示“撤销第 N 章同步批次，影响 X 条事实、Y 条关系”；每行不重复展示像是只撤销该条的文案。
7. **修正抽屉显示可证明的真实影响**：保留纠错理由和“新事实取代旧事实”语义，影响预览只返回可从持久数据精确计算的当前时间线投影影响（是／否及数量）、相关事件链接数、是否需要重建 embedding、批次事实／关系数量；运行时 context 是临时装配结果，不伪造“受影响上下文条数”。
8. **页脚只显示当前可用动作**：“状态与经历”是只读栏目，干净状态下隐藏“撤销修改／保存人物卡”，仅保留关闭和状态说明；其他栏目只在 dirty 时显示保存组。
9. **精确重试复用幂等键**：修正／批次撤销在打开命令草稿时生成稳定 `operation_key`，同一 canonical payload 的超时／断线重试必须复用；作者改变 payload 后建立新草稿／新 key，成功、显式取消或目标切换后才释放旧 key。禁止在每次点击提交时临时生成新 key。
10. **所有异步分支有代次隔离**：首次历史加载、加载更多、来源读取、批次影响预览和写命令完成都绑定 novel／timeline／instance／filter／target／snapshot identity，并使用 AbortController 或 generation fence。目标、筛选、抽屉或作品变化后，旧响应不得追加旧页、打开错误抽屉或覆盖新 workspace。

### 3.3 新增全书级“故事账本”工作台

账本不放入“设置”，应作为 **PawApp 内部**工作台一级阅读／管理区域，与章节、大纲、人物、伏笔并列；不得占用 QwenPaw 宿主全局导航。当前内部导航已有 6 项，增加第 7 项后必须在短高度保持全部 section 和“返回创作中心”可滚动、可达。它不是新的通用后台管理台，只服务作者对当前作品的查看、核对和明确修正。

信息架构：

1. **总览**：当前有效、历史、冲突／不确定、来源失效、已撤销数量，以及账本 snapshot／诊断版本和当前时间线。
2. **事实列表**：按时间线、事实类型、实体、维度、生命周期、健康度、来源章节和批次组合筛选，服务端游标分页。
3. **事实详情**：结构化内容、有效性解释、事件链接、不可变来源、提案／批次、被哪些当前投影消费。
4. **核对队列**：只聚合冲突、不确定和来源失效；缺失维度作为中性覆盖率，不自动变成错误。
5. **作者动作**：核心版本提供查看来源、修正和批次撤销；有类型的手工增加事实放入 P1 后续波次，必须沿用候选／作者命令、CAS 和作品范围校验，不提供原始 JSON 编辑或静默覆盖。

覆盖范围不得只按当前人物样例反推。G0 必须冻结 StoryFact 类型／实体矩阵，至少覆盖 `character_state`、`relationship_state`、`storyline_event`、`foreshadow_event`、`story_time`、`knowledge_event`、`world_state` 和 `general_fact`；无实体 ID、实体已删除或仅有来源快照时也要有可解释显示与筛选规则，不能丢行或伪造实体。

读取一致性使用 G0 冻结的完整 `ledger_snapshot_token`；若 G0 证明扩张后的单一 `story_ledger_version` 已覆盖所有会改变返回内容的根写入，token 可以编码该版本，否则必须编码账本、人物目录和其他必要根版本。summary、list、detail、source 和 impact preview 都返回同一口径 token，并可同时返回面向诊断的 `story_ledger_version`；每个响应的 token 与正文必须来自同一数据库读取快照，不能存在 check-then-read 窗口。游标至少绑定稳定排序键、筛选指纹和 token。翻页时 token 或筛选变化不得把两个快照混成同一列表，应返回有类型的 `stale_page`／409 或经 G0 冻结的明确刷新结果。影响预览返回 `preview_snapshot_token`，最终命令使用匹配的 expected token／版本；前端冲突刷新要保留筛选和选中上下文，并告知作者数据已经更新。

共享前端边界：先把人物卡现有来源查看、修正、批次预览和状态标签 **提取／移动** 到 `frontend/src/story-ledger/`，再由人物卡轻量 wrapper 和全书账本共同消费；旧副本在调用者切换并通过回归后删除，不复制成两套。该目录同时承载 ledger contract、API、filter model 和共享写命令，禁止两份 DTO、两套状态标签或两套业务逻辑继续漂移。

跨入口联动：人物事实数量／风险摘要可深链到预筛选账本；时间线可深链到对应 timeline filter；来源和修正统一打开共享详情，不再各自维护抽屉协议。

原生助手边界：增加账本 section 后同步更新 `WORKBENCH_SECTIONS` 和 assistant studio context 集成测试。冻结单独的账本 context envelope，只允许作品 ID／标题、`section="ledger"`、时间线 ID／名称、规范化筛选摘要、选中 fact ID，以及经过长度上限与敏感字段排除的短摘要／哈希；schema 直接禁止 `source_excerpt`、完整 `object_text`、完整账本、完整章节来源和可编辑字段。来源正文只在作者明确动作后按既有公开契约提供，不能靠前端约定“尽量少传”。

列表可访问性：先删除现有不完整的 `div role="table"`／`article role="row"` 混合语义；宽容器若按列对齐则使用带列标题、行／单元格和正确阅读顺序的真实语义表格，窄容器切换为带字段标签的卡片。若 G0 选择所有尺寸均为记录列表，则移除全部 table role。更多菜单必须支持键盘、可读名称、焦点返回；筛选控件有显式 label，异步加载／冲突／完成状态有适度 live announcement。本计划只承诺覆盖这些路径，不在只读截图复查阶段宣称整页 WCAG 合规。

### 3.4 工作台容器响应（核心系统门禁）

- 不强制或自动折叠 QwenPaw 原生助手；PawApp 必须适应宿主左右栏的合法组合。
- 以 `.anw-workbench-main`／`.mb-workbench-main` 的实际可用宽度驱动角色、账本和时间线的布局降级，不能只依赖外层 viewport。实现可使用命名 container query 或等价的稳定容器状态，但须复用现有 token 和工作台密度机制。
- 中栏变窄时优先切换单列、卡片和可滚动局部区域，不允许正文逐字纵排、操作按钮互相挤压或靠隐藏核心内容“修复”。
- 今后的真实浏览器桌面验收固定使用 **1080P（1920×1080）和 2K（2560×1440）** 两档，并在每一档同一目标 viewport 下分别测试助手展开／折叠；宿主左栏、短高度、键盘焦点和 200% 等效窄屏继续由自动化／诊断路径覆盖。若工具不能改变真实浏览器 zoom，必须明确记录限制，不得把等效窄屏写成真实 200% zoom。
- 因 `styles.ts` 与工作台 shell 是系统共享面，基础 smoke 必须覆盖章节、大纲、人物、伏笔、设定、朗读和新增账本全部 section；人物／账本／时间线做深验收，朗读与计划 50 协调所有权和回归，不能用三个目标页通过来推断其他 section 无回归。

### 3.5 时间线与账本联动

前端当前只接了 list／fork／character instances，后端已经提供 timeline patch、timeline links、merge、story-event links、story-state projection 和 revision timeline mapping。本计划复用已有后端，不重建第二套时间线服务。

源码复查确认，现有 `StoryTimelineWorkspace` 只在首次渲染用 `initialStoryLedgerVersion` 初始化本地 state，props 更新时不会同步；普通 `refresh()` 的 list response 也不返回／刷新账本快照，因此其他入口变更账本后再 fork 可能携带旧版本。时间线切换虽然声明了 `role="tablist"`／`role="tab"`，却用 `aria-current` 代替 `aria-selected`，也没有关联 tabpanel 和方向键／roving tabindex 契约。

- 单时间线：全书账本默认使用主线，隐藏持久选择器。
- 多时间线：在工作台层级保持当前 timeline context，账本、人物卡、投影和 revision 映射统一使用它；不沿用“最近一次选择”静默猜测。
- 账本快照由工作台共享状态唯一持有；novel 变化、外部 mutation 成功或 refresh 返回新 token 时同步时间线，不能由子组件长期保留只在 mount 时取值的私有版本。过期 fork 返回冲突后刷新 timeline／snapshot，并保留作者已输入的分支名供确认重试。
- 多线切换使用完整 tabs 契约（`aria-selected`、关联 panel、可见焦点和方向键／roving tabindex），或若内容不是 tabpanel 就移除 tab role，改为语义明确的选择列表；禁止继续混用 `role="tab"` 与 `aria-current`。
- 核心版本先完成 timeline context、筛选深链和当前 projection 的可解释读取；“时间线与人物实例”的 link／merge／revision mapping 写 UI 放入 P1 后续波次。若 G0 证明已有真实多时间线数据依赖这些能力，才升级为核心门禁；合并前必须预览将影响的账本投影和冲突，不做一键静默合并。

## 4. 目标、非目标与冻结契约

### 4.1 目标

- 同一 fact 在 Context V3/V4、投影、嵌入、人物卡和全书账本中使用同一权威纳入结果；面向作者时保留独立的 effective-state 与 health 两条轴。
- 所有纳入冻结快照矩阵的权威故事状态变化，每个业务事务精确推进一次对应快照；无变化操作不推进，任何实时 join 根变化都不能绕过快照。
- 所有作者可见写操作都有 CAS、幂等或批次证据、可恢复路径和可理解冲突。
- 全书与人物事实分页的数据库读取、SQL 数和内存受页大小／冻结聚合策略约束，不再先全量投影后内存切页。
- 人物卡保持轻量，全书账本提供统一审计和纠错入口。
- 工作台在 QwenPaw 左右栏合法组合下按中间容器宽度降级，原生助手展开时核心内容仍可读、可操作。
- 确认没有调用者、没有独立契约价值的凑余在替代完成后立即删除，不继续双轨。

### 4.2 非目标

- 不修改 QwenPaw 上游核心代码、私有配置或私有数据库结构。
- 不重新设计人物卡四栏目、关系网、伏笔页或原生聊天。
- 不自动合并语义相似但证据不同的事实。
- 不引入新模型选择器、通用 Agent Runtime、任务队列、第二个数据库或向量系统。
- 不对真实小说做自动修正、撤销、restore 或批量数据清洗。

### 4.3 `L51-G0` 必须冻结的共享契约

- 权威纳入／effective-state 与 health 两轴的输入、输出、优先级和解释 reason code，禁止合并枚举；
- `StoryFact.status` 与 `DerivedSourceBinding.validity_state` 的唯一分工；
- 全库 `story_ledger_version` 读取／校验／加一清单，以及所有会改变账本呈现但当前没有版本引用的关系、故事线、伏笔、人物目录和 document revision 写入口；冻结受保护命令矩阵、事务边界、no-op 和每事务一次规则；
- 单一扩张账本版本或 opaque 复合 `ledger_snapshot_token` 的选择、组成、返回／校验位置、同一数据库读取快照方案和实时根 join 边界；禁止返回内容可变而 token 不变，禁止版本检查与页面读取之间的并发竞态；
- expected snapshot／`expected_story_ledger_version`、canonical payload hash、幂等键精确回放／冲突优先级、无变化结果和 409／`stale_page` 错误契约；
- 全书账本类型／实体覆盖矩阵，以及 list/detail/summary/source/correction/batch-preview 的 DTO、快照 token 与筛选绑定游标；
- 数据库有界分页／summary 查询形状、每页批量 enrichment、SQL 数／内存预算和 500／2,000／10,000 查询计划基线；是否新增索引只能由 `EXPLAIN (ANALYZE, BUFFERS)` 证据决定；
- 历史 fallback 候选的只读识别分级、作者修复和禁止自动删除边界；
- 每个删除候选的内部／公开／数据兼容分类、替代路径和明确移除时点；
- “源码迁移 head”与“长期环境已应用 head”的独立证据字段和文档措辞，禁止用其中一个推断另一个；
- 多时间线工作台 context 及单线零配置规则；
- 前端稳定 operation key 生命周期、所有 append／preview／source／mutation 的 generation／取消协议，以及时间线共享 snapshot 同步和 tabs 语义；
- PawApp 内部账本 section、深链参数、禁止来源正文的原生助手 context envelope，以及覆盖全部工作台 section 的容器响应断点／状态契约；
