# 架构边界与模型接入决策

## ADR-001：Portkey 从默认组件降为可选网关

状态：已采纳。

**项目建议**：MVP 的聊天模型直接通过 QwenPaw Provider 配置。Portkey 不进入默认 Compose profile，只有出现以下可复现需求时才启用：

- 多供应商自动故障切换；
- 集中限流、预算和调用观测；
- QwenPaw Provider 无法表达的路由或请求转换；
- 多个应用需要共享统一网关策略。

原因：QwenPaw 已有聊天模型配置、密钥、Provider 和工具调用链。个人单机 MVP 再默认部署 Portkey 会增加服务、配置和排障面，却不直接改善小说写作闭环。Portkey 1.15.2 仍是兼容的 OpenAI 风格网关，可在需要时插入 QwenPaw `OpenAIProvider` 的 `base_url` 和自定义请求头，不需要业务代码依赖其私有 SDK。

最小兼容面只有 OpenAI chat-completions 协议：QwenPaw 自定义 Provider 配置 `base_url=http://portkey:8787/v1`、模型 ID、服务端 API Key 和 Portkey 所需自定义请求头；Portkey 再负责上游供应商路由。小说 PawApp 看不到 Portkey 配置，也不直接调用其 SDK。阶段二只在启用可选 profile 时做一次流式文本、tool-call、错误码和取消传播契约测试。

## ADR-002：哪些模型能力能交给 QwenPaw

| 能力 | QwenPaw 2.1.0 已核实能力 | 小说工作台方案 |
|---|---|---|
| 聊天大模型 | Provider 页面、流式聊天、工具调用、密钥和自定义 OpenAI 兼容地址 | **完全交给 QwenPaw**；PawApp 通过官方聊天上下文调用 |
| Skills | 官方 Skill 机制和插件 Skill provider | **完全交给 QwenPaw**；插件首期提供六类可演进的小说 Skills |
| MCP | QwenPaw 负责 MCP 会话和工具；内部小说能力无需 MCP | **完全交给 QwenPaw**；小说内部能力注册为 PawApp 原生工具 |
| Embedding | 支持多类配置，但当前只由 ReMeLight 记忆消费；官方说明没有通用 PawApp Embedding API | QwenPaw 继续管理自己的记忆向量；小说 `novel_chunks` 由项目自有 `DashScopeEmbeddingAdapter` 调用设置页配置的阿里云百炼原生接口 |
| 图片 | 上游有 `qwen-image` 工具插件，Creator PawApp 也有自己的图片实现；不是通用 PawApp 模型服务 | 核心写作 MVP 完成后优先评估调用官方工具；小说仍负责结果下载、持久化和 `media_assets` |
| TTS | Creator PawApp 内有 DashScope/CosyVoice 专用实现，SIP channel 也有语音逻辑；没有通用 PawApp TTS 服务 | 保留 `TTSAdapter`；多角色朗读专题优先验证本地 MOSS-TTS-Nano ONNX，并由小说插件持久化版本与音频；物理执行形态由专题阶段 0 决定 |

**已核实事实**：QwenPaw 官方 Embedding 文档明确写明当前直接接入方是 ReMeLight、没有通用 Embedding API，且当前只有 ReMeLight 消费这套配置。参见 [QwenPaw 2.1.0 Embedding 文档](https://github.com/agentscope-ai/QwenPaw/blob/v2.1.0/website/public/docs/embedding.zh.md)。

**已核实事实**：QwenPaw Creator 的 Embedding 和 TTS 客户端放在 Creator PawApp 自己的后端目录中，说明它们是应用级实现而非宿主公共服务。参见 [Creator Embedding 实现](https://github.com/agentscope-ai/QwenPaw/blob/v2.1.0/plugins/apps/qwenpaw-creator/backend/models/embedding_model.py)和 [Creator TTS 实现](https://github.com/agentscope-ai/QwenPaw/blob/v2.1.0/plugins/apps/qwenpaw-creator/backend/models/tts_model.py)。

**技术推断**：让小说 PawApp 直接导入这些内部模块、读取 QwenPaw 私有配置文件或调用未公开内部路由，都会把插件绑定到上游实现细节，违反“不修改上游、只用公开接口”的边界。因此当前不能为了“一处配置”牺牲升级隔离。

**项目建议**：聊天不再命名为通用 `ChatModelAdapter`，避免暗示小说插件会直接调用或替代 QwenPaw Provider。改为一个只包装 PawApp 公共聊天上下文的网关；非聊天模型继续使用窄适配器：

```text
PawAppAgentChatGateway
  └── ctx.chat_stream() / ctx.chat()（唯一 MVP 实现）

EmbeddingAdapter
  └── DashScopeEmbeddingAdapter（固定阿里云百炼原生 HTTP 协议）

TTSAdapter
  ├── MossNanoTTSAdapter（多角色朗读专题首选，本地 ONNX，阶段 0 后定物理拓扑）
  └── 其他供应商适配器仅在另行审批后增加

ImageGenerationAdapter
  └── MVP 后续图片阶段；优先评估 QwenPaw 官方 qwen-image 工具

MediaStorage
  └── LocalMountedMediaStorage（MVP）
```

这些接口不是第二套 Agent Runtime；它们只隔离供应商 HTTP/SDK 差异。Agent 自主决策、会话和工具调用仍全部在 QwenPaw。

**项目决策**：小说 Embedding 配置出现在小说 PawApp 自己的“向量检索与索引”设置页，不复用 QwenPaw 全局 Embedding 页面，也不建立第二个设置网站。Base URL、write-only API Key、候选模型和受支持维度由项目领域服务管理，实际调用仍由小说 PawApp 的窄适配器完成；页面只显示“已配置”或数据库已有末四位掩码，不返回完整 Key 或末八位。详细安全与切换规则见[第24号专项计划](./24-小说语义检索与向量模型专项施工计划.md)。

## ADR-003：MVP 使用 Monaco 编辑 Markdown 源文本

状态：已采纳。

**项目建议**：富文本/WYSIWYG 暂缓。MVP 使用 Monaco Editor 编辑 Markdown 源文本，预览由独立只读区域渲染；正式 revision 保存 Markdown 源码，预览 HTML 不是权威数据，也不回写正文。

这与 VS Code 的使用模式一致：编辑 `.md` 时操作 Markdown 源码，预览作为独立视图或并排视图实时渲染。参见 [VS Code 官方 Markdown 文档](https://code.visualstudio.com/docs/languages/markdown)。Monaco 是微软维护的浏览器代码编辑器，与 VS Code 编辑器核心同源，但它不是完整 VS Code 工作台，也不会自动带上 VS Code 的全部 Markdown 扩展、命令和预览实现。参见 [Monaco Editor 官方仓库](https://github.com/microsoft/monaco-editor)和 [0.56.0 release](https://github.com/microsoft/monaco-editor/releases/tag/v0.56.0)。

实现边界：

- 使用 `monaco-editor` 公共 ESM API，不访问内部模块。
- 不使用额外 React wrapper；由 PawApp React 组件直接管理 Monaco 实例生命周期。
- Markdown 预览使用独立解析器并经过 DOM 净化，默认禁用脚本和危险 HTML。
- 自动保存、revision 冲突和 AI Diff 都针对 Markdown 源文本。
- 首期不实现粗体按钮、块级拖拽、富文本粘贴保真和 ProseMirror schema。

## ADR-004：向量模型不设允许列表（已被替代）

状态：**历史决策，已于 2026-08-26 被固定阿里云方案替代。**

历史方案曾允许本地/云端、多供应商、任意模型和任意维度。用户现已确认：首期只实现阿里云百炼 DashScope Native，active 模型为 `qwen3.7-text-embedding`、正式默认 2048 维 Dense、cosine；仅允许官方支持的 `256/512/768/1024/1536/2048/2560`，不实现 Ollama、OpenAI 兼容或第二供应商。

未来阿里云新版本仍允许通过 candidate profile 升级，但模型或维度改变必须重建候选 generation 并在验收后原子激活；它不是日常模型下拉框。API Key 轮换不重建；查询侧 instruct、Top-K 或融合权重变化只做检索回归，不重建正文向量。完整决策、fingerprint 分层和失败回退见[第24号专项计划](./24-小说语义检索与向量模型专项施工计划.md)。

仍然有效的数据原则是：查询只使用 active generation，旧向量不得冒充新向量；向量是可重建派生数据；pgvector 精确扫描优先，近似索引只有真实性能证据后才另行批准。参见 [pgvector 官方 FAQ](https://github.com/pgvector/pgvector#can-i-store-vectors-with-different-dimensions-in-the-same-column)。

## ADR-005：建书向导先保存草稿，最终一步原子创建

状态：已采纳。

**项目建议**：从进入建书向导到最终确认之前，只写入有过期时间的 novel_setup_draft，不提前创建 novel。最终创建请求携带 draft_id 和 idempotency_key，由服务端在单个数据库事务内创建 novel、默认卷章骨架、结构化模板快照和系统封面引用，并把草稿标为 created。

原因：

- 用户在思路、模板、命名或封面步骤退出时，不应在作品库留下半成品。
- AI 模板生成可能失败或重试，不能与正式小说生命周期绑死。
- 浏览器刷新、断线和重复点击都需要可恢复、可幂等。
- 作者级私有库会继续变化，作品必须保存创建当时采用的内容与版本快照。
- AI 模板任务状态和候选结果可以绑定草稿，不污染正式作品事务。

创建顺序：

    向导草稿自动保存
      -> 可选 AI 模板幂等生成与流式恢复
      -> 作者确认模板、命名和封面
      -> 最终创建事务
      -> 返回唯一 novel_id
      -> 跳转作品工作台

最终请求网络中断后，客户端必须使用同一 idempotency_key 查询或重放；服务端返回既有 novel_id，不得创建第二部小说。详细字段、API 和验收见[创作中心、私有库与建书向导产品规格](./05-创作中心与建书向导产品规格.md)。

## ADR-006：小说工作台是增量 PawApp，不替换 QwenPaw 页面

状态：已采纳。

**已核实事实**：QwenPaw 2.1.0 的 PawApp manifest 使用 `type: app` 和 `meta.pawapp` 声明应用入口；后端通过公开的 PawApp/Plugin API 注册路由、工具、命令、Hook 和 Skill provider。宿主负责加载应用前端，并共享 React、ReactDOM 和 Ant Design。

**项目决策**：小说工作台与 QwenPaw 原生页面共存：

- QwenPaw 原生首页、聊天、Agent、Provider、Skills、MCP、工具、记忆、频道、任务和设置入口全部保留，URL 和行为不由小说插件接管。
- 小说插件只新增一个“AI小说世界2026”应用入口及其工作台页面。
- 小说前端运行在 QwenPaw 宿主页面内；普通业务请求调用同源 PawApp API，AI 对话通过 `PawAppAgentChatGateway` 进入 QwenPaw Agent。
- 小说后端路由在同一个 QwenPaw FastAPI 进程中挂载，但必须使用独立命名空间；MVP 不启动第二个小说 API 服务。
- PawApp 宿主入口使用 `/apps/ai-novel-world-2026`；PawApp 后端由公开注册接口挂载为 `/api/ai-novel-world-2026/...`。`novels/...` 只作为应用内部页面标识，不注册 `/novels`、`/api/novels` 等全局路由。
- 卸载或禁用小说 PawApp 后，QwenPaw 必须恢复为纯上游状态，不留下被覆盖的路由、菜单或组件。
- 小说不得读取或修改 QwenPaw 私有配置文件，不 monkey patch，不覆盖核心路由，不依赖未公开内部模块。

**非回归门槛**：阶段 2 必须建立 QwenPaw 原生入口和设置的冒烟测试；每次上游升级先在并行环境验证，再切换固定版本。

## ADR-007：自动草稿与不可变 revision 分层

状态：已采纳。

**项目决策**：PostgreSQL 同时保存可变 working copy 和不可变 revision，但两者职责不同：

- 自动保存只以比较并交换方式更新 `document_working_copies`，携带 `draft_version` 和内容哈希；它不会每次击键都制造正式 revision。
- `document_revisions` 只在显式保存、空闲/离开检查点、AI 讨论前检查点和接受 AI 提案时创建。
- 每个 revision 保存 Markdown 权威快照和由固定版本解析器生成的纯文本快照；HTML 预览、Diff、chunks 和向量均在其外部生成。解析器升级不会静默改写旧 revision 的纯文本快照。
- revision 至少区分 `user_checkpoint`、`ai_accepted`、`imported` 和后续明确增加的类型。显式检查点一旦成为 AI proposal 基线，就必须在同一事务移动 `document.current_revision_id` 并与当时 working copy 对齐；历史恢复通过创建新 revision 完成，不把当前指针直接倒拨到旧记录。
- AI 提案同时绑定 `base_revision_id`、`base_draft_version` 和 `base_content_hash`。任一基线变化都不能覆盖当前稿，只能返回冲突并重新计算候选 Diff。
- 发送 AI 消息前，前端先刷新防抖保存并建立检查点；保存失败时必须明确说明 AI 只能看到上次确认版本，同时保留 IndexedDB 恢复稿。
- `novel_chunks` 只绑定不可变 revision，不索引尚未确认的 working copy。
- 默认检索只返回每个 document 当前有效 revision 的 chunks；历史 revision 只有在用户显式请求历史比较时才能进入结果，不能靠“旧向量以后会被覆盖”保证正确性。

## ADR-008：AI 工具按权限分层

状态：已采纳。

所有真正注册给 QwenPaw Agent 的工具使用 `novel_` 命名空间，避免全局工具 ID 冲突。领域服务中的类型化应用命令不等于必须注册为 LLM 工具。

| 执行面 | 能力示例 | 调用规则 |
| --- | --- | --- |
| Agent 只读工具 | `novel_get_context`、`novel_search`、`novel_get_document` | 可以显式 `enabled=True`；服务端从会话绑定确定 novel/document 范围，不信任模型自行扩大范围 |
| Agent 候选工具 | `novel_propose_document_patch`、`novel_extract_story_fact_candidates` | 只能写 proposal/candidate，不得改变 working copy、当前 revision 或正式事实 |
| UI 应用命令 | `save_chapter_draft`、`accept_document_revision` | 由同源 PawApp API 调用同一领域服务，不注册为 LLM 工具；接受还需单次 UI 令牌和三重基线校验 |
| 系统内部命令 | `update_story_facts_after_acceptance`、派生领取与重建 | 由持久执行器调用，不注册为 LLM 工具；冲突事实仍需用户确认 |
| 显式媒体工具 | `novel_synthesize_speech` | 只有明确朗读意图时允许；服务端仍执行缓存、范围和任务状态校验 |

PawApp `@tool` 默认启用，因此每个 Agent 工具必须显式声明启用策略并做安装后注册表测试。表中 UI/系统命令即使保留需求中的概念名称，也不得只靠提示词或前端隐藏来阻止 Agent 调用。工具层、UI API 和后台派生处理必须调用同一个小说领域服务，不能复制业务规则。

首期 Skill 能力基线为：小说方向讨论、故事设定总表/总纲、章节大纲、正文写作、连贯性与小说账本检查、文风审查。这是最小起点，不是永久固定清单；内容可以版本化优化，能力也可以按真实需求新增、拆分、合并或退役。已经对外使用的 Skill ID 变更必须有兼容别名或迁移测试。

QwenPaw 2.1.0 的 Skill provider 会向所有 workspace 安装 Skills 且默认启用，因此项目采用“专用小说 Agent/workspace 中启用”的目标边界；阶段二先验证公开配置路径和插件升级时对 workspace 副本的同步行为。若宿主不能可靠自动限定，则插件注册 `enabled_by_default=False`，由用户在专用小说 Agent 中启用，不能修改 QwenPaw 私有 workspace 文件实现作用域。

## ADR-009：大纲分阶段生成，最终采用前不改变正式作品

状态：已采纳为扩展功能架构；是否进入核心 MVP 尚待阶段 4 前裁决。

**项目决策**：背景、角色、主情节和作品定位的 AI 结果先写入 outline_generation_draft。每一步都可以手填或单独生成，使用 section、input_hash 和 idempotency_key 防止网络重试重复执行。只有用户在最终复核页点击“采用此大纲”后，服务端才在一个 PostgreSQL 事务内创建正式大纲 revisions、确认后的角色资料和目标容量设置。

边界：

- 单步生成任务保留输入哈希、状态、结果哈希和错误诊断；本项目不建设商业用量账本。
- 未采用草稿不得进入正式 AI 上下文、向量、事实账本或章节生成。
- 最终采用必须校验正式大纲基线；另一标签页已经修改时返回冲突。
- 目标章节数只是规划参数，不创建相同数量的空章节。
- 线索、关系网、分卷和章节属于独立候选生成动作，不随大纲提交静默写入。
- 已有正式大纲的“重新生成”产生 proposal 或新候选 revision，不能覆盖当前 revision。
- 最终提交使用 idempotency_key；重放返回同一组正式 revision IDs。

该决策沿用 ADR-007 的 working copy/revision 分层和 ADR-008 的候选生成权限：模型只能写草稿或候选，正式采用由 UI 授权并通过领域服务完成。完整状态机、字段和验收见[分阶段大纲生成与作品初始化产品规格](./07-分阶段大纲生成与作品初始化产品规格.md)。

## ADR-010：重新生成和章节情报同步统一走候选采用协议

状态：已采纳为扩展功能架构；是否进入核心 MVP 尚待阶段 4 前裁决。

**实测证据**：妙笔神书的整套大纲重新生成会替换正式大纲与角色，却保留已有章节；随后章节“同步进展”又可能按姓名新增资料为“未知”的旧角色。重复保存同步结果还会制造多余线索事件。

**项目决策**：大纲重新生成、章纲生成、正文重新生成以及章节情报提取都只能创建 proposal/candidate。它们共享以下安全协议：

- 输入绑定不可变 revision、input_hash、生成器 fingerprint 和 idempotency_key。
- 当前正式数据在用户复核前保持不变。
- 复核页展示逐项 Diff、实体匹配、分类、来源和生成任务状态。
- UI 应用命令在单个事务内采用；网络重放返回同一结果。
- 同一输入的重复同步返回同一提案，不追加重复角色、关系、线路、事件或伏笔。
- 取消采用只拒绝候选，不伪装成已取消仍在运行或已经完成的模型任务。

模型不能获得直接覆盖正式大纲、角色或故事账本的工具。详细内容模型与验收见[创作工作台内容模型与关系图产品规格](./09-创作工作台内容模型与关系图产品规格.md)。

## ADR-011：叙事情报必须绑定来源 revision，并允许人工重分类

状态：已采纳为扩展功能架构。

**实测证据**：章节同步把同事、导师和师徒关系归为“感情线”，并在正文明确写出主线目标时仍没有生成主线事件；线索页又只允许查看和删除，不能编辑或重分类。

**项目决策**：角色、关系、线路事件、伏笔和事实都不得只保存模型结论。每个 AI 候选至少保存来源 `chapter_revision_id`、文本范围、模型任务、输入哈希、置信度、原始建议类型和作者最终类型。线路类型是可配置枚举，`relationship` 与 `romance` 分开；作者可以编辑、移动、合并、拒绝或手工补建事件。

章节正文产生新 revision 后，旧情报不被静默改写或删除，只标记“来源已非当前”并允许重新提取比较。这样既保留审计链，也避免当前版本检索把过期事件误当成无来源事实。

## ADR-012：角色关系语义与关系图布局分离

状态：已采纳为扩展功能架构。

**实测证据**：关系文本和连线可持久化，但双指缩放和节点拖动在刷新后重置；未勾选“单向关系”时编辑器仍显示单箭头文案，Canvas 也缺少可访问的 DOM 语义。

**项目决策**：`character_relationships` 只保存稳定端点、有向/无向、类型、标签、描述和 revision；缩放、平移与节点坐标保存在独立的可选个人 graph view 中。拖动默认只是未保存视图，用户点击“保存布局”后才持久化。任何图操作都必须有等价的键盘可用列表界面；箭头视觉必须由 directionality 唯一决定。

## ADR-013：MOSS-TTS-Nano 是本地模型执行依赖，不是第二套业务服务

状态：技术方案已采纳，物理拓扑待多角色朗读阶段 0 基准冻结。

**项目决策**：浏览器只访问 PawApp API，小说、人物、朗读脚本、持久任务和媒体状态仍全部由现有后端与 PostgreSQL 管理。`TTSAdapter` 后面的 Nano ONNX 可以是后端进程内、后台受管本机进程或 Compose 私有 Sidecar；这三种形态使用相同窄模型契约，由真实 M4 基准选择。

即使采用 Sidecar，它也不能拥有业务路由、任务账本或小说数据库权限，只接受 health/capabilities/warmup/synthesize/cancel 等模型请求，并绑定回环地址或容器私网。它不是第二套 Agent Runtime，也不改变“一个 PawApp 业务 API”的边界。官方浏览器 ONNX 路径只作为低延迟试听候选，不承担正式批量任务、媒体落盘或崩溃恢复。

完整产品、隐私、数据、缓存和实施设计见 [MOSS-TTS-Nano 多角色智能朗读产品与技术设计](./18-MOSS-TTS-Nano多角色智能朗读产品与技术设计.md)。

## 配置与密钥边界

- 聊天模型密钥只保存在 QwenPaw 原生 Provider 服务端配置中。
- Embedding 的 Base URL、API Key、候选模型和维度通过小说 PawApp 的“向量检索与索引”设置页呈现；TTS、图片仍按各自专项配置，不共用向量密钥。
- 用户在设置页首次输入密钥时，明文会短暂存在浏览器内存并通过保存请求发送，这是无法回避的输入过程；浏览器不得把它写入 LocalStorage、IndexedDB、崩溃草稿、日志或遥测，服务端保存后不得在任何读取响应中回显明文，只返回 `configured` 和脱敏提示。
- 如果用户要求密钥完全不经过浏览器，必须使用环境变量或 secret 文件挂载，而不是宣称设置页能做到这一点。
- API Key 的密文可进入项目专用 secret record，但根密钥必须位于数据库之外；实现前先验证是否存在公开 PawApp Secret API，不得假定或偷读 QwenPaw 私有配置。
- QwenPaw Provider 和小说向量配置彼此独立；即使人工输入同一阿里云密钥，插件也不得读取 QwenPaw 核心 Provider 或 ReMeLight 配置。
- 如果 QwenPaw 后续发布通用 PawApp Embedding API，只能在新的兼容性裁决后迁移；不得静默改变当前数据、密钥或索引边界。

QwenPaw 2.1.0 的 `PawAppContext.user` 尚未接入真实认证身份，当前返回 Agent ID。个人 MVP 因此使用固定的本地 owner/profile；数据库中的 `owner_id` 只是未来兼容字段，不作为已核实的多用户安全边界，也不据此建设 RBAC。

## 数据一致性顺序

```text
编辑器自动保存
  -> CAS 校验 draft_version
  -> 更新 PostgreSQL working copy
  -> 必要时创建不可变检查点 revision

用户接受 AI 提案
  -> 校验 current_revision、draft_version、content_hash 均等于 proposal 基线
  -> 单事务创建正式 document_revision、移动当前指针
  -> 同事务写入 background_jobs 待处理记录（scope_kind=revision）
  -> 提交成功
  -> 可恢复执行器领取待处理记录
  -> 生成 revision 绑定的 chunks 并调用 Embedding
  -> 提取带来源的事实候选；冲突项等待用户确认
  -> 可选生成 TTS 缓存
```

正文提交是主事务。向量、事实候选和 TTS 都是幂等、可重试的后续工作；共享 `background_jobs` 通过 `scope_kind/scope_id` 覆盖 revision、音色预览和朗读 Edition 等作用域，保证进程在事务提交后崩溃也不会遗忘任务。QwenPaw PawTask 只用于向 UI 展示运行进度，不作为持久任务权威，也不假定前端取消一定能终止后端工作。

同一派生协议也适用于成为当前版本的 `user_checkpoint` 和 `imported` revision；不能只索引 AI 接受版本，否则作者手写和导入的正文会缺失。是否立即提取事实由 revision 类型和策略决定，但正式检索必须能覆盖当前有效正文。

执行器必须使用 PostgreSQL 原子领取和租约，而不是“查询 pending 后直接运行”：记录至少具有唯一幂等键、`locked_by`、`lease_until`、attempts、next_retry_at、last_error 和终止状态。领取使用事务锁或等价的 `FOR UPDATE SKIP LOCKED` 方案；进程失联后由过期租约重新领取，达到上限后进入可人工重试的 dead-letter 状态。外部模型请求还要保存供应商请求 ID，避免恢复时重复执行。
