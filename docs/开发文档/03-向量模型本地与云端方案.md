# 向量模型本地与云端方案

## 结论

**项目建议**：同时支持本地和云端，通过同一个 `EmbeddingAdapter` 契约接入，**不硬编码供应商、模型名称、部署方式或向量维度**。Ollama Qwen3 Embedding 和阿里云百炼只是预置示例，不是使用限制。

每个向量配置形成一个 `embedding_profile`，记录接口类型、模型名、实际返回维度、归一化方式、查询指令、分块器版本、距离度量、存储类型、索引策略和 fingerprint。检索只比较同一 profile 的向量；更换其中任一影响向量空间的参数时，不得混用旧向量，需为新 profile 重建派生索引。

本地模型不进入默认 Docker Compose，由 macOS 原生 Ollama 运行；QwenPaw 容器和 PawApp 通过 `host.docker.internal:11434` 访问。这样能使用 Apple Silicon 原生加速，并避免在 Linux 容器中绕过 Metal。`11434` 已经是首位为 `1` 的五位端口；未来若容器化，仍只允许发布为 `127.0.0.1:11434:11434`。

## 软件什么时候调用 Embedding

Embedding 只负责“把文本变成可比较的向量”，不生成小说。调用发生在以下时机：

| 场景 | 调用内容 | 频率 |
|---|---|---|
| 接受新正文 revision | 对该不可变 revision 的分块批量向量化 | 每次正式接受或建立需检索的正式检查点后的派生任务 |
| 导入旧章节 | 对导入并确认的正文分块批量向量化 | 每次导入 |
| `search_novel` 语义检索 | 对用户/Agent 的查询生成一个查询向量 | AI 确实需要检索前文时 |
| 重建索引 | 对所有当前有效 revision 分块重新向量化 | 新建/切换 profile、模型、维度、指令或索引损坏时 |
| 质量评测 | 对固定测试集生成向量并比较召回 | 版本升级或模型选择时 |

以下行为不调用：每次键盘输入、每次自动保存草稿、每条普通聊天消息、Diff 渲染、拒绝 AI 提案、读取明确 document ID。这样既降低延迟和无效资源占用，也避免给尚未接受的内容建立正式索引。

“当前有效 revision”必须由数据库关系确定：默认检索把 chunks 与 `documents.current_revision_id` 联结，只返回当前指针指向的 revision。历史 revision 的向量可以保留以便重建和显式历史比较，但不得混入普通 `search_novel`；删除旧向量不是保证检索正确性的前提。

## 模型规格与本机适配

官方模型卡列出 0.6B/4B/8B 三档，32K 上下文，最高维度分别为 1024/2560/4096，并支持自定义较低维度。Ollama 当前模型文件约为：

| Ollama 标签 | 量化/文件大小 | 运行内存项目估算 | 电脑建议 | M4/16 GB 判断 |
|---|---:|---:|---|---|
| `qwen3-embedding:0.6b` | Q8_0，639 MB | 约 1.5–3 GB 峰值，随输入和批量变化 | 8 GB 可用，16 GB 舒适 | **默认推荐**，可与 QwenPaw、Postgres、浏览器并行 |
| `qwen3-embedding:4b` | Q4_K_M，2.5 GB | 约 4–8 GB 峰值 | 最低 16 GB，推荐 24 GB+ | 能跑，但长输入/大批量时可能与 Docker 争内存；只做对比测试 |
| `qwen3-embedding:8b` | Q4_K_M，4.7 GB | 约 7–12 GB 或更高 | 最低 16 GB，推荐 32 GB+ | 不作为默认；容易产生内存压力和系统换页 |

运行内存是**技术推断**，不是 Ollama 的官方保证值；实际值受量化、批量、上下文长度、Ollama 版本和并发影响。正式选择前用本机真实章节做 0.6B 与 4B 的延迟、峰值内存和召回率对比。

官方依据：[Ollama 模型页](https://ollama.com/library/qwen3-embedding)给出 639 MB、2.5 GB、4.7 GB；[Qwen3-Embedding-0.6B 模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)给出参数、32K、维度和评测结果。

## 本地资源占用

- 模型下载占用约 0.64 GB（0.6B）。
- 推理消耗本机内存和 CPU/GPU 时间；个人小说的增量索引是短时任务，不需要 24 小时满载。
- Ollama 可以按需加载/卸载模型；正文和向量仍保存在 PostgreSQL，模型服务停止不会丢数据。
- 初次全书导入或全量重建会短时占用更多资源；应分批、显示进度、允许重试，不阻塞编辑器保存。

本地部署关注并发、峰值内存、温度和对编辑器响应的影响，不建设调用账单。

## 云端适配边界

云端 Embedding 仅作为可选适配器。项目关心协议、维度、限流、超时、数据区域、隐私和失败恢复，不在产品中展示供应商价格、token 余额或费用估算。通过 revision 级增量索引、内容哈希去重和不索引未接受提案，减少无效调用并保持索引可恢复。

## 模型无关接口

```python
class EmbeddingAdapter(Protocol):
    model_fingerprint: str
    dimensions: int

    async def embed_documents(self, texts: list[str]) -> list[list[float]]: ...
    async def embed_query(self, text: str) -> list[float]: ...
    async def healthcheck(self) -> EmbeddingHealth: ...
```

首批实现只是方便开箱，不构成允许列表：

- `OllamaEmbeddingAdapter`：调用 Ollama `/api/embed`；模型名由 profile 配置，可使用任意兼容 Embedding 模型。
- `OpenAICompatibleEmbeddingAdapter`：模型名、Base URL、维度参数和请求头均由服务端配置。
- 其他供应商若协议不同，只增加窄适配器，不改变领域服务和 `novel_chunks`。
- 测试用 `DeterministicFakeEmbeddingAdapter`：不联网，保证单元测试可重复。

每条 `novel_chunks` 至少记录 `revision_id`、`embedding_profile_id`、模型 fingerprint、实际维度、分块器版本、内容哈希和索引状态。查询只能使用与所选 fingerprint、维度、距离度量和规范化配置一致的向量。

MVP 的 pgvector 列不写死 `vector(1024)` 这类 typmod，而使用可记录不同维度的 `vector`，并先采用按 profile 过滤后的精确距离扫描。个人小说数据量下先验证真实延迟；只有数据规模证明需要时，才为固定 profile/维度建立 HNSW 或 partial expression index。这样不会为了索引方便限制模型选择。

pgvector 0.8.6 的近似索引有明确维度上限，必须写进 profile 的索引决策：

| 向量存储/索引 | HNSW/IVFFlat 可索引维度上限 | 项目处理 |
| --- | ---: | --- |
| `vector` | 2,000 | 1024 维可直接建立 profile 专用近似索引；2560/4096 维不能直接这样做 |
| `halfvec` | 4,000 | 2560 维可评估 halfvec 索引及精度影响；4096 维仍超过上限 |
| 无近似索引 | `vector` 最多可存 16,000 维 | 首期按 profile 精确扫描，适合个人小说规模 |

对 4096 维或其他高维模型，允许选择精确扫描、模型支持的较低输出维度、经过评测的 subvector/binary 方案，或以后增加专用检索后端；不得为了建索引而偷偷截断向量。索引策略是 profile 的属性，模型选择不受允许列表限制。

pgvector 官方明确支持用无维度 typmod 的 `vector` 在同一列保存不同维度，并要求近似索引只覆盖同一维度的行；`vector`/`halfvec` 的近似索引维度上限及高维替代方式也由官方文档列出。参见 [官方说明与 partial index 示例](https://github.com/pgvector/pgvector#can-i-store-vectors-with-different-dimensions-in-the-same-column)和 [pgvector 索引说明](https://github.com/pgvector/pgvector#indexing)。

每次创建需要索引的 revision 时，在同一数据库事务写入 `revision_derivations(kind='embedding', status='pending')`。提交后执行器通过 PostgreSQL 原子领取和有期限租约再分块、调用模型；记录至少包含唯一幂等键、attempts、next_retry_at、locked_by、lease_until 和 last_error。若 QwenPaw 或向量服务中途退出，过期租约允许安全续跑；QwenPaw 的任务进度只用于展示，不替代这条持久化恢复链。

## 与 QwenPaw 的关系

QwenPaw 2.1.0 自身可以在 Agent 配置中选择 Ollama 或云 Embedding，但该配置只服务 ReMeLight 记忆，没有供 PawApp 调用的通用 Embedding API。小说索引因此不能直接复用其内部模型对象。

部署时可以让 QwenPaw 记忆和小说 PawApp 指向同一个 Ollama/云端服务和同样的模型名称；也可以使用不同模型。各自仍维护独立索引。小说正文事实留在 PostgreSQL，QwenPaw 记忆索引不能替代 `novel_chunks`。

## 首次基准验收

1. 用 20–50 个真实中文章节构造查询—相关段落小测试集。
2. 比较 0.6B 本地、4B 本地和一个云端 profile 的 Recall@5、平均延迟、P95、峰值内存和索引时间；各模型使用其已验证配置，不要求相同维度。
3. 0.6B 若达到可接受召回率即作为默认；只有明显质量差距才升级 4B。
4. 模拟 Ollama 停止和云 API 500：正文保存必须成功，索引状态进入 `pending/failed`，恢复后重试。
5. 验证模型切换会阻止混用旧向量，并能从 revision 文本全量重建。
