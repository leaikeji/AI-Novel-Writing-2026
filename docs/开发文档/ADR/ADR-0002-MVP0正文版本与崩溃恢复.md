# ADR-0002：MVP-0 正文版本与崩溃恢复

状态：已接受并实现。

决策日期：2026-08-23（Asia/Shanghai）。

## 背景

个人小说工作台需要频繁自动保存，同时必须避免断网、数据库故障、多标签并发或历史恢复造成正文静默丢失。MVP-0 又不应提前引入协同编辑、复杂事件账本或 AI 提案系统。

## 决策

1. PostgreSQL 是小说权威数据源。
2. 每个文档有一份 `document_working_copies` 可变当前稿，包含 `draft_version`、`base_revision_id`、Markdown、内容哈希和更新时间。
3. `document_revisions` 只保存不可变检查点。创建小说时生成空的 initial revision；手动检查点和历史恢复生成新 revision。
4. 自动保存采用 `expected_draft_version` 的 CAS。版本不符返回 409，绝不静默覆盖。
5. 浏览器每次输入先写 IndexedDB 恢复稿，再防抖提交 PostgreSQL；成功后清除恢复稿。
6. 数据库或网络恢复后，页面比较服务器正文与本地恢复稿，由用户点击恢复；恢复动作立即重新走同一 CAS 保存服务。
7. UI API 和 Agent 只读工具共用同一领域服务。MVP-0 不注册任何 Agent 正文写工具。
8. 向量分块表可以随最小迁移存在，但向量数据始终是可重建派生数据，本阶段保持空且不参与读取。
9. 章节列表的 `version_state` 是服务层只读派生值，不增加数据库状态字段：空 initial revision 且无正文为 `empty_draft`，工作稿与基线检查点不一致为 `saved_working_copy`，工作稿与基线检查点一致为 `checkpointed`。当前领域模型没有“已发布”生命周期，UI 不得将任何上述状态表述为已发布；浏览器内尚未同步的输入仍只由编辑器的本地恢复状态表达。

## 后果

- 自动保存不会为每次按键制造不可变 revision；revision 表保持可理解的检查点语义。
- working copy 可以包含尚未建立检查点的最新正式用户输入，PostgreSQL 仍是刷新后的权威来源。
- IndexedDB 不是长期正文库；它只解决尚未同步输入的崩溃恢复。
- 历史恢复不会改写旧 revision，也不会把当前指针静默倒退，而是创建带 `manual_restore` 来源的新版本。
- 章节列表能区分空白草稿、已保存但未建检查点的工作稿，以及与最近检查点一致的正文，而不会引入虚假的发布概念。
- 未来 AI 写回若获批准，必须在此 CAS/revision 基线上新增候选与接受事务，不能绕开版本校验。

## 已验证

- Alembic 升降级往返。
- 同版本首次保存成功、旧版本请求 409、先到正文保持不变。
- 手动检查点与恢复为新版本。
- PostgreSQL 停止期间输入保留在 IndexedDB；恢复后重新同步并刷新持久。
